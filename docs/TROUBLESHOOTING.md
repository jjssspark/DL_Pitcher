## TS-001 · 대용량 CSV·모델이 커밋 이력에 쌓여 .git이 2GB까지 비대화

날짜: 2026-07-27
영역: Infra
심각도: High
상태: 해결됨 (히스토리 재시작)

증상
커밋은 4개뿐인데 git count-objects -vH로 확인한 .git 크기가 로컬 기준 500MB 이상, 패킹된 상태로도 1.4GB를 넘었다.

재현 조건
각 커밋에 Statcast CSV(월별 6개, 전체 87MB), YOLO 사전학습 가중치, 학습된 모델(.h5)이 그대로 커밋되어 있던 상태에서 git count-objects -vH 실행.
재현율: 항상 (이 이력을 갖고 있는 한).

원인
표면 - .git이 비정상적으로 크다.
근본 - .gitignore를 나중에 추가해도 이미 커밋된 이력의 blob은 그대로 남는다. 매달 수십 MB짜리 CSV와 대용량 바이너리가 초기 커밋들에 반복적으로 쌓여 있었다.
확인 방법 - git count-objects -vH로 로컬/패킹 용량을 직접 측정.

시도했지만 안 된 것
시도: .gitignore만 추가
결과: 용량 그대로
이유: 이미 커밋된 과거 이력은 .gitignore의 영향을 받지 않는다

해결
두 선택지(git filter-repo로 과거 이력에서 대용량 blob 제거 / 현재 상태 기준으로 새 히스토리 시작) 중, 커밋이 4개뿐이라 잃을 게 적고 이미 public 저장소라 과거 이력에 민감정보가 없는지도 재확인해야 했기 때문에 새 히스토리로 시작하는 쪽을 선택했다. 기존 히스토리는 로컬 브랜치로 보존.
커밋: 85298e6 Restart project history with a clean, reproducible snapshot

검증
새 root 커밋 이후 서비스가 의존하는 모델 3개(pitch_predictor.h5, scaler.pkl, baseball_detector.pt)만 Git LFS로 추적되고, 재수집·재학습 가능한 대용량 산출물(Statcast CSV, YOLO 학습셋, 사전학습 체크포인트)은 .gitignore로 제외됨을 확인.

추후 관리
재발 방지 - .gitattributes에 LFS 추적 대상을 명시하고, .gitignore에 재생성 가능한 대용량 산출물을 등록해뒀다.
남은 리스크 - 새 기여자가 대용량 파일을 실수로 다시 커밋하면 동일 문제가 재발할 수 있다. pre-commit 파일 크기 훅은 아직 없음.

배운 점
.gitignore는 미래의 커밋만 막는다. 이미 이력에 들어간 대용량 파일은 별도로 제거하지 않는 한 저장소에 영구히 남는다. 커밋 수가 적을 때 정리하는 비용이 가장 낮다.

## TS-002 · 프로젝트 폴더 이동 후 venv의 pip가 shebang 경로 문제로 깨짐

날짜: 2026-07-27
영역: Build
심각도: Medium
상태: 우회 적용

증상
venv/bin/pip freeze를 실행하면 다음 에러가 났다.

bad interpreter: No such file or directory

재현 조건
환경: macOS, Python 3.13 venv
재현 절차: venv를 /Users/tina/Desktop/baseball-pitch-predictor에서 생성 → 프로젝트 폴더를 /Users/tina/Project/baseball-pitch-predictor로 이동 → venv/bin/pip freeze 실행
재현율: 항상

원인
표면 - pip 실행이 안 됨.
근본 - venv 생성 시 pip, pip3, ipython 등 콘솔 스크립트의 첫 줄(shebang)에 인터프리터의 절대경로가 하드코딩된다(#!/Users/tina/Desktop/.../venv/bin/python3.13). 폴더를 옮기면 이 경로가 더는 존재하지 않아 셸이 인터프리터를 못 찾는다.
확인 방법 - venv/pyvenv.cfg와 콘솔 스크립트 첫 줄을 직접 열어 옛 경로(/Desktop/...)가 박혀 있는 것을 확인.

시도했지만 안 된 것
시도: venv/bin/pip 직접 실행
결과: 동일 에러
이유: 스크립트 자체의 shebang이 깨진 것이라 실행 방식을 바꿔도 소용없음

해결
venv/bin/python3.13은 시스템 Python으로의 심볼릭 링크라 경로 이동의 영향을 받지 않는다는 점을 이용해, 인터프리터를 직접 호출하는 방식으로 우회했다.

venv/bin/python3.13 -m pip freeze

requirements.txt 자체는 pip freeze에 의존하지 않고, site-packages의 *.dist-info 폴더명에서 패키지명·버전을 직접 파싱해서 만들었다.

검증
위 명령으로 패키지 목록을 정상적으로 얻어 requirements.txt를 작성했다.

추후 관리
재발 방지 - 근본 해결은 아니다. venv 자체를 새로 만드는 것이 가장 깔끔한 해법으로 남아 있다.
남은 리스크 - 이 venv를 다시 옮기면 동일 증상이 재발한다.

배운 점
venv의 콘솔 스크립트(pip, ipython 등)는 인터프리터 경로가 생성 시점에 고정된다. venv 폴더(또는 상위 프로젝트 폴더)를 옮기면 항상 깨진다고 가정해야 하고, python -m pip 형태로 인터프리터를 직접 호출하면 임시 우회가 가능하다.

재발 (2026-08-05) - 같은 venv를 git worktree(`.claude/worktrees/pitch-type-cv-classifier/venv` 심볼릭 링크)에서 참조했을 때 `venv/bin/jupyter`, `venv/bin/pip`가 동일하게 `bad interpreter` 에러로 깨져 있는 것을 재확인. `venv/bin/python3 -m nbconvert`, `venv/bin/python3 -m pip`처럼 `python3 -m <module>` 형태로 우회해 해결 — 근본 원인과 우회법 모두 이 항목과 동일.

## TS-003 · opencv-python과 opencv-python-headless 동시 설치로 인한 충돌 위험

날짜: 2026-07-27
영역: Build
심각도: Medium
상태: 해결됨

증상
의존성 점검 중 opencv-python과 opencv-python-headless가 같은 환경에 동시에 설치되어 있는 것을 발견했다. 둘 다 cv2 모듈을 제공한다.

원인
표면 - 같은 모듈(cv2)을 제공하는 패키지가 두 개 설치되어 있다.
근본 - 어느 패키지가 실제로 로드되는지가 설치 순서에 따라 달라진다. GUI가 없는 서버/배포 환경(Streamlit Cloud 등)에서는 opencv-python이 불필요한 GUI 의존성(X11 등) 때문에 임포트 에러를 일으킬 수 있다.

해결
requirements.txt에 opencv-python-headless 하나만 남기고 주석으로 이유를 명시했다.

opencv-python-headless==4.10.0.84
(주석: opencv-python 과 opencv-python-headless 가 동시에 설치되어 있으면 로드되는 cv2가 설치 순서에 따라 달라질 수 있음. GUI가 필요 없으므로 headless 하나만 남기는 것을 권장)

검증
pip list에서 opencv-python이 없고 opencv-python-headless만 남아 있는 것을 확인.

추후 관리
재발 방지 - 새 의존성 추가 시 pip list | grep opencv로 중복 설치 여부를 확인하는 습관을 남겼다.

배운 점
같은 최상위 모듈(cv2)을 제공하는 패키지가 여러 개 설치돼도 pip나 import는 에러를 내지 않는다. 배포 환경(GUI 없음)을 기준으로 어떤 변형이 필요한지 미리 결정해야 한다.

## TS-004 · 헤드리스 환경에서 matplotlib 한글 그래프가 네모(tofu)로 깨짐

날짜: 2026-08-03
영역: ML/Viz
심각도: Low
상태: 해결됨

증상
src/evaluate.py로 혼동행렬·클래스별 정확도 그래프를 재생성했더니, 그래프의 한글 라벨(구종명, "정확도" 등)이 전부 빈 네모(tofu)로 나왔다.

재현 조건
환경: macOS 로컬에서는 발생하지 않고, CI/서버처럼 시스템 한글 폰트가 없는 헤드리스 환경에서 재현.
재현 절차: plt.rcParams["font.family"]를 지정하지 않은 채 한글 라벨이 포함된 그래프 생성.
재현율: 항상 (한글 폰트 미탑재 환경에서).

원인
표면 - 그래프의 한글 텍스트가 깨짐.
근본 - matplotlib 기본 폰트(DejaVu Sans)에 한글 글리프가 없다. 로컬 macOS에서는 matplotlib이 시스템 폰트(AppleGothic 등)를 알아서 찾아 쓰기 때문에 문제가 드러나지 않았을 뿐이다.
확인 방법 - 로컬(정상)과 폰트가 다른 환경을 비교해 동일 코드에서 결과가 갈리는 것을 확인.

해결
src/evaluate.py에 폰트 우선순위를 지정하고, 마이너스 기호 깨짐도 함께 방지했다.

plt.rcParams["font.family"] = ["NanumGothic", "AppleGothic", "Malgun Gothic"]
plt.rcParams["axes.unicode_minus"] = False

검증
그래프를 재생성해 한글 라벨이 정상 출력되는 것을 확인 (notebooks/figures/07_confusion_matrix.png 등).

추후 관리
재발 방지 - 우선순위 리스트 방식이라 실행 환경에 셋 중 하나만 있어도 동작한다.
남은 리스크 - Streamlit Cloud 배포 환경에는 위 폰트가 기본으로 없을 수 있다. 배포 시 폰트 설치 단계가 필요하다는 것을 로드맵에 남겨뒀다(docs/ROADMAP.md).

배운 점

시도했지만 안 된 것
해당 없음 — requirements.txt의 사전 주석 덕분에 원인을 바로 특정할 수 있었다.

해결
Streamlit Cloud는 packages.txt에 적힌 패키지를 apt-get으로 설치해준다는 점을 이용해, 루트에 packages.txt를 추가했다.

tesseract-ocr

커밋: 889da2f chore: Streamlit Cloud 배포용 packages.txt 추가 (tesseract-ocr)

재발 방지 - Python 패키지가 시스템 바이너리에 의존하는 경우(pytesseract, ffmpeg 등) requirements.txt 주석뿐 아니라 packages.txt도 같이 챙기는 것을 배포 체크리스트에 남긴다.

2. playerVars에 autoplay: 1, mute: 1 추가 (브라우저 자동재생 정책상 음소거 없이는 자동재생 불가).

추후 관리
재발 방지 - 없음.

## TS-007 · OCR 이벤트 기반 투구-영상 싱크가 20% 커버리지 한계로 2구째부터 어긋남

날짜: 2026-08-04
영역: FE
심각도: High
상태: 우회 적용

증상
1구는 정확했지만 2구째부터 표시되는 구종/싱크가 실제 영상과 어긋났다.

재현 조건
환경: Streamlit Community Cloud 배포, 고정 데모 모드(game_pk=775300, 고정 YouTube 영상).
재현 절차: 영상 재생하며 2번째 투구 이후 표시되는 구종/구속을 실제 중계와 대조.
재현율: 항상 (OCR 커버리지가 구조적으로 낮음).

원인
표면 - 특정 투구부터 표시되는 싱크가 실제와 안 맞음.
근본 - 정적 OCR 스캔이 320구 중 65개(~20%)만 감지했다. 감지 이벤트 사이 간격 동안 실제로는 여러 투구가 지나가는 경우가 흔해, 이벤트 기반 순차/점프 로직으로는 근본적으로 정확한 싱크가 불가능한 구조였다.
확인 방법 - "1~5이닝 캡이 조기 종료 원인"이라는 가설로 OCR 스캔을 이닝 제한 없이 재생성했으나, 결과 파일이 이전과 MD5 완전 동일 → 가설 기각. 캡이 아니라 OCR 인식률 자체가 낮은 것이 원인임을 확인.

시도했지만 안 된 것
시도: OCR 정적 스캔 타임스탬프 기반 순차(+1) 싱크, "P:N" 카운트 점프 감지
결과: 1구는 맞았지만 2구부터 어긋남
이유: 320구 중 65개(~20%)만 감지되는 낮은 OCR 커버리지 — 감지 간 간격이 실제로는 여러 투구를 건너뛰는 경우가 흔함

시도: 이닝 캡(max_pitches=140)이 조기 종료 원인이라는 가설로 OCR 스캔 재생성
결과: 재생성 파일이 이전과 MD5 동일 — 가설 기각
이유: 애초에 이닝 캡에 도달한 적이 없었고, 진짜 원인은 OCR 자체의 낮은 인식률이었음

해결
근본적으로 OCR 이벤트 기반 싱크를 포기하고 "영상 재생시간 ÷ 전체 길이 × 총 투구수"로 인덱스를 추정하는 시간 비례 방식으로 전환했다 (streamlit_app/app.py, 커밋 2112ebc). 이 전환 직후 남아있던 경계값 잔여 버그 2건은 TS-008 참고.

검증
배포 사이트에서 투구가 끊기거나 한 인덱스에 고정되지 않고 매끄럽게 진행되는 것을 확인.

추후 관리
재발 방지 - 없음.
남은 리스크 - 시간 비례 방식은 프레임 단위 정확도를 포기한 근사치다. 이닝별로 투구 간 실제 간격이 크게 다를 수 있어(공수교대, 중계 지연 등) 표시되는 투구가 점점 실제와 벌어질 수 있다 — 사용자가 인지하고 승인한 트레이드오프.

배운 점
감지 커버리지가 낮은 이벤트 기반 시스템은 "이벤트 사이 간격 동안 상태가 그대로"라고 가정하면 안 된다. 원인 불명의 증상을 만났을 때 가장 그럴듯한 가설(이닝 캡)부터 검증했지만 틀렸고, 재생성 파일의 MD5를 비교하는 저비용 검증으로 가설을 빠르게 기각할 수 있었다.

## TS-008 · 시간 비례 싱크 전환 후에도 경계값(t≈0)에서 투구 인덱스가 실제보다 앞서 표시

재현 절차: 페이지 새로고침 → 자동 로드 완료 직후 / 재생 시작 직후 화면 확인.

확인 방법 - 코드를 직접 추적해 _vid_t/_vid_pl 세션 상태 갱신 순서와 조건문을 특정. 수정 후 배포 사이트 스크린샷으로 "투구 타임라인 0" 상태가 재생 시작 전까지 유지되는 것을 확인.

이유: target_idx + 1 선행 오프셋이 별개 원인으로 남아 있었음

해결
streamlit_app/app.py 두 곳 수정:
1. _vid_t is not None and loaded → _vid_t is not None and loaded and _vid_pl 로 조건 강화 (커밋 0f9822b)
2. _new_cidx_ts = min(_target_idx + 1, len(pitches)-1) → _new_cidx_ts = max(0, min(_target_idx, len(pitches)-1)) 로 선행 오프셋 제거 (커밋 566aed8)

검증
배포 사이트 새로고침 직후 스크린샷 — "투구 타임라인 0" 유지, "방금 던진 구종" 카드는 "경기 로드 후 재생" placeholder만 표시되는 것 확인.

추후 관리
재발 방지 - 없음 (자동 테스트 없이 수동 스크린샷 검증에 의존).
남은 리스크 - 없음 (경계값 버그 자체는 완전히 해결. 시간 비례 방식 자체의 근사치 한계는 TS-007 참고).

배운 점

상태: 우회 적용

증상
배포된 Streamlit 앱에서 영상 영역이 완전히 검은 화면으로 나오고, 재생 버튼도 안 보이고 재생도 안 됐다. 사용자 보고: "영상 재생바 안뜨고 / 영상 재생도 안됏는데 바로 방금던진구종이 뜸" (이후 "이번엔 영상 재생이 아예 안된느데?"로 재확인).

오류 153 / 동영상 플레이어 구성 오류 (embed URL 직접 접속 시 유튜브 네이티브 오류 화면)

재현 조건
환경: Streamlit Community Cloud 배포, streamlit_app/youtube_player 커스텀 컴포넌트 (Streamlit 컴포넌트 iframe 안에 YouTube IFrame API iframe을 다시 중첩하는 구조).
재현 절차: 배포 URL 접속 → 고정 데모 자동 로드 → 영상 영역 확인.
재현율: 이 세션에서는 100% (자동화 브라우저, 배포 페이지에서 실제 사용된 embed URL을 직접 열어도 동일 재현). 이전 라운드에는 정상 재생됐다는 보고("아 되네")도 있어 간헐적 성격도 있음.

원인
표면 - 유튜브 iframe 자체가 렌더링되지 않고 완전히 검은 화면으로 남음.
근본 - youtube_player 커스텀 컴포넌트가 이미 Streamlit이 만든 컴포넌트 iframe 안에서 다시 YouTube IFrame API로 또 다른 iframe을 로드하는 "iframe 안의 iframe" 구조였다. 배포 페이지에서 실제 network 요청으로 사용된 embed URL(정확한 origin/referrer/enablejsapi 파라미터 포함)을 그대로 브라우저에서 직접 열어보니 유튜브가 "오류 153: 동영상 플레이어 구성 오류"를 반환 — 이중 iframe 중첩 상황에서 origin 파라미터가 실제 최상위 origin과 일치하지 않아 유튜브 측 검증에 실패하는 것으로 추정.
확인 방법 - (1) 배포 페이지의 network 요청에서 실제 embed URL을 캡처, (2) 그 URL을 그대로 브라우저에서 열어 유튜브 네이티브 오류 화면(오류 153)을 재현 확인.

시도했지만 안 된 것
시도: TS-006의 레이스 컨디션/autoplay 수정 (window.YT 가드 + playerVars autoplay/mute)
결과: 단독 테스트 페이지에서는 재생 상태 도달, 배포 환경에서는 여전히 검은 화면
이유: 레이스 컨디션은 별개 문제였고, 오류 153의 근본 원인(이중 iframe origin 불일치)은 그대로 남아 있었음

시도: origin/referrer 파라미터를 애플리케이션 코드에서 직접 조정
결과: 검토 후 폐기, 시도하지 않음
이유: Streamlit 컴포넌트 iframe이 생성하는 origin은 Streamlit 프레임워크 내부 영역이라 애플리케이션 코드로 제어 불가능

해결
streamlit_app/app.py의 영상 렌더링 분기 수정 — 로컬 파일 재생(local_video_player, 로컬 개발 전용)은 그대로 두고, YouTube 재생 경로만 커스텀 youtube_player 컴포넌트 대신 Streamlit 기본 st.video(url, autoplay=True, muted=True)로 교체. 더 이상 쓰이지 않는 _yt_id()/_yt 제거. (커밋 f24213d)

검증
배포 사이트 스크린샷으로 유튜브 네이티브 플레이어(제목·재생바·컨트롤 포함)가 정상 렌더링되는 것을 확인.

추후 관리
재발 방지 - 없음 — 근본 원인(Streamlit 컴포넌트 iframe 안에서의 YouTube IFrame API 중첩 자체)은 회피했을 뿐 고치지 않음.
남은 리스크 - 실시간 재생 시간 이벤트를 더 이상 받을 수 없어, 자동 투구 싱크(시간 비례 방식, TS-007/TS-008 참고)가 YouTube 경로에서는 동작하지 않게 됨 — 수동 슬라이더/이전·다음 버튼으로 대체. 향후 실시간 싱크가 다시 필요해지면 iframe 중첩이 없는 방식(단일 iframe에 직접 YT.Player 마운트, 또는 서버 사이드 폴링)을 검토해야 한다.

배운 점
Streamlit components.v1.declare_component로 만든 컴포넌트는 그 자체가 이미 하나의 iframe이라, 그 안에서 또 다른 서드파티 iframe(YouTube 등)을 API 기반으로 제어하려 하면 "iframe 안의 iframe"이 되어 origin 검증에 실패할 수 있다. 서드파티 임베드는 가능하면 최상위 페이지에 가장 가까운 곳에서 렌더링하거나, 프레임워크가 제공하는 네이티브 위젯이 있다면 커스텀 컴포넌트보다 그걸 먼저 검토하는 게 안전하다.

## TS-010 · git worktree로 전환하기 직전 커밋 없이 작성한 파일이 워크트리에는 보이지 않아 유실

날짜: 2026-08-05
영역: Infra
심각도: Medium
상태: 해결됨

증상
브레인스토밍 스킬로 설계 문서를 작성·커밋한 뒤, 이어서 구현 계획 문서(`docs/superpowers/plans/2026-08-05-pitch-type-cv-classifier-pilot.md`)를 메인 체크아웃에 Write로 작성했다. 곧바로 `EnterWorktree`로 격리된 작업공간으로 전환한 뒤 `sdd-workspace` 스크립트로 그 계획 파일을 읽으려 하자 `no such plan file` 에러가 났다.

재현 조건
환경: 같은 저장소 안에서 Write 도구로 새 파일 생성 → git add/commit 하지 않은 상태 → EnterWorktree(name=...)로 새 워크트리 진입.
재현율: 항상 (커밋 없이 작성한 파일이 있는 상태에서 워크트리 전환 시).

원인
표면 - 방금 만든 파일이 새 워크트리 디렉터리에 없다.
근본 - git worktree는 같은 `.git` 객체 저장소를 공유하지만 워크트리마다 독립된 작업 디렉터리(파일시스템)를 갖는다. 커밋되지 않은 워킹트리 변경분은 git 객체가 아니라 순수 파일시스템 상태이므로, 다른 워크트리에서는 애초에 존재할 방법이 없다. `EnterWorktree`는 브랜치(커밋 이력) 기준으로 워크트리를 만들 뿐, 원본 체크아웃의 미커밋 변경분을 복사해오지 않는다.
확인 방법 - 워크트리 진입 후 `ls docs/superpowers/plans/`로 해당 파일이 없는 것을 확인, `git status --short`로 원본 체크아웃 쪽에는 아직 untracked 상태로 남아있었을 것으로 추정(직접 재확인은 샌드박스 제약으로 워크트리 세션에서 다른 워크트리 경로에 대해 `git -C`를 쓸 수 없어 못함).

시도했지만 안 된 것
없음 — 원인이 명확해서 바로 우회로 넘어감.

해결
같은 내용을 워크트리 안에서 Write로 다시 작성하고 그 자리에서 커밋했다. 이후 `sdd-workspace`/`task-brief` 스크립트가 정상적으로 파일을 찾음.

검증
`sdd-workspace docs/superpowers/plans/...pilot.md` 재실행 시 정상적으로 워크스페이스 경로 출력, 이후 태스크별 `task-brief` 생성도 문제없이 진행됨.

추후 관리
재발 방지 - 앞으로 이런 워크플로(브레인스토밍 → writing-plans → subagent-driven-development)를 이어서 진행할 때는, 워크트리 전환 직전에 만든 파일은 반드시 커밋까지 마치고 나서 EnterWorktree를 호출한다.
남은 리스크 - 아래 정정 참고. 커밋해도 완전히 안전하지는 않다.

정정 (2026-08-05, 최종 브랜치 리뷰 중 발견) - 최초 진단이 절반만 맞았다. 이번 세션에서 실제로 유실된 파일은 두 종류였다.
(1) 구현 계획 문서(`docs/superpowers/plans/...pilot.md`) — Write만 하고 커밋 안 한 상태에서 워크트리 전환 → 원인은 위에 기록한 그대로.
(2) 설계 스펙 문서(`docs/superpowers/specs/2026-08-05-...design.md`) — 이건 실제로 로컬 main 브랜치에 **커밋까지 했었다**(커밋 11f880c). 그런데도 워크트리에는 없었다. `git merge-base --is-ancestor 11f880c HEAD`로 확인해보니 11f880c는 워크트리 브랜치의 조상이 아니었다. 원인은 `EnterWorktree`의 `worktree.baseRef` 기본값이 `fresh`라는 점 — 이는 로컬 `main` HEAD가 아니라 **`origin/main`(원격 추적 브랜치)**을 기준으로 새 브랜치를 만든다. 그 시점에 로컬 main은 이미 11f880c까지 진행했지만 아직 push 전이라 origin/main은 그 이전 커밋(6f6abf2)에 머물러 있었고, 그 결과 로컬에만 있던 커밋이 통째로 새 워크트리 브랜치에서 빠졌다.
즉 "커밋했으니 안전하다"가 성립하려면 **push까지 돼 있거나, `worktree.baseRef=head`로 로컬 HEAD 기준 분기**해야 한다. 재발 방지 항목을 이렇게 정정한다: 워크트리 전환 전에는 (a) 커밋 여부뿐 아니라 (b) 그 커밋이 origin에 반영됐는지, 또는 baseRef 설정이 로컬 HEAD 기준인지도 함께 확인해야 한다.

배운 점
git worktree는 "같은 저장소의 다른 브랜치를 보는 창"이지 "같은 작업 디렉터리의 스냅샷"이 아니다. 커밋되지 않은 파일은 그 워크트리에만 속한다. 나아가 로컬에만 있고 origin에 push하지 않은 커밋도, 워크트리 도구가 기본적으로 origin 기준(`fresh`)으로 브랜치를 만든다면 새 워크트리에서 조용히 빠질 수 있다 — "커밋했다"와 "다른 워크트리에서 보인다"는 별개의 조건이다.

## TS-011 · 360p 하드코딩 다운로드로 오버레이 OCR이 23%만 검출되어 CV 파일럿 데이터셋이 통째로 비어서 중단

날짜: 2026-08-05
영역: ML
심각도: High
상태: 해결됨

증상
CV 구종 그룹 분류기 파일럿(`scripts/build_pitch_group_dataset.py`)을 실제 경기(game_pk=775294, 2024 WS G1) 하나로 처음 돌리자 데이터셋이 0행으로 나오고 중단됐다.

```
OCR 타임스탐프(65개)와 Statcast 투구 수(280개)가 달라 앞에서부터 65개만 매칭합니다.
game_pk=775294 OCR-Statcast 구종 그룹 일치율이 25.6%로 낮아 페어링 밀림이 의심됩니다. 이 경기 데이터를 제외합니다.
[중단] 생성된 데이터셋이 비어 있습니다. 위 경고 로그를 확인하세요.
```

재현 조건
환경: macOS, `yolo_detector.resolve_video_path()`로 받은 YouTube 영상(640x360, 29.97fps, 137분), tesseract OCR.
재현율: 항상.

원인
표면 - OCR이 280구 중 65구(23%)만 검출했고, 검출된 것마저 Statcast 구종 시퀀스와 25.6%만 일치했다.
근본 - `yolo_detector.resolve_video_path()`가 yt-dlp 포맷 셀렉터에 `height<=360`을 하드코딩하고 있었다. 이 함수는 원래 공 모션 감지 데모용(속도·용량 우선)으로 만들어졌고 OCR 판독을 고려한 적이 없다. 360p에서 Fox 스코어보드의 구속·구종 텍스트는 원본 크롭 기준 각각 약 12x80px, 16x205px로, 압축 노이즈와 모션 블러가 겹치면 tesseract가 프레임마다 다르게 오독한다. 그 결과 "MPH" 부분문자열 매칭과 "P:N" 정규식이 대부분의 샘플에서 조용히 빗나갔다.
확인 방법 - 스캔 로직(15프레임 간격 샘플링 + 해시 변화 감지 + 임계값 이진화)을 그대로 복제해 필터링 **전** 원시 OCR 출력을 구간별로 로깅했다. 1200~1500초 5분 구간에서 260샘플 중 "MPH"가 깨끗하게 잡힌 건 2건뿐이었고, 나머지 다수는 오버레이가 없는 게 아니라 콜론이 빠진 "PN", M이 빠진 "PH" 같은 오독이었다.

시도했지만 안 된 것
- 처음 세운 가설은 "크롭 위치가 잘못됐다"였다. 넓은 하단 크롭을 떠서 육안 확인했더니 실제 스코어보드("KNUCKLE CURVE / 82MPH / COLE / NYY 0 LAD 0")와 정확히 맞아 있었다 — 위치 문제가 아니었다.
- 두 번째 가설은 "360p면 무조건 못 읽는다"였는데, 프레임 한 장을 뽑아 5~6배 업스케일하니 사람 눈에는 읽혔다. 즉 "항상 불가"가 아니라 "프레임마다 되다 안 되다" 하는 문제였고, 이 구분이 원인 특정의 열쇠였다.

해결
`yolo_detector.py`는 기존 데모 파이프라인이 공유하고 설계 문서상 비범위(수정 금지)라 건드리지 않았다. 대신 파일럿 스크립트 안에 720p 다운로더 `resolve_video_hq()`를 새로 만들고, 캐시 파일명도 `pitchiq_hq_yt_<id>.mp4`로 분리해 기존 360p 캐시와 충돌하지 않게 했다.

검증
같은 1200~1500초 구간을 720p 영상으로 재계측: 원시 "MPH" 검출 2건 → 18건(9배). 이어 전체 경기 실행에서 OCR 검출이 65개 → **237개(280구 중 85%)**로 올라갔고, 일치율 게이트에 걸리지 않고 다음 단계로 진행됐다.

추후 관리
재발 방지 - OCR을 쓰는 경로와 모션 감지만 쓰는 경로는 요구 해상도가 다르다. 영상 획득 함수를 공유할 때 해상도 가정을 호출부가 아니라 함수 안에 숨겨두면 이런 식으로 조용히 어긋난다.
남은 리스크 - 여전히 15%는 미검출이다. 파일럿 표본 확보에는 충분하지만, 1080p 상향이나 크롭·전처리 튜닝 여지가 남아 있다. 720p 파일은 경기당 약 1.2GB로 360p(455MB)의 2.6배라 디스크 사용량이 늘어난다.

배운 점
파이프라인이 비어 있는 결과를 낼 때, 새로 만든 코드보다 **재사용한 기존 코드의 숨은 가정**을 먼저 의심해야 한다. 이번에 신규 패키지(`pitch_type_cv`)의 안전장치(일치율 50% 미만이면 해당 경기 제외)는 정확히 설계대로 작동해 오염된 데이터가 학습셋에 들어가는 것을 막았다 — 빈 데이터셋은 버그가 아니라 안전장치가 일한 결과였다. 또한 "읽히나?"를 한 장으로 확인하는 것과 "일관되게 읽히나?"를 분포로 확인하는 것은 전혀 다른 질문이다.

## TS-012 · 720p 전환 후 궤적 추출이 4배 느려짐 — 59.94fps와 MPS 미사용, 그리고 내림 연산이 샘플링을 무효화

날짜: 2026-08-05
영역: ML
심각도: Medium
상태: 해결됨

증상
TS-011 수정(720p 전환) 후 OCR은 237개까지 정상 검출됐으나, 그다음 궤적 추출 단계에서 진행이 거의 멈춘 것처럼 느려지고 아래 로그가 수백 줄 쏟아졌다.

```
[OCR] 7975.5s → Fastball Nonemph
[OCR] 완료: 237개 감지 (예상 0개)
OCR 타임스탐프(237개)와 Statcast 투구 수(280개)가 달라 앞에서부터 237개만 매칭합니다.
[h264 @ 0x340f54470] mmco: unref short failure
```

재현 조건
환경: macOS(Apple Silicon), 720p 59.94fps 영상, yolov8n, `extract_trajectory_window()` 기본 윈도우(t-3.0s ~ t-0.3s).
재현율: 항상.

원인
표면 - `mmco: unref short failure`가 계속 출력되며 느려 보였다.
근본 - 세 가지가 겹쳤고, **눈에 띈 로그는 원인이 아니었다**.
(1) `mmco` 경고는 임의 위치 시크 시 H.264 디코더가 참조 프레임을 잃으며 내는 무해한 경고다. 실측 결과 디코딩·시크는 투구당 0.8~1.0초로 전체의 4%에 불과했다. 나머지 96%는 YOLO 추론이었다.
(2) 720p 다운로드는 **59.94fps**였다(360p는 29.97fps). 같은 2.7초 윈도우가 81프레임 → 163프레임으로 두 배가 됐다. 원 설계는 30fps 기준(`yolo_detector.DEFAULT_FPS = 30`)이었으므로 이는 의도치 않은 배증이다.
(3) Ultralytics는 macOS에서 MPS를 자동 선택하지 않아 CPU로 돌고 있었다(125ms/frame).
확인 방법 - 한 윈도우에 대해 디코딩 시간과 YOLO 시간을 분리 계측하고, CPU/MPS × 전체프레임/절반샘플링 × 1장씩/배치16의 6개 조합을 실측 비교했다.

시도했지만 안 된 것
- **배치 추론(batch=16)**: 이론상 가장 유망해 보였으나 실측에서 오히려 느렸다(MPS 기준 절반샘플링 3.10s → 8.80s). `WARNING ⚠️ NMS time limit 2.050s exceeded`가 뜨는 것으로 보아 NMS가 병목이었다. 채택하지 않았다.
- **첫 수정이 조용히 무효였다**: `target_fps` 샘플링을 넣고 유닛 테스트 37개가 전부 통과했는데, 실제 영상에서 궤적 포인트가 61/32/72로 **수정 전과 완전히 동일**했다. 원인은 `step = int(fps / target_fps)` — `59.94 / 30.0 = 1.998`을 내림하면 **1**이 되어 샘플링이 통째로 사라진다. 합성 테스트 영상은 정확히 60.0fps라 `2`가 나와 통과해버렸다. NTSC 프레임레이트(29.97/59.94)는 정수 배수에서 미세하게 어긋난다는 점을 놓친 것이다.

해결
`yolo_detector.py`·`pose_detector.py`는 설계상 비범위라 그대로 두고, 파일럿 범위 안에서만 고쳤다.
- `frames_in_window()`/`extract_trajectory_window()`에 `target_fps: float | None = None` 추가(기본값 None이라 기존 호출부 5곳 전부 동작 불변). 건너뛸 프레임은 `grab()`만 호출해 BGR 변환·복사를 생략.
- 스텝 계산을 `_sampling_step()` 순수 함수로 분리하고 **내림 대신 반올림**으로 교체. NTSC 케이스(59.94/30 → 2, 29.97/30 → 1, 30/60 → 1)를 검증하는 회귀 테스트 추가.
- 파일럿 스크립트에서 `torch.backends.mps.is_available()`일 때 `yolo_model.to("mps")`, `target_fps=30.0` 전달.
- `OPENCV_FFMPEG_LOGLEVEL=-8`을 cv2 import 전에 설정해 무해한 h264 경고 로그만 억제.

검증
유닛 테스트 37개 전부 통과. 실제 영상 3개 윈도우 실측에서 궤적 포인트가 61/32/72 → 30/16/37로 정확히 절반이 되어 샘플링 적용을 확인했고, 투구당 20.3초 → 9.8초(237투구 환산 80분 → 39분)로 개선됐다.

추후 관리
재발 방지 - 프레임레이트가 걸린 계산은 합성 60.0fps 영상만으로 검증하면 안 된다. 실제 방송 영상은 NTSC(29.97/59.94)다.
남은 리스크 - 벤치 예측은 12분이었으나 실측은 39분이었다. 차이는 디코딩 비용으로, 82프레임을 고르려면 163프레임을 모두 디코딩해야 하기 때문이다. 키프레임 기반 시크나 윈도우 축소(설계 문서가 "첫 경기로 실측 보정 필요"라고 명시한 t-3.0s~t-0.3s 범위)로 더 줄일 여지가 있다.

배운 점
가장 시끄러운 로그가 가장 중요한 원인인 경우는 드물다 — `mmco` 경고는 수백 줄이 떴지만 비용의 4%였고, 조용한 CPU 폴백이 96%였다. 그리고 **유닛 테스트 통과가 수정 적용을 보장하지 않는다**. 합성 픽스처가 실제 데이터의 성질(NTSC 프레임레이트)을 갖고 있지 않으면, 테스트는 통과하면서 프로덕션에서는 아무 일도 일어나지 않는다. 이번에는 실제 영상으로 사후 실측을 한 덕에 잡았다.

## TS-013 · COCO 'sports ball' 오탐으로 궤적의 65%가 랜덤워크였고, 그 노이즈가 가짜 그룹 분리를 만들어냄

날짜: 2026-08-05
영역: ML
심각도: High
상태: 우회 적용

증상
TS-012 수정 후 첫 데이터셋(233샘플)이 정상 생성됐고, 그룹별 특징 중앙값이 아래처럼 크게 갈렸다. 이 시점에는 "궤적 특징이 구종 그룹을 구분한다"는 신호로 보였다.

```
group      curvature_ratio  vertical_drop_px
FASTBALL              7.09              65.5
BREAKING             20.75              29.7
```

그러나 곡률비(궤적 총길이 ÷ 시작-끝 직선거리) 분포를 보니 실제 투구에서 나올 수 없는 값이었다.

```
곡률비  중앙값 6.79   최댓값 511
곡률비 > 5.0 : 152개 = 65.2%
```

실제 투구 궤적은 거의 직선이라 곡률비가 1.0~1.5다. 6.79는 공이 프레임마다 화면을 되짚어 다니고 있다는 뜻이다.

재현 조건
환경: macOS(Apple Silicon), 720p 59.94fps 중계 영상, `yolov8n.pt`(COCO 사전학습), 클래스 `sports ball`, 윈도우 t-3.0s ~ t-0.3s, 30fps 샘플링.
재현율: 항상. 233샘플 중 152개.

원인
표면 - 궤적 특징이 그룹별로 달라 보였다.
근본 - COCO 사전학습 YOLO의 `sports ball`은 야구 중계 화면에서 공이 아닌 둥근 물체(관중석 조명, 로고, 헬멧, 스코어보드 요소 등)를 자주 잡는다. 프레임마다 다른 물체를 최고 신뢰도로 고르면 궤적이 화면을 가로지르는 **랜덤워크**가 된다. 그 랜덤워크의 통계적 성질이 장면 구성(카메라 앵글, 배경)에 따라 달라지고, 장면 구성은 구종과 상관이 있다(브레이킹볼은 헛스윙·포수 미트 클로즈업이 잦다). 그래서 **구질이 아니라 장면이 그룹을 갈랐다**.
확인 방법 - 신뢰도 필터와 연속성 필터를 임계값별로 나눠 6개 투구에 실측 적용했다.

```
타임스탬프  원시  conf>=.25      jump40      jump60     jump100
   223.7   40점       40점  22점/곡률2.0  22점/곡률2.0  24점/곡률20.6
   246.5   45점       45점  24점/곡률8.8  29점/곡률3.4  29점/곡률3.4
   275.5   53점       53점  12점/곡률2.2  12점/곡률2.2  12점/곡률2.2
   290.3   30점       30점  11점/곡률1.9  11점/곡률1.9  12점/곡률2.2
   307.1   42점       42점  13점/곡률1.2  13점/곡률1.2  13점/곡률1.8
   327.6   27점       27점  15점/곡률1.3  15점/곡률1.3  15점/곡률1.3
```

시도했지만 안 된 것
- **신뢰도 임계값 필터(conf >= 0.25)**: 가장 먼저 떠오르는 대응이었으나 **한 점도 걸러내지 못했다**(40/40, 45/45, 53/53...). `detect_ball_in_frame`이 이미 0.15 하한으로 필터링해 반환하는데, 오탐들이 전부 0.25를 넘는 신뢰도로 검출되고 있었다. 즉 **YOLO는 오탐을 확신하고 있었고, 신뢰도에는 판별력이 전혀 없었다.** `MIN_BALL_CONF`는 0.15 그대로 두었다.
- **jump 임계값 100px**: 너무 관대해 223.7s에서 오탐 구간을 다시 받아들였다(곡률 2.0 → 20.6).
- **jump 임계값 40px**: 너무 빡빡해 246.5s의 실제 궤적을 중간에서 잘랐다(29점/곡률3.4 → 24점/곡률8.8).

해결
설계상 `yolo_detector.py`는 비범위이므로 파일럿 범위 안에서만 처리했다.
- `longest_smooth_run(trajectory, max_jump_px)`를 `trajectory_features.py`에 추가. 연속 프레임 간 이동거리가 임계값 이하인 **최장 구간만** 남긴다. 실제 공은 프레임 사이를 순간이동하지 않는다는 물리적 사실이 유일한 근거다.
- `MAX_JUMP_PX = 60.0` (720p·30fps 기준). 위 실측 표에서 40과 100 양쪽 실패를 피하는 값으로 선택했다.
- `extract_trajectory_points()`를 추가해 `(x, y, conf)` 원시 좌표를 반환하고, 파일럿 스크립트가 투구 단위로 JSONL에 append 저장한다. 임계값을 다시 조정할 때 영상 재처리(경기당 39분) 없이 캐시 위에서 재계산할 수 있다.

검증
유닛 테스트 41개 전부 통과(`longest_smooth_run` 4건 신규 — 연속 궤적 보존, 순간이동 시 짧은 쪽 폐기, 2점 미만 입력, 첫 구간이 아니라 최장 구간 선택).
전체 재추출(232샘플) 후 곡률비 분포:

```
             필터 전   필터 후
중앙값          6.79     2.18
5.0 초과       65.2%    13.8%
```

**그리고 가짜 분리가 사라졌다** — 이것이 이 항목의 핵심 결과다.

```
특징(중앙값)               BREAKING  FASTBALL  OFFSPEED
curvature_ratio                2.24      2.14      2.32
vertical_drop_px              -3.00      0.00      2.00
apparent_speed_px_per_frame    3.74      2.75      2.51
```

분류 성능도 같이 확인했다(1경기뿐이라 경기 단위 홀드아웃이 불가능해, 누수를 허용한 관대한 조건인 경기 내 5-fold CV로 상한만 측정).

```
최빈값 기준선(항상 BREAKING) : 0.496
RF 5-fold CV                : 0.517 +- 0.051
순열검정                     : p = 0.045
특징 중요도                  : 7개 전부 0.13~0.16 (평평)
```

추후 관리
재발 방지 - **모델 성능을 보기 전에 입력 데이터가 물리적으로 가능한 값인지 먼저 본다.** 곡률비 511은 어떤 투구에서도 나올 수 없는 값이었고, 그 한 줄만 봤어도 그룹별 차이표를 신호로 읽지 않았을 것이다.
남은 리스크 -
(1) 필터는 "매끄러운 최장 구간"을 남길 뿐, 그 구간이 **공**인지 **투구**인지는 보장하지 않는다. 매끄럽게 움직이는 다른 물체(주자, 배트, 팬)일 수 있다.
(2) 윈도우 t-3.0s ~ t-0.3s가 실제 투구 순간을 담는지 미검증이다. 설계 문서가 "첫 경기로 실측 보정 필요"라고 명시한 부분이고, 지금은 리플레이·관중석 컷을 잡고 있을 가능성이 열려 있다.
(3) OFFSPEED가 232개 중 14개(6%)뿐이라 이 그룹은 사실상 학습되지 않는다.
(4) 노트북 `01_pitch_group_classifier.ipynb`의 성공 기준이 "33% 랜덤 베이스라인 상회"인데, 클래스가 115/103/14로 불균형이라 **아무것도 배우지 않아도 49.6%가 나온다**. 이 기준을 그대로 두면 51.7%를 성공으로 오판한다. 기준을 최빈값 기준선으로 교체해야 한다.

배운 점
노이즈는 신호를 가리기만 하는 게 아니라 **가짜 신호를 만들어낸다**. 필터 전 그룹별 차이(곡률 7.09 vs 20.75)는 필터 후보다 훨씬 커 보였지만, 그건 구질 차이가 아니라 장면 차이였다. 데이터를 정리했더니 성능이 나빠 보이는 상황은 대개 성능이 나빠진 게 아니라 **원래 없던 성능이 드러난 것**이다.
그리고 가장 자연스러운 대응이 항상 효과적인 건 아니다 — 오탐에 대한 첫 반응은 신뢰도 임계값이었지만 판별력이 0이었다. YOLO는 틀린 물체를 자신 있게 잡는다. 실제로 통한 건 모델의 확신이 아니라 **물리적 제약(공은 순간이동하지 않는다)** 이었다.

후속 - 이 항목의 "곡률비 2.18로 개선" 결론은 **틀렸다**. 곡률비가 낮아진 이유는 궤적이 깨끗해져서가 아니라, 필터가 공 대신 매끄럽게 움직이는 투수 글러브를 골랐기 때문이다. TS-014 참고.

## TS-014 · YOLO가 공을 한 번도 잡은 적이 없었다 — 감지 713건 전부 글러브·선수 몸통

날짜: 2026-08-05
영역: ML
심각도: Critical
상태: 미해결

증상
TS-013의 연속성 필터로 곡률비가 정상 범위(중앙값 2.18)로 들어왔는데도 분류 성능이 기준선을 넘지 못했다.

```
최빈값 기준선(항상 BREAKING) : 0.496
RF 5-fold CV (누수 허용 상한): 0.517 +- 0.051
특징 중요도                   : 7개 전부 0.13~0.16 (평평)
그룹별 곡률비 중앙값          : BREAKING 2.24  FASTBALL 2.14  OFFSPEED 2.32
```

정확도가 낮은 것보다 **중요도가 평평한 것**이 이상했다. 신호가 약할 때는 특정 특징에 중요도가 몰리고 정확도만 낮다. 7개가 균등하다는 건 어느 특징에도 정보가 없다는 뜻이다.

재현 조건
환경: macOS(Apple Silicon), 720p 중계 영상(중계 기본 센터필드 와이드 앵글), `yolov8n.pt` COCO 사전학습, 클래스 `sports ball`.
재현율: 항상. 100%.

원인
표면 - 특징 공학이나 모델 선택 문제로 보였다.
근본 - **YOLO가 공을 단 한 번도 잡지 않았다.** COCO의 `sports ball`은 축구공·농구공·테니스공 크기의 물체로 학습됐다. 중계 와이드 앵글에서 야구공은 720p 기준 5~10px에 불과해 이 클래스의 학습 분포 밖이다. 대신 크기·형태가 유사한 **투수 글러브**를 높은 신뢰도로 잡았고, 글러브는 투구 동작 내내 화면에 있으며 매끄럽게 움직인다.
그 결과 TS-013의 `longest_smooth_run`이 상황을 **더 정교하게 악화**시켰다 — 공은 설령 잡혀도 궤적이 짧은데, 글러브는 82프레임 내내 연속적이다. "가장 매끄러운 최장 구간"을 고르는 규칙이 구조적으로 글러브를 선택한다. 곡률비 2.18은 투구 궤적이 아니라 **투수 팔 스윙의 곡률**이었다.
확인 방법 - 숫자를 더 보는 대신 프레임을 직접 렌더링해 감지 박스를 그렸다. 그다음 박스 크기를 정량화했다.

```
투구 15개 · 감지 713건
박스 최대변(px): 최소 23  25% 44  중앙값 49  75% 56  최대 202
12px 이하(실제 공 크기): 0건 = 0.0%
25px 초과(공일 수 없음): 711건 = 99.7%
```

신뢰도는 오히려 높았다 — 글러브 감지가 conf 0.94, 0.74, 0.70으로 나온다.

시도했지만 안 된 것
- **신뢰도 임계값**(TS-013): 판별력 0. 오탐이 정탐보다 신뢰도가 높다.
- **연속성 필터**(TS-013): 곡률 지표는 개선했으나 잡는 대상은 글러브로 고정시켰다. 지표가 좋아지는 것과 문제가 풀리는 것은 다르다.
- **경기 수 확대 검토**: 6경기(약 4시간) 추가 추출을 고려했으나, 착수 전 윈도우 검증을 먼저 한 덕에 헛수고를 피했다. 표본을 10배로 늘려도 글러브 궤적은 구종을 구분하지 않는다.
- **프로젝트 자체 학습 모델(`models/baseball_detector.pt`)로 교체**: 이 저장소에 이미 커스텀 학습된 야구공 탐지 모델이 있었고(`docs/ROADMAP.md`에 "완성된 것"으로 등재), 파일럿은 `load_model()`을 인자 없이 호출해 COCO로 폴백하고 있었다. 교체해봤더니 **더 나빴다**.

```
                감지된 프레임    박스 최대변 중앙값   12px 이하(실제 공)
COCO yolov8n     575/1230 (47%)        49px            0건
커스텀            41/1230 ( 3%)        73px (최대 636)  0건
```

  원인은 학습 데이터의 도메인이었다. `models/baseball_detector-2/val_batch0_pred.jpg`를 열어보니 학습셋이 **야구공 제품 사진·사인볼 수집품·리틀리그 스냅샷·공을 든 인물 사진**이었다. 중계 와이드 앵글에서 날아가는 5~10px 공은 한 장도 없다. 학습 지표는 좋았지만(precision 0.866 / recall 0.909 / mAP50 0.852, epoch 42) 그건 **그 데이터셋에서의 점수**다. 클래스명도 `{0: '0', 1: '1'}`로 의미가 없다.

해결
없음. 근본 원인이 파일럿 설계의 전제("사전학습 YOLO로 중계 화면의 야구공을 추적할 수 있다")에 있어, 이 파일럿 범위 안에서는 고칠 수 없다. COCO든 자체 학습 모델이든 **중계 앵글의 소형 공으로 학습된 적이 없다**는 점에서 동일하다.

검증
윈도우 자체는 정상이었다 — 컨텍스트 시트(t-6s ~ t+2s)에서 t-3s에 투수 와인드업, t-2s경 릴리스, t+0s에 결과 장면으로, `t-3.0s ~ t-0.3s` 윈도우는 실제 투구 순간을 정확히 담고 있었다. **윈도우가 아니라 감지기가 문제였다.**

추후 관리
재발 방지 - **모델 성능을 의심하기 전에 입력을 눈으로 본다.** 감지 박스를 프레임에 그려보는 데 10분이 걸렸고, 그 10분이 앞선 몇 시간의 특징 튜닝·필터 설계를 모두 대체했다. 곡률비·정확도·중요도 어느 지표도 "글러브를 보고 있다"를 말해주지 못했지만 이미지 한 장이 즉시 말해줬다.
남은 리스크 / 선택지 -
(1) **중계 도메인 프레임으로 재학습.** ROADMAP이 이미 목표로 삼은 방향이고, 빠진 것은 모델이 아니라 데이터의 도메인이다. 학습셋 재료는 이미 있다 — 720p 경기 영상, OCR 타임스탬프 237개, 검증된 윈도우. 라벨링 비용이 관건.
(2) 감지 대신 프레임 차분·광류 기반 소형 고속 물체 추적. 사전학습 모델 불필요하나 중계 컷 전환에 취약.
(3) 궤적을 포기하고 자세 추정 기반 특징으로 선회. 단, `src/pose_detector.py`는 이름과 달리 실제로는 프레임 차분 모션 감지다(ROADMAP 27행에 기록됨) — 실제 포즈 추정을 하려면 별도 구현이 필요하다.
(4) 파일럿을 음성 결과로 종료.
TS-013에서 만든 궤적 JSONL 캐시와 `longest_smooth_run`은 감지기를 교체해도 그대로 재사용할 수 있다. `detect_ball_in_frame`은 이미 `CONF_THRESHOLD = 0.15`, `BALL_CLASS_NAMES = None`으로 커스텀 모델을 받도록 준비돼 있어, 감지기 교체 시 호출부에 경로만 넘기면 된다.

배운 점
**지표가 좋아지는 것과 문제가 풀리는 것은 다르다.** 곡률비를 6.79에서 2.18로 낮췄고 그건 진짜 개선처럼 보였지만, 실제로 한 일은 "엉뚱한 물체를 더 일관되게 추적하기"였다. 지표는 자기가 무엇을 측정하는지 모른다.
그리고 **파이프라인의 가장 밑단 가정을 가장 먼저 검증해야 한다.** "YOLO가 공을 잡는다"는 이 프로젝트 전체가 딛고 선 전제였는데, 아무도 확인하지 않은 채 그 위에 특징 공학·필터·분류기·평가를 쌓았다. 전제가 틀리면 그 위 모든 층의 작업은 정교할수록 낭비다.
**학습 지표는 학습 도메인 안에서만 유효하다.** 자체 학습 모델의 mAP50 0.852는 진짜 점수였지만, 그 검증셋은 사인볼 클로즈업과 리틀리그 사진이었다. 배포 도메인(중계 와이드 앵글)에서는 감지율 3%다. 지표를 볼 때 "몇 점인가"보다 "무엇에 대해 몇 점인가"를 먼저 물어야 한다 — 이번에는 `val_batch0_pred.jpg` 한 장이 results.csv 43줄보다 많은 것을 말해줬다.
마지막으로, **가진 자산을 먼저 확인한다.** 커스텀 탐지 모델이 저장소에 있었고 ROADMAP에 "완성"으로 적혀 있었는데, 파일럿은 `load_model()`을 인자 없이 호출해 COCO로 폴백하고 있었다. 결과적으로 그 모델도 답은 아니었지만, 그걸 확인하는 데 5분이면 됐을 일을 며칠 뒤에야 했다.

## TS-015 · 감지점 중심 크롭이 움직임을 지워, 정상 추적을 "정지 물체 오탐"으로 오판

날짜: 2026-08-06
영역: ML
심각도: High
상태: 해결됨

증상
TS-014의 처방대로 Roboflow 중계 도메인 데이터셋으로 파인튜닝한 뒤, `scripts/verify_ball_detector.py`로 실제 경기 영상에 감지 박스를 렌더링해 확인했다. 컨택트 시트를 보니 세 투구 모두 심판 가슴·포수 어깨 부근의 흰 둥근 물체에 박스가 걸려 있었고, 프레임이 f45→f53으로 바뀌어도 배경과 물체 위치가 거의 그대로였다. "또 정지 물체를 잡고 있다, TS-014의 재현"으로 판단했다.

재현 조건
환경: macOS(Apple Silicon), 720p 중계 영상, `runs/detect/runs/ball_broadcast/weights/best.pt`(에폭 2 체크포인트).
재현율: 항상. 크롭 방식을 쓰는 한 100%.

원인
표면 - 감지기가 정지 물체를 잡는 것으로 보였다.
근본 - **컨택트 시트가 감지점을 중심으로 크롭하고 있었다.** `make_tile()`이 매 프레임 감지 좌표 주변 160x160을 잘라내므로, 공이 화면을 가로질러도 타일 안에서는 **항상 정중앙에 온다.** 대상이 움직이든 정지해 있든 렌더 결과가 동일해진다. 즉 이 시각화는 "무엇을 잡았는가"는 보여주지만 "그것이 움직이는가"는 원리적으로 보여줄 수 없다.
부차 원인 - 타일 선택을 `sorted(key=-conf)[:6]`으로 했다. 신뢰도 상위 6개는 시간적으로 몰리는 경향이 있어 배경이 서로 비슷했고, "정지해 있다"는 인상을 강화했다.

확인 방법 - 이미지를 더 보는 대신 원좌표를 프레임별로 찍었다.

```
=== 투구 #209 t=6861.86s  Sinker ===
frame  t_rel     cx    cy   size  conf
   53  -1.23s   750  287   27  0.39
   54  -1.20s   736  286   27  0.33
   56  -1.13s   713  283   23  0.28
   57  -1.10s   703  285   26  0.55
   58  -1.07s   696  288   25  0.78
   59  -1.03s   690  294   19  0.59
   60  -1.00s   687  300   24  0.58
   61  -0.97s   683  311   22  0.51
   62  -0.93s   680  319   22  0.38
   63  -0.90s   680  331   22  0.32

=== 투구 #158 t=4939.43s  Fastball ===
   45  -1.50s   734  270   27  0.70
   48  -1.40s   719  258   23  0.42
   49  -1.37s   713  257   22  0.56
   50  -1.33s   709  256   21  0.59
   51  -1.30s   706  257   21  0.88
   52  -1.27s   704  258   22  0.74
   53  -1.23s   703  258   22  0.56
```

판단이 정반대로 뒤집혔다. 싱커는 x가 750→680으로 이동하다 멈추는 동안 y가 287→331로 **낙차가 가속**하고, 패스트볼은 x 734→703 이동에 y가 270→258로 **거의 평평**하다. 정지 물체가 아니라 구종별로 형태가 다른 실제 투구 궤적이다.

시도했지만 안 된 것
- **컨택트 시트를 더 많이 열어보기**: 투구 3개를 봤지만 전부 같은 인상을 줬다. 표본을 늘려도 시각화 자체가 움직임을 지우므로 몇 장을 보든 결론이 같다. 잘못된 렌더링은 반복 관찰로 교정되지 않는다.

해결
원좌표(`cx`, `cy`)를 프레임 인덱스와 함께 표로 출력해 판단했다. 크롭 타일은 "박스 안의 것이 공인가"(정체 확인)에만 쓰고, "움직이는가"(궤적 확인)는 좌표로 본다 — 두 질문에 서로 다른 도구가 필요하다.

검증
두 투구의 좌표열이 물리적으로 타당했다: 프레임 간 이동량이 연속적이고(순간이동 없음), 릴리스에서 플레이트 방향으로 단조 이동하며, 수직 낙차가 시간에 대해 가속한다. 구종 라벨(Sinker/Fastball)과 궤적 형태가 일치했다.

추후 관리
재발 방지 - **시각화가 답해줄 수 있는 질문의 범위를 먼저 정한다.** 정규화·정렬·중심맞춤이 들어간 그림은 그 축의 정보를 지운다. 감지점 중심 크롭은 위치를, 프레임 정규화는 밝기를, 궤적 정렬은 시작점을 지운다.
남은 리스크 - 투구 #158의 f42~f47에 `(640,307)` 부근 고정 좌표 오탐이 공과 동시에 잡히고 있다(`n_det=2`). 현재 추출 로직이 프레임마다 `max(conf)`를 고르므로 가끔 이 오탐을 선택한다. TS-013의 `longest_smooth_run`은 이걸 못 거른다 — 정지 물체도 "매끄럽다"는 조건을 만족하기 때문이다. 학습 완주 후에도 남으면 **직전 프레임 위치와의 연속성**으로 후보를 고르는 방식으로 바꿔야 한다.

배운 점
**틀린 결론을 만든 것은 감지기가 아니라 내 시각화였다.** TS-014의 교훈은 "숫자 말고 이미지를 봐라"였고 그건 옳았지만, 이번엔 그 이미지가 거짓말을 했다. 시각화도 코드이고, 코드처럼 검증 대상이다.
**"정지해 보인다"는 관찰은 좌표 없이는 주장이 될 수 없다.** 나는 배경이 비슷하다는 인상만으로 정지를 결론냈다. 실제로는 크롭 창이 대상을 따라다녔기 때문에 배경이 비슷했던 것이고, 이건 오히려 대상이 **움직이고 있다**는 증거였다.

원인
표면 - 학습이 실패한 것처럼 보였다.
근본 - **크래시가 아니다.** 로그에 트레이스백·에러·OOM 메시지가 전혀 없고, 마지막 줄이 정상 진행 상황(`3/50 ... 127/214 2.2s/it`)에서 그대로 끊겼다. 두 백그라운드 작업이 **동시에** 죽은 점으로 보아 개별 프로세스 실패가 아니라 하네스 수준의 백그라운드 작업 정리로 판단했다. 두 작업 모두 하네스가 추적·관리하는 대상이었다.
확인하지 않은 것 - 정확히 어떤 시그널로 종료됐는지는 확인하지 못했다. 종료 코드나 시그널 로그가 남지 않았다.

시도했지만 안 된 것
- **`nohup setsid ... &`**: macOS에는 `setsid` 바이너리가 없다. `nohup: setsid: No such file or directory`로 즉시 실패했고, 프로세스가 아예 뜨지 않았다. Linux 기준 관용구를 그대로 옮긴 실수다.

해결
Python 안에서 `os.setsid()`를 호출해 프로세스 그룹을 분리하고, 하네스가 추적하지 않는 방식으로 띄웠다.

```bash
nohup venv/bin/python3 -c "
import os
os.setsid()
from ultralytics import YOLO
YOLO('runs/detect/runs/ball_broadcast/weights/last.pt').train(resume=True)
" > train2.log 2>&1 < /dev/null & disown
```

에폭마다 체크포인트가 저장돼 있어 `resume=True`로 에폭 3부터 이어서 돌렸다. 처음부터 다시 학습하지 않았다.

검증
재개 후 로그에 `3/50 ... 1/214`부터 정상 진행이 찍히고, `ps aux | grep "[t]rain(resume"`로 프로세스 1개가 살아있음을 확인했다.

추후 관리
재발 방지 - **긴 학습은 하네스가 관리하는 백그라운드 작업으로 띄우지 않는다.** 프로세스 그룹을 분리하고, 진행 상황은 파일(`results.csv`)을 폴링해서 읽는다.
남은 리스크 - macOS에는 `setsid`가 없다. 셸 관용구를 옮길 때 플랫폼을 먼저 확인해야 한다 (`coreutils` 설치 시 `gsetsid`로 존재).

재발 사례 (2026-08-06, 같은 원인)
클립 데이터셋 빌드(`scripts/build_pitch_group_clips_dataset.py`, 1193투구·약 100분)를 하네스 백그라운드로 띄웠다가 같은 방식으로 정리됐다. 로그에 에러 없이 끊겼고 상태가 `killed`로 보고됐다. 위 재발 방지 항목을 학습에만 적용하고 **데이터 처리에는 적용하지 않은 것이 원인**이다 — 기준은 "학습이냐"가 아니라 "하네스 작업 수명보다 오래 걸리냐"다.

손실은 없었다. 감지 후보를 투구 1건마다 JSONL에 append하도록 만들어 둔 덕에 672투구분이 남아 있었고, 재기동 시 캐시 적중으로 건너뛰었다. 재기동은 `runpy`로 CLI를 그대로 실행하되 `os.setsid()`를 먼저 호출하는 형태를 썼다 — `exec(open(...).read())`는 `__file__`이 정의되지 않아 스크립트의 `ROOT` 계산이 깨진다.

```bash
nohup venv/bin/python3 -c "
import os, runpy
os.setsid()
runpy.run_path('scripts/build_pitch_group_clips_dataset.py', run_name='__main__')
" > output/pitch_type_cv/build_clips.log 2>&1 < /dev/null & disown
```

배운 점
**"죽었다"와 "실패했다"는 다르다.** 트레이스백이 없다는 사실 자체가 진단 정보다. 원인을 코드에서 찾기 전에 로그의 마지막 줄이 정상이었는지, 다른 프로세스도 같이 죽었는지를 먼저 봐야 한다.
**긴 작업은 중간 산출물이 있으면 사고가 사고로 끝난다.** Ultralytics가 에폭마다 `last.pt`를 남긴 덕에 21분치를 그대로 살렸고, 그 체크포인트로 계획보다 일찍 실전 검증까지 돌려 TS-015를 앞당겨 발견했다.

## TS-017 · 물리적으로 통과 불가능한 게이트를 세웠고, 고치니 정지 오탐이 그 게이트를 통과했다

날짜: 2026-08-06
영역: ML
심각도: High
상태: 부분 해결

증상
Roboflow 중계 도메인 데이터셋으로 파인튜닝한 감지기가 통과 기준을 계속 못 넘었다. 학습 지표는 크게 좋아지는데 실전 감지율만 제자리였다.

```
              mAP50      실전 감지율   박스 최대변 중앙값
에폭 2        0.502        16.5%           26px
에폭 15       0.912        18.3%           24px
```

mAP50이 82% 뛰는 동안 감지율은 11% 올랐다. TS-014("학습 지표는 학습 도메인 안에서만 유효하다")와 같은 형태로 보였다.

재현 조건
환경: macOS(Apple Silicon), 720p 중계 영상, 궤적 윈도우 `t-3.0s ~ t-0.3s`(2.7초, 30fps 샘플링 시 82프레임).
재현율: 항상.

원인 (1) — 게이트의 분모가 틀렸다
표면 - 감지기 성능이 부족해 보였다.
근본 - **"윈도우 프레임 대비 감지율 30%"는 물리적으로 달성 불가능한 기준이었다.** 윈도우는 2.7초인데 공이 실제로 날아가는 시간은 0.45초뿐이다(90mph로 18.44m). 30fps에서 약 14프레임, **윈도우의 17%**다. 나머지 83%는 와인드업과 포구 후 장면이라 날아가는 공이 애초에 화면에 없다. 완벽한 감지기도 이 지표로는 17%가 상한이고, 실측 18.3%는 이미 그 근처였다.
확인 방법 - 감지가 **언제** 일어나는지 프레임 인덱스와 함께 봤다. 감지가 윈도우 전체에 흩어진 게 아니라 t-1.5s ~ t-0.9s 구간에 몰려 있었고, 그 구간 길이가 공의 비행 시간과 일치했다.

원인 (2) — 고친 지표를 정지 오탐이 통과했다
분모를 궤적 품질로 바꾸자(연속 이동 사슬 길이) 7/8투구가 통과했다. 그런데 궤적 좌표를 보니 절반이 가짜였다.

```
투구 #135 Slider — 원시 후보
  f 29~f 44 : (405,453) 부근 16프레임 연속, conf 0.25~0.41   <- 화면 고정 오탐
  f 45      : (432,345|0.57)  (405,453|0.26)                 <- 공과 오탐이 동시에
  f 46      : (455,332|0.67)                                  <- 진짜 공
```

근본 - **정지 오탐은 궤적 필터를 구조적으로 통과한다.** TS-013의 `longest_smooth_run`은 "연속 프레임 간 이동이 작은 최장 구간"을 고르는데, 정지 물체는 이 조건을 **완벽하게** 만족한다. 게다가 신뢰도도 실제 공보다 높은 경우가 있어(0.71 vs 0.45) 프레임별 `max(conf)` 선택이 공을 버리고 오탐을 집는다. TS-013에서 글러브가 이긴 것과 완전히 같은 구조다.
추가로 - 감지 누락을 잇기 위한 `max_gap_frames=2` 관용 때문에, 정지 오탐이 110px 점프로 공에 이어붙었다. 사슬 **전체** 변위가 크므로 "실제로 이동하는가" 조건도 통과해버렸다.

시도했지만 안 된 것
- **`longest_smooth_run` 재사용**: TS-013 자산을 그대로 쓰려 했으나 정지 물체에 무력하다. 매끄러움은 운동성을 함의하지 않는다.
- **신뢰도 임계값 상향**: TS-013에서 이미 판별력 0으로 확인됐고, 이번에도 오탐 conf가 공보다 높은 프레임이 있어 같은 결론이다.
- **정지 구간 트림의 첫 구현**: 이동량이 작은 앞뒤 구간을 잘라내되 **경계점을 남겼더니** 효과가 없었다. 정지 구간의 마지막 점이 남고, 거기서 다음 점으로의 "큰 이동"이 운동으로 잡혀 사슬이 그대로 통과했다. 경계점 자체가 정지 물체의 좌표이므로 함께 버려야 한다.

해결
`longest_moving_chain()`을 새로 만들었다 (`src/pitch_type_cv/trajectory_features.py`). 세 조건을 함께 건다.

1. **연속성** — 프레임 간 이동 ≤ `max_jump_px`(60), 간격만큼 비례 확대
2. **운동성** — 사슬 전체 변위 ≥ `min_total_move_px`(30). 정지 사슬은 길어도 탈락
3. **앞뒤 정지 구간 트림** — 프레임당 이동 < `min_step_px`(3.0)인 앞뒤 구간 제거, **경계점 포함**

프레임별 최고 신뢰도가 아니라 후보 전체를 받도록 `extract_trajectory_candidates()`도 추가했다. 정지 오탐과 공이 같은 프레임에 있을 때 신뢰도로 고르면 공을 잃기 때문이다.

검증
합성 케이스 6개로 단위 테스트를 먼저 작성해 RED 확인 후 구현했다 (정지 오탐 배제 / 전부 정지면 빈 결과 / 1프레임 누락 브리지 / 긴 정지보다 짧은 이동 선호 / 점프로 붙은 정지 머리 트림 / 미트 정지 꼬리 트림). 기존 41개 포함 **47개 전부 통과**.

실측 대조로 트림이 과잉이 아님을 확인했다. 트림 후 0프레임이 된 두 투구의 원시 후보를 직접 열어보니, 정말로 공 궤적이 없었다.

```
#135 : 정지 오탐 16프레임 + 공 2프레임(변위 26px < 30px)  -> 궤적 없음이 맞다
#217 : (663,314) 부근 4프레임 3px 이동 + 흩어진 단발       -> 비행 궤적 자체가 없다
```

트림 전 7/8 통과는 **가짜였고**, 실제는 5/8(62%)이다. 기준 75% 미달.

추후 관리
재발 방지 - **통과 기준을 세울 때 그 지표의 물리적 상한을 먼저 계산한다.** "30%"는 그럴듯해 보였지만 상한이 17%인 지표였다. 달성 불가능한 기준은 모델을 아무리 개선해도 실패로만 보이게 만들고, 실제 진전을 감춘다.
남은 리스크 -
(1) 현재 5/8(62%)로 기준 미달. 학습이 아직 진행 중(에폭 17/50)이라 최종 판정은 완주 후다.
(2) 궤적이 잡히는 투구와 안 잡히는 투구가 무작위가 아닐 수 있다. 감지가 되는 투구만으로 데이터셋을 만들면 **선택 편향**이 생긴다 — 예컨대 배경이 어두운 구장, 특정 카메라 앵글에서만 잡힌다면 그 조건이 구종과 상관될 수 있다. Phase 4 결과 해석 시 반드시 확인해야 한다.
(3) 정지 오탐의 정체를 아직 모른다. `(405,453)`, `(663,314)`, `(601,181)` 등 투구마다 다른 위치라 화면 고정 그래픽은 아니다. 경기장 내 흰 둥근 물체로 추정되나 확인하지 않았다.

배운 점
**기준을 세우는 것과 옳은 기준을 세우는 것은 다르다.** "사후 조정 금지"를 스스로 못 박았는데, 정작 그 기준이 물리적으로 불가능했다. 규율은 지켰지만 규율이 지킬 가치가 있는지는 검증하지 않았다. 기준을 정할 때 "이 지표의 최댓값은 얼마인가"를 먼저 물었어야 했다.
**같은 실패가 형태를 바꿔 세 번 반복됐다.** TS-013은 글러브, TS-014도 글러브, TS-017은 정지 오탐이다. 전부 "매끄럽고 오래 지속되는 엉뚱한 물체가 짧고 끊기는 진짜 공을 이긴다"는 하나의 구조다. 필터를 고칠 때마다 그 구조를 다시 만족하는 다른 물체가 등장했다. 증상이 아니라 구조를 봤어야 했다 — 필요한 조건은 "매끄러움"이 아니라 **"움직임"**이었다.
**필터를 강화하면 통과율이 떨어지는 게 정상이다.** 7/8 → 5/8은 후퇴가 아니라 앞의 7/8이 거짓이었다는 뜻이다. 지표가 나빠지는 방향의 변경을 받아들일 수 있어야 실제 상태를 볼 수 있다.

## TS-018 · CONF_THRESHOLD = 0.15가 한 번도 작동한 적이 없었다

날짜: 2026-08-06
영역: ML
심각도: Critical
상태: 해결됨

증상
파인튜닝이 진행될수록 검증 지표는 오르는데 실전 감지가 **줄었다**. 에폭 30이 에폭 18보다 나빴다.

```
              mAP50    recall    실전 게이트   #53 원시감지  #144   #217
에폭 18       0.935     0.869     5/8 (62%)        10          20     12
에폭 30       0.955     0.929     4/8 (50%)         1           1      1
```

검증셋 recall이 0.869에서 0.929로 올랐는데 우리 영상에서는 감지가 1건으로 붕괴했다. 도메인 갭이 벌어지는 것으로 보였다.

재현 조건
환경: macOS(Apple Silicon), 720p 중계 영상, `yolo_detector.detect_ball_in_frame`.
재현율: 항상. 100%.

원인
표면 - 학습이 진행되며 우리 도메인에 과적합 반대 방향으로 드리프트한 것으로 보였다.
근본 - **`CONF_THRESHOLD = 0.15`가 실행되지 않는 코드였다.** `detect_ball_in_frame`은 이렇게 되어 있었다.

```python
results = model(frame, verbose=False, imgsz=imgsz)[0]
for box in results.boxes:
    conf = float(box.conf[0])
    if conf < CONF_THRESHOLD:   # 0.15
        continue
```

Ultralytics `model()`의 기본 `conf`는 **0.25**다. 모델이 이미 0.25에서 잘라낸 결과를 받아 0.15로 다시 거르고 있었으니, 이 조건은 단 한 번도 참이 된 적이 없다. TS-013에서 "방송 화면 소형 야구공 감지용(기본 0.3은 너무 높음)"이라며 0.15로 낮춘 것도 효과가 없었다.

확인 방법 - 임계값을 0.15 → 0.08 → 0.04 → 0.02로 낮추며 감지 수를 셌다.

```
=== #53 — 임계값별 감지/사슬 ===
  conf>=0.15 : 원시    1  사슬  0프레임
  conf>=0.08 : 원시    1  사슬  0프레임
  conf>=0.04 : 원시    1  사슬  0프레임
  conf>=0.02 : 원시    1  사슬  0프레임
```

**임계값을 8분의 1로 낮췄는데 결과가 한 건도 안 변한다.** 이건 모델 특성이 아니라 그 코드가 실행되지 않는다는 뜻이다. 지금까지 관측된 최저 신뢰도가 정확히 0.25였던 것과도 일치한다. 모델에 `conf`를 직접 넘기자 결과가 즉시 달라졌다.

```
=== #53 — model(conf=...) 직접 지정 ===
  conf=0.25 : 원시    1  사슬  0프레임
  conf=0.10 : 원시    3  사슬  0프레임
  conf=0.05 : 원시   15  사슬  3프레임
```

시도했지만 안 된 것
- **임계값 스윕**(첫 시도): 위 표대로 0.02까지 내려도 무변화. 이때 "모델이 정말 공을 못 본다"로 결론냈다면 파일럿을 잘못 종료했을 것이다.
- **윈도우 확장**: 투구가 윈도우 밖에 있나 싶어 `t-3.0s`를 `t-5.0s`, `t-6.0s`로 넓혔다. #144는 원시 감지가 **11건으로 완전히 동일**했다. 윈도우 문제가 아니었다.

해결
`detect_ball_in_frame`에 `conf: float | None = None`을 추가해 모델에 직접 넘긴다. 기본값 `None`이면 인자를 아예 넘기지 않아 기존 데모 경로 동작이 그대로 보존된다.

```python
results = model(frame, verbose=False, imgsz=imgsz, **kwargs)[0]
```

`src/yolo_detector.py`는 설계 문서상 수정 비범위였으나, 우회하려면 감지 로직을 복제해야 해서 동작 불변인 선택적 인자만 추가했다.

추후 관리
재발 방지 - **임계값을 바꿨는데 결과가 안 변하면 그 코드는 실행되지 않는 것이다.** 파라미터 튜닝 전에 그 파라미터가 실제로 영향을 주는지부터 확인한다. 스윕은 튜닝 도구이자 배선 검사 도구다.

배운 점

## TS-019 · 정지 오탐이 사슬 한가운데로 들어왔다 — 같은 구조의 네 번째 재발

날짜: 2026-08-06
영역: ML
심각도: High
상태: 해결됨

증상
TS-017에서 만든 `longest_moving_chain`이 게이트를 7/8로 통과시켰는데, 궤적 좌표를 열어보니 절반이 오염돼 있었다.

```
투구 #53 — 이동사슬 12프레임 (통과로 집계됨)
  f44 (720,357)  f46 (742,292)  f47 (738,276)   <- 진짜 공
  f48 (721,356)  f49 (721,356)  f50 (721,356)   <- 정지 오탐
  f51 (721,356)  f52 (722,356)
  f54 (706,246)  f55 (700,254)  f56 (694,263)   <- 다시 진짜 공
  f57 (687,276)  f59 (674,306)
```

재현 조건
환경: macOS(Apple Silicon), 720p 중계 영상, imgsz 960 / conf 0.05.
재현율: 항상.

원인
표면 - 사슬 필터가 정지 오탐을 못 걸렀다.
근본 - **TS-017의 트림이 사슬의 앞뒤만 보고 있었다.** `max_gap_frames=2` 관용 때문에 f47(공)에서 f49(정지 오탐)로 건너뛸 수 있고 — 두 점 사이 거리 81.8px은 gap 2에서 허용치 120px 이내다 — 정지 구간이 사슬 **한가운데** 박힌다. 앞뒤 트림은 원리적으로 여기 닿지 않는다.

부차 문제 - `chain_members`가 좌표만으로 매칭해, 사슬에 정지 좌표가 한 번 들어가면 그 좌표를 가진 **모든 프레임**이 출력·렌더링에 포함됐다. 실제 사슬보다 표가 길게 보였다.

시도했지만 안 된 것 (두 번 실패했다)
- **간선 최소 이동량 조건**: 정지 감지끼리 간선을 못 만들게 했다. 정지 구간이 길게 이어지는 건 막았지만, 정지 감지 **하나**가 큰 점프로 사슬 끝에 붙는 건 그대로였다. 그 점프는 이동량이 커서 조건을 통과한다.
- **속도 이상치 트림**: 끝점의 프레임당 속도가 주변 중앙값의 3배를 넘으면 자르게 했다. #53(55.8 vs 10대, 비율 5.5)은 잡혔지만 #135(55.8 vs 26.65, 비율 2.09)는 임계 미만이라 그대로 통과했다. 비율을 낮추면 정상적으로 가속하는 공의 끝부분이 잘려나간다.

  이 과정에서 별개 버그도 하나 찾았다. 이상치를 **원 이동거리**로 비교하니 감지가 한 프레임 빠진 구간(gap 2)의 스텝이 2배로 나와, 정상 가속 구간이 이상치로 잘렸다. 프레임당 속도로 정규화해 고쳤다.

해결
사후 필터링을 포기하고 **사슬을 만들기 전에** 정지 후보를 제거했다.

```python
def _drop_static_nodes(nodes, radius_px=3.0, min_repeats=3):
    """여러 프레임에서 사실상 같은 좌표에 나타나는 감지를 버린다."""
```

이게 정지 오탐의 정의다. 90mph 공은 30fps에서 포구 직전까지도 프레임당 3px 이상 움직이므로, 3픽셀 반경 안에 서로 다른 프레임의 감지가 3개 이상 모이면 공이 아니다. 사슬 구성 전에 빼면 앞·중간·뒤·전체 네 경우가 한 번에 사라진다.

간선 최소 이동량 조건과 앞뒤 트림은 다중 방어로 남겨뒀다 — 2회만 감지된 정지 물체는 사전 필터에 안 걸린다.

검증
합성 케이스 7개로 단위 테스트를 먼저 작성해 RED 확인 후 구현했다. 기존 41개 포함 **48개 전부 통과**.
실측 재검증에서 #53의 사슬이 12 → 9프레임으로 줄었다 (가짜 3프레임 제거). 게이트는 7/8(88%) 유지, 사슬 중앙값 7.0프레임, 박스 최대변 중앙값 21px.

추후 관리
재발 방지 - **거르려는 대상을 정의로 붙잡는다.** "정지 물체 = 여러 프레임에서 같은 좌표"는 정의이고, 그걸 직접 검사하면 발현 형태와 무관하게 잡힌다. "매끄러운 최장 구간"이나 "전체 변위"는 정의가 아니라 증상의 대리 지표였고, 그래서 매번 다른 형태로 빠져나갔다.
남은 리스크 - 2회 이하로만 감지되는 정지 물체는 사전 필터를 통과한다. 실측에서 문제되지 않았지만 다른 경기 영상에서는 확인이 필요하다.

배운 점
**같은 구조가 네 번 반복됐다.** TS-013(글러브) · TS-014(글러브) · TS-017(정지 오탐, 앞뒤) · TS-019(정지 오탐, 중간). 전부 "매끄럽고 오래 지속되는 엉뚱한 물체가, 짧고 끊기는 진짜 공을 이긴다"는 하나의 구조다. 필터를 고칠 때마다 그 구조를 다시 만족하는 형태가 등장했다.
**증상을 막는 필터는 증상만큼 필요하다.** 앞을 막으면 중간으로, 중간을 막으면 끝으로 온다. 세 번째 패치를 짜고 있다면 대상을 잘못 정의한 것이다. 네 번째에 와서야 정의로 돌아갔고, 그러자 한 함수로 끝났다.
**게이트 통과가 검증의 끝이 아니다.** 7/8 통과 후 좌표를 안 열어봤다면 오염된 궤적으로 Phase 4를 돌렸을 것이다. 통과했을 때야말로 결과를 의심해야 한다 — 실패는 알아서 눈에 띄지만 성공은 그렇지 않다.

## TS-021 · "사슬 확보율 93.3%"가 타구 비행까지 세고 있었다

투구별 클립에서 릴리스 위치를 찾기 위해 클립 앞 12초를 전부 스캔하고, 프레임별 감지 후보에서 `longest_moving_chain`으로 사슬을 뽑아 시작 시각 분포를 쟀다. 결과는 좋아 보였다.

근본 - **확보율이 "투구 사슬을 찾았는가"가 아니라 "움직이는 사슬이 하나라도 있는가"를 재고 있었다.** 타구는 공이고 움직이므로 `longest_moving_chain`의 두 조건(연속성·운동성)을 완벽히 만족한다. 안타가 나온 클립에서는 타구 비행 구간이 투구 구간보다 길어 최장 사슬로 선택된다. 지표 이름은 "사슬 확보율"이었고 실제로 그걸 정확히 쟀지만, 알고 싶었던 건 "투구 궤적 확보율"이었다.

시도했지만 안 된 것
- **가설: 윈도우를 좁히면 타구 후보가 배제되므로 확보율이 오른다.** 틀렸다. 같은 60클립을 2.8~4.2초로 재스캔하니 93.3% → **90.0%**로 내려갔다. 좁힌 윈도우에서는 타구가 후보에서 빠지는 동시에, 원래 타구로 집계되던 클립 중 일부는 투구 사슬도 3점을 못 채워 탈락했다. 즉 93.3%는 오르내릴 수치가 아니라 **처음부터 다른 것을 세고 있던 수치**였고, 90.0%가 실제 값이다.

해결
스캔 윈도우를 클립 시작 기준 2.8~4.2초로 고정했다. 근거는 같은 실측의 다른 통계다 — 사슬 시작 시각의 5퍼센타일이 전 그룹 2.92초로 하한이 날카롭다(프리롤 고정). 그룹별 중앙값도 3.03/3.22/3.24초로 0.21초 안에 모여 구종별 위상 차이가 없다.

2.5~4.5초와 확보율이 54/60으로 동일하고, 사슬 점수 중앙값은 좁은 쪽이 낫고(OFFSPEED 10 대 8), 감지 프레임이 30% 적다.

검증
같은 60클립을 두 윈도우로 재스캔해 그룹별 확보율과 사슬 점수를 대조했다. 최종값 FASTBALL 85% / BREAKING 90% / OFFSPEED 95%, 전체 90.0%.
비교 기준: OCR 경로의 전체 확보율은 68%였다.

추후 관리
재발 방지 - 확보율 같은 비율 지표는 **분자와 분모가 각각 무엇을 세는지** 적어두고, 분자가 원하는 대상만 세는지 별도로 확인한다. 이번에는 "범위 상단 8.13초"라는 물리적으로 불가능한 값이 단서였다 — 요약 통계에 중앙값만 찍었다면 못 봤다.
남은 리스크 - 2.8~4.2초 밖에 릴리스가 오는 클립은 통째로 놓친다. 실측 60개에서는 하한 2.92초로 여유가 있었으나, 다른 시즌·다른 중계사 클립은 프리롤이 다를 수 있어 경기를 추가할 때 재확인이 필요하다.

배운 점
**지표가 통과했다고 측정이 맞은 게 아니다.** TS-017에서 게이트 기준의 분모를 잘못 잡았고, TS-019에서 게이트를 통과한 사슬이 오염돼 있었다. 이번엔 게이트도 사슬도 정상인데 **지표가 다른 대상을 셌다.** 셋 다 "숫자가 좋아 보였다"에서 출발한다.
**분포의 꼬리를 본 게 유일한 단서였다.** 중앙값 3.03초만 보면 완벽한 결과다. 범위를 같이 찍었기 때문에 8.13초가 눈에 들어왔다.
**가설이 틀렸을 때 수치가 왜 움직였는지까지 설명해야 한다.** "좁히면 오른다"가 틀렸을 때 90.0%를 그냥 채택했다면, 3.3%p 하락을 손실로 오해했을 것이다. 실제로는 잘못 세던 것을 빼낸 것이다.

## TS-022 · venv의 urllib만 SSL 인증서 검증에 실패 — curl과 requests는 정상

날짜: 2026-08-06
영역: Build
심각도: Low
상태: 해결됨

증상
MLB StatsAPI 생존 확인 스크립트가 첫 요청에서 죽었다.

```
  File ".../urllib/request.py", line 1322, in do_open
    raise URLError(err)
urllib.error.URLError: <urlopen error [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed:
unable to get local issuer certificate (_ssl.c:1032)>
```

에러만 보면 네트워크 차단이나 방화벽을 의심하게 된다. 실제로는 같은 URL이 다른 도구로는 정상이었다.

```
$ curl -s -o /dev/null -w "%{http_code}\n" "https://statsapi.mlb.com/api/v1.1/game/775294/feed/live"
200
$ venv/bin/python3 -c "import certifi, requests; print(certifi.where())"
/Users/tina/Project/baseball-pitch-predictor/venv/lib/python3.13/site-packages/certifi/cacert.pem
```

재현 조건
환경: macOS, python.org 배포판 Python 3.13 기반 venv. 표준 라이브러리 `urllib.request`로 HTTPS 요청 시 항상.

원인
표면 - 인증서 검증 실패.
근본 - **`urllib`은 OpenSSL의 기본 신뢰 저장소를 보고, `requests`는 `certifi` 번들을 본다.** macOS의 python.org 배포판은 시스템 키체인을 OpenSSL 신뢰 저장소로 연결하지 않는다(그래서 `Install Certificates.command`를 따로 실행하게 돼 있다). 이 venv에서는 그 단계를 거치지 않았고, `certifi`는 `requests` 의존성으로 이미 설치돼 있었다. `curl`은 아예 별개로 시스템 저장소를 쓰므로 셋의 결과가 갈렸다.

시도했지만 안 된 것
없다. `curl`과 `certifi` 확인 한 번으로 갈렸다. 다만 **`curl`로 먼저 확인하지 않았다면** 네트워크 차단으로 오진하고 프록시 설정을 뒤졌을 가능성이 크다.

해결
일회성 프로브를 `urllib` 대신 `requests`로 바꿨다. 리포에 남는 코드(`scripts/calibrate_clip_window.py`, `scripts/build_pitch_group_clips_dataset.py`)도 전부 `requests`를 쓴다.

```python
# 안 됨
import urllib.request
data = json.load(urllib.request.urlopen(url))

# 됨 — certifi 번들을 사용
import requests
data = requests.get(url, headers={"User-Agent": UA}, timeout=60).json()
```

`requests`는 이미 의존성에 있어 추가 설치가 없었다.

검증
전환 후 StatsAPI 조회 280/280 성공, Savant 클립 페이지·mp4 다운로드도 정상(4,989,652바이트, `video/mp4`).

추후 관리
재발 방지 - 이 프로젝트에서 HTTP 요청은 `requests`로 통일한다. 표준 라이브러리라는 이유로 `urllib`을 쓰지 않는다.
남은 리스크 - venv 자체의 신뢰 저장소는 고치지 않았다. `urllib`을 쓰는 서드파티 라이브러리를 새로 넣으면 같은 증상이 날 수 있다. 근본 해결은 `/Applications/Python 3.13/Install Certificates.command` 실행이다.

배운 점
**"네트워크가 안 된다"는 결론은 도구를 바꿔 확인하기 전까지 성립하지 않는다.** 에러 메시지가 SSL을 가리켰지만 원인은 그 프로세스의 인증서 경로였다. `curl` 한 줄이 범위를 절반으로 줄였다.

## TS-023 · 특징을 더하니 전체 정확도는 올랐는데 겨냥한 클래스는 나빠졌다

날짜: 2026-08-07
영역: ML
심각도: Medium
상태: 해결됨

증상

OFFSPEED(체인지업·스플리터) f1 0.14를 올리려고 궤적 좌표에서 특징 7개를 새로 뽑아 붙였다. 결과는 겉보기에 성공이었다.

```
[기준(7)]   정확도 0.587 (기준선 대비 +0.103)  중요도비  3.75
            OFFSPEED  p=0.24 r=0.10 f1=0.14
[+시간(10)] 정확도 0.600 (기준선 대비 +0.117)  중요도비  7.31
            OFFSPEED  p=0.09 r=0.05 f1=0.06
[+기하(11)] 정확도 0.673 (기준선 대비 +0.190)  중요도비 24.31
            OFFSPEED  p=0.14 r=0.07 f1=0.10
[전체(14)]  정확도 0.673 (기준선 대비 +0.190)  중요도비 21.96
            OFFSPEED  p=0.10 r=0.05 f1=0.07
```

정확도 +8.6%p, 중요도비 3.75 → 24.31. 판정 지표 세 개 중 둘이 큰 폭으로 좋아졌다. 그런데 **이 작업의 목적이었던 OFFSPEED f1은 0.14에서 0.07로 반토막 났다.**

재현 조건

클래스 사전확률이 크게 불균형한 상태(FASTBALL 48% / BREAKING 38% / OFFSPEED 13%)에서 소수 클래스를 겨냥해 특징을 추가할 때. 홀드아웃 300개 중 OFFSPEED는 40개라, 40개를 전부 틀려도 전체 정확도는 0.87배까지만 떨어진다.

원인

표면 - 특징을 늘렸는데 목표 클래스의 f1이 내려갔다.

근본 - **추가한 특징이 FASTBALL·BREAKING의 분리에만 기여했고, 그 결과 모델이 OFFSPEED를 더 확실하게 버리게 됐다.** 임계값과 무관한 one-vs-rest AUC로 재면 이게 그대로 보인다.

```
                기준(7)  ->  전체(14)
FASTBALL AUC     0.792   ->   0.851   (+0.059)
BREAKING AUC     0.725   ->   0.819   (+0.094)
OFFSPEED AUC     0.641   ->   0.648   (+0.007)   <- 사실상 제자리
```

혼동행렬에서는 OFFSPEED 40개 중 2개만 맞고 나머지가 FASTBALL 19 / BREAKING 19로 갈린다. 다른 두 클래스의 경계가 선명해질수록, 사전확률 13%짜리 클래스를 argmax로 뽑을 이유는 오히려 줄어든다.

물리적으로는 예상된 결과였다. 체인지업·스플리터를 패스트볼과 가르는 것은 **속도**인데, 픽셀 좌표만으로는 절대 속도를 복원할 수 없다. 새로 넣은 7개는 전부 좌표에서 파생된 것이라 OFFSPEED에 넣을 정보가 애초에 없었다.

시도했지만 안 된 것

- **가설: 시간 계열 특징(`frame_span`, `end_frame`, `speed_ratio_late_early`)이 속도 대리 지표가 되어 OFFSPEED를 가른다.** 틀렸다. `+시간(10)`은 정확도 0.587 → 0.600으로 거의 안 움직였고 OFFSPEED f1은 0.14 → 0.06으로 내려갔다. 정확도 상승분은 전부 기하 계열 4개, 그중 `vertical_accel_px` 하나(중요도 0.42)가 끌었다.
- **가설: 결정 규칙만 고치면(클래스 가중치) 목표를 통과한다.** 수치상으로는 통과하지만 새 정보가 아니다. 가중치를 올리면 f1이 오르는 대신 전체 정확도가 정확히 원위치한다 — 같은 ROC 곡선 위에서 동작점만 옮긴 것이고, AUC가 안 움직였다는 사실과 일치한다.

```
OFFSPEED 가중치  1: 전체정확도 0.673  p=0.14 r=0.07 f1=0.10
OFFSPEED 가중치  3: 전체정확도 0.607  p=0.21 r=0.35 f1=0.26
OFFSPEED 가중치  8: 전체정확도 0.587  p=0.25 r=0.57 f1=0.35
OFFSPEED 가중치 12: 전체정확도 0.597  p=0.27 r=0.65 f1=0.38
```

해결

두 가지를 갈라 처리했다.

1. **정확도 개선은 진짜다** — 경기 단위 leave-one-game-out 4폴드로 재확인했다. 홀드아웃 1경기의 우연이 아니다.

```
기준(7)    정확도 0.613 (경기별 0.66 / 0.59 / 0.62 / 0.59)  기준선 대비 +0.165
+기하(11)  정확도 0.661 (경기별 0.66 / 0.63 / 0.68 / 0.67)  기준선 대비 +0.212
전체(14)   정확도 0.659 (경기별 0.66 / 0.64 / 0.65 / 0.67)  기준선 대비 +0.210
```

2. **OFFSPEED는 좌표로 안 된다는 것이 확정됐다** — 그래서 박스 크기(공이 카메라에 가까워지는 속도)로 넘어간다. 캐시가 `(frame_idx, [cx, cy, conf])`만 담고 mp4는 처리 후 지우므로 재수집이 필요하다. 재수집을 두 번 하지 않도록 `extract_trajectory_candidates`가 `(x, y, conf, w, h)`를 남기게 먼저 고치고, v1 캐시 히트로 건너뛰어지지 않도록 `clip_trajectory_cache_v2/`로 분리했다.

검증

- 특징 확장 전후로 기존 7개 컬럼이 1030행 전부 비트 단위 동일 (`np.allclose(equal_nan=True)`) — 신규 특징이 기존 계산을 건드리지 않았다
- 재수집 전 클립 1개 스모크 테스트에서 박스 크기가 실제로 잡히고(`(683.0, 328.0, 0.204, 13.0, 19.0)`) 좌표·신뢰도가 v1 캐시와 정확히 일치 — 재수집이 같은 궤적을 재현한다
- 전체 테스트 79개 통과

추후 관리

재발 방지 - **소수 클래스를 겨냥한 작업은 전체 정확도로 판정하지 않는다.** 판정 지표에 대상 클래스의 one-vs-rest AUC를 넣는다. AUC는 임계값·클래스 가중치와 무관해서 "정보가 늘었나"와 "동작점을 옮겼나"를 갈라준다. f1만 보면 둘이 섞인다.

남은 리스크 - `vertical_accel_px` 하나가 중요도 0.42로 지배적이다. 4경기 4폴드에서 일관되긴 하나, 중계 카메라가 다른 시즌·다른 구장에서도 유지되는지는 확인 안 됐다.

배운 점

**"지표 셋을 함께 본다"는 규칙만으로는 부족하다. 그 셋이 목표와 같은 것을 재는지도 확인해야 한다.** 이번에 정확도와 중요도비는 정직하게 개선을 가리켰다. 다만 그 개선이 다른 클래스에서 왔을 뿐이다. TS-021에서 "사슬 확보율"이 타구 비행을 세고 있었던 것과 같은 구조다 — 지표는 자기가 정의한 것을 정확히 쟀고, 그게 알고 싶던 것이 아니었다.

## TS-024 · 속도 대리 지표의 물리적 전제가 이 카메라에서 성립하지 않았다

날짜: 2026-08-07
영역: ML
심각도: Medium
상태: 해결됨

증상

TS-023에서 "픽셀 좌표로는 절대 속도를 복원할 수 없으니 박스 크기(공이 카메라에 가까워지는 속도)가 유일한 속도 대리 지표"라고 결론짓고, 1193개 클립을 전부 재다운로드·재감지했다(약 100분). 박스 특징 2개를 붙인 결과는 이렇다.

```
[기준(7)]     홀드아웃 0.590  LOGO 0.614  OFFSPEED LOGO AUC 0.710
[+기하(11)]   홀드아웃 0.670  LOGO 0.659  OFFSPEED LOGO AUC 0.730
[좌표전체(14)] 홀드아웃 0.657  LOGO 0.654  OFFSPEED LOGO AUC 0.724
[+박스(16)]   홀드아웃 0.700  LOGO 0.665  OFFSPEED LOGO AUC 0.728
```

전체 정확도는 홀드아웃 0.700으로 최고를 찍었다. 그런데 **OFFSPEED AUC는 0.710 → 0.728, +0.018로 사전에 정한 기준 0.03에 못 미쳤다.** 박스 특징을 넣기 전인 `+기하(11)`의 0.730보다도 낮다. FASTBALL·BREAKING AUC도 0.861 → 0.850, 0.827 → 0.822로 미세하게 내려갔다. 정확도만 오르고 정보량은 늘지 않은 것이다.

재현 조건

중견수 뒤에서 홈플레이트를 향해 잡는 표준 중계 카메라. Baseball Savant 투구별 클립은 전부 이 앵글이다.

원인

표면 - 박스 크기 변화율이 OFFSPEED를 가르지 못한다.

근본 - **"공이 카메라에 가까워진다"는 전제가 이 앵글에서 틀렸다.** 카메라가 투수 뒤에 있으므로 공은 던져지는 순간부터 카메라로부터 **멀어진다**. 실측된 `box_growth_per_frame`은 평균 −0.148 px/frame(표준편차 0.312)로 음수다.

크기 문제도 겹친다. 궤적 하나가 약 10프레임이므로 총 변화량은 1.5px 남짓인데, 박스 자체가 평균 17.0px(표준편차 1.8)이고 YOLO 박스 좌표는 정수로 양자화된다. **재려는 신호가 측정 단위보다 작다.**

```
release_box_size        평균 17.03  표준편차 1.81
box_growth_per_frame    평균 -0.15  표준편차 0.31   <- 10프레임 누적 1.5px
```

시도했지만 안 된 것

- **가설: 끝점 차분이 양자화에 취약하니 최소제곱 기울기로 바꾸면 신호가 산다.** 실제로 `_box_growth_per_frame`을 끝점 차분에서 전체 점 최소제곱 적합으로 구현했다. 기울기 추정은 안정됐지만 AUC는 안 움직였다. 추정 방법의 문제가 아니라 신호 자체가 없었다.
- **조기 신호를 무시하고 완주했다.** 재수집이 69개 쌓였을 때 `box_growth_per_frame` 단변량 OFFSPEED AUC가 0.540(무신호)이었다. 그 시점에 중단할 수 있었으나 부분 표본이라 판단을 유보하고 끝까지 돌렸다. 최종 수치는 조기 신호와 일치했다.

해결

3분류를 접고 **FASTBALL vs BREAKING 2분류로 문제를 재정의했다.**

```
경기 단위 leave-one-game-out (n=857)
 game_pk    n   정확도  기준선   AUC
  775294  211   0.735  0.592  0.857
  813024  247   0.794  0.425  0.901
  813026  139   0.827  0.597  0.912
  813027  260   0.777  0.558  0.852
평균          0.783  0.543  (+0.240)   평균 AUC 0.881
```

3분류 LOGO 0.665보다 높고 경기별 편차도 작다. OFFSPEED를 억지로 끼워 셋 다 흐리게 만드는 것보다, **중계 영상으로 되는 것과 안 되는 것의 경계를 명시하는 쪽**이 정직한 결론이다.

박스 특징 2개는 코드에서 빼지 않았다. 전체 정확도 기준으로는 최고 집합이고(홀드아웃 0.700), `box_growth_per_frame`은 중요도 3위(0.054)다. OFFSPEED에 정보를 안 넣었을 뿐 무용하지는 않다.

검증

- 재수집 다운로드 실패 0건, 1193투구 중 궤적 1029개(86.3%) — v1의 1030개와 1개 차이. 재수집이 같은 궤적을 재현했다
- 박스 컬럼이 궤적 확보 1029행 전부에 0이 아닌 값으로 채워짐 (미수집 상태의 0.0 폴백과 구분됨)
- 전체 테스트 84개 통과

추후 관리

재발 방지 - **대리 지표를 도입할 때는 그 물리적 전제가 이 데이터에서 성립하는지 먼저 한 클립으로 잰다.** 이번 건은 클립 하나에서 박스 크기 시계열만 찍어봤어도 부호가 음수인 것을 100분 전에 알 수 있었다.

남은 리스크 - 2분류로 좁혔을 뿐 OFFSPEED 문제 자체는 미해결이다. 절대 속도가 필요하면 중계 영상이 아니라 트래킹 데이터(Statcast `release_speed`)를 라벨이 아닌 입력으로 쓰는 경로를 따로 검토해야 한다. 그 경우 "영상만으로 예측"이라는 전제가 깨진다.

배운 점

**대리 지표는 "무엇을 대신하는가"보다 "그 대신이 이 측정 조건에서 성립하는가"가 먼저다.** 박스 크기가 거리를 반영한다는 것 자체는 맞다. 다만 이 카메라에서는 부호가 반대고 변화량이 측정 해상도 아래였다. TS-023이 "지표가 목표와 다른 것을 쟀다"였다면, 이번은 "지표가 잴 수 있는 크기가 아니었다"다.
