## TS-001 · 대용량 CSV·모델이 커밋 이력에 쌓여 .git이 2GB까지 비대화

날짜: 2026-07-27
영역: Infra
심각도: High
상태: 해결됨 (히스토리 재시작)

증상
커밋은 4개뿐인데 git count-objects -vH로 확인한 .git 크기가 로컬 기준 500MB 이상, 패킹된 상태로도 1.4GB를 넘었다.

재현 조건
각 커밋에 Statcast CSV(월별 6개, 전체 87MB), YOLO 사전학습 가중치, 학습된 모델(.h5)이 그대로 커밋되어 있던 상태에서 git count-objects -vH 실행.
재현율: 항상 (이 이력을 갖고 있는 한).

원인
표면 - .git이 비정상적으로 크다.
근본 - .gitignore를 나중에 추가해도 이미 커밋된 이력의 blob은 그대로 남는다. 매달 수십 MB짜리 CSV와 대용량 바이너리가 초기 커밋들에 반복적으로 쌓여 있었다.
확인 방법 - git count-objects -vH로 로컬/패킹 용량을 직접 측정.

시도했지만 안 된 것
시도: .gitignore만 추가
결과: 용량 그대로
이유: 이미 커밋된 과거 이력은 .gitignore의 영향을 받지 않는다

해결
두 선택지(git filter-repo로 과거 이력에서 대용량 blob 제거 / 현재 상태 기준으로 새 히스토리 시작) 중, 커밋이 4개뿐이라 잃을 게 적고 이미 public 저장소라 과거 이력에 민감정보가 없는지도 재확인해야 했기 때문에 새 히스토리로 시작하는 쪽을 선택했다. 기존 히스토리는 로컬 브랜치로 보존.
커밋: 85298e6 Restart project history with a clean, reproducible snapshot

검증
새 root 커밋 이후 서비스가 의존하는 모델 3개(pitch_predictor.h5, scaler.pkl, baseball_detector.pt)만 Git LFS로 추적되고, 재수집·재학습 가능한 대용량 산출물(Statcast CSV, YOLO 학습셋, 사전학습 체크포인트)은 .gitignore로 제외됨을 확인.

추후 관리
재발 방지 - .gitattributes에 LFS 추적 대상을 명시하고, .gitignore에 재생성 가능한 대용량 산출물을 등록해뒀다.
남은 리스크 - 새 기여자가 대용량 파일을 실수로 다시 커밋하면 동일 문제가 재발할 수 있다. pre-commit 파일 크기 훅은 아직 없음.

배운 점
.gitignore는 미래의 커밋만 막는다. 이미 이력에 들어간 대용량 파일은 별도로 제거하지 않는 한 저장소에 영구히 남는다. 커밋 수가 적을 때 정리하는 비용이 가장 낮다.

## TS-002 · 프로젝트 폴더 이동 후 venv의 pip가 shebang 경로 문제로 깨짐

날짜: 2026-07-27
영역: Build
심각도: Medium
상태: 우회 적용

증상
venv/bin/pip freeze를 실행하면 다음 에러가 났다.

bad interpreter: No such file or directory

재현 조건
환경: macOS, Python 3.13 venv
재현 절차: venv를 /Users/tina/Desktop/baseball-pitch-predictor에서 생성 → 프로젝트 폴더를 /Users/tina/Project/baseball-pitch-predictor로 이동 → venv/bin/pip freeze 실행
재현율: 항상

원인
표면 - pip 실행이 안 됨.
근본 - venv 생성 시 pip, pip3, ipython 등 콘솔 스크립트의 첫 줄(shebang)에 인터프리터의 절대경로가 하드코딩된다(#!/Users/tina/Desktop/.../venv/bin/python3.13). 폴더를 옮기면 이 경로가 더는 존재하지 않아 셸이 인터프리터를 못 찾는다.
확인 방법 - venv/pyvenv.cfg와 콘솔 스크립트 첫 줄을 직접 열어 옛 경로(/Desktop/...)가 박혀 있는 것을 확인.

시도했지만 안 된 것
시도: venv/bin/pip 직접 실행
결과: 동일 에러
이유: 스크립트 자체의 shebang이 깨진 것이라 실행 방식을 바꿔도 소용없음

해결
venv/bin/python3.13은 시스템 Python으로의 심볼릭 링크라 경로 이동의 영향을 받지 않는다는 점을 이용해, 인터프리터를 직접 호출하는 방식으로 우회했다.

venv/bin/python3.13 -m pip freeze

requirements.txt 자체는 pip freeze에 의존하지 않고, site-packages의 *.dist-info 폴더명에서 패키지명·버전을 직접 파싱해서 만들었다.

검증
위 명령으로 패키지 목록을 정상적으로 얻어 requirements.txt를 작성했다.

추후 관리
재발 방지 - 근본 해결은 아니다. venv 자체를 새로 만드는 것이 가장 깔끔한 해법으로 남아 있다.
남은 리스크 - 이 venv를 다시 옮기면 동일 증상이 재발한다.

배운 점
venv의 콘솔 스크립트(pip, ipython 등)는 인터프리터 경로가 생성 시점에 고정된다. venv 폴더(또는 상위 프로젝트 폴더)를 옮기면 항상 깨진다고 가정해야 하고, python -m pip 형태로 인터프리터를 직접 호출하면 임시 우회가 가능하다.

## TS-009 · Streamlit 컴포넌트 안에 YouTube iframe을 재중첩해 오류 153으로 영상 재생 자체가 안 됨

## TS-010 · git worktree로 전환하기 직전 커밋 없이 작성한 파일이 워크트리에는 보이지 않아 유실

날짜: 2026-08-05
영역: Infra
심각도: Medium
상태: 해결됨

증상
브레인스토밍 스킬로 설계 문서를 작성·커밋한 뒤, 이어서 구현 계획 문서(`docs/superpowers/plans/2026-08-05-pitch-type-cv-classifier-pilot.md`)를 메인 체크아웃에 Write로 작성했다. 곧바로 `EnterWorktree`로 격리된 작업공간으로 전환한 뒤 `sdd-workspace` 스크립트로 그 계획 파일을 읽으려 하자 `no such plan file` 에러가 났다.

재현 조건
환경: 같은 저장소 안에서 Write 도구로 새 파일 생성 → git add/commit 하지 않은 상태 → EnterWorktree(name=...)로 새 워크트리 진입.
재현율: 항상 (커밋 없이 작성한 파일이 있는 상태에서 워크트리 전환 시).

원인
표면 - 방금 만든 파일이 새 워크트리 디렉터리에 없다.
근본 - git worktree는 같은 `.git` 객체 저장소를 공유하지만 워크트리마다 독립된 작업 디렉터리(파일시스템)를 갖는다. 커밋되지 않은 워킹트리 변경분은 git 객체가 아니라 순수 파일시스템 상태이므로, 다른 워크트리에서는 애초에 존재할 방법이 없다. `EnterWorktree`는 브랜치(커밋 이력) 기준으로 워크트리를 만들 뿐, 원본 체크아웃의 미커밋 변경분을 복사해오지 않는다.
확인 방법 - 워크트리 진입 후 `ls docs/superpowers/plans/`로 해당 파일이 없는 것을 확인, `git status --short`로 원본 체크아웃 쪽에는 아직 untracked 상태로 남아있었을 것으로 추정(직접 재확인은 샌드박스 제약으로 워크트리 세션에서 다른 워크트리 경로에 대해 `git -C`를 쓸 수 없어 못함).

시도했지만 안 된 것
없음 — 원인이 명확해서 바로 우회로 넘어감.

해결
같은 내용을 워크트리 안에서 Write로 다시 작성하고 그 자리에서 커밋했다. 이후 `sdd-workspace`/`task-brief` 스크립트가 정상적으로 파일을 찾음.

검증
`sdd-workspace docs/superpowers/plans/...pilot.md` 재실행 시 정상적으로 워크스페이스 경로 출력, 이후 태스크별 `task-brief` 생성도 문제없이 진행됨.

추후 관리
재발 방지 - 앞으로 이런 워크플로(브레인스토밍 → writing-plans → subagent-driven-development)를 이어서 진행할 때는, 워크트리 전환 직전에 만든 파일은 반드시 커밋까지 마치고 나서 EnterWorktree를 호출한다.
남은 리스크 - 아래 정정 참고. 커밋해도 완전히 안전하지는 않다.

정정 (2026-08-05, 최종 브랜치 리뷰 중 발견) - 최초 진단이 절반만 맞았다. 이번 세션에서 실제로 유실된 파일은 두 종류였다.
(1) 구현 계획 문서(`docs/superpowers/plans/...pilot.md`) — Write만 하고 커밋 안 한 상태에서 워크트리 전환 → 원인은 위에 기록한 그대로.
(2) 설계 스펙 문서(`docs/superpowers/specs/2026-08-05-...design.md`) — 이건 실제로 로컬 main 브랜치에 **커밋까지 했었다**(커밋 11f880c). 그런데도 워크트리에는 없었다. `git merge-base --is-ancestor 11f880c HEAD`로 확인해보니 11f880c는 워크트리 브랜치의 조상이 아니었다. 원인은 `EnterWorktree`의 `worktree.baseRef` 기본값이 `fresh`라는 점 — 이는 로컬 `main` HEAD가 아니라 **`origin/main`(원격 추적 브랜치)**을 기준으로 새 브랜치를 만든다. 그 시점에 로컬 main은 이미 11f880c까지 진행했지만 아직 push 전이라 origin/main은 그 이전 커밋(6f6abf2)에 머물러 있었고, 그 결과 로컬에만 있던 커밋이 통째로 새 워크트리 브랜치에서 빠졌다.
즉 "커밋했으니 안전하다"가 성립하려면 **push까지 돼 있거나, `worktree.baseRef=head`로 로컬 HEAD 기준 분기**해야 한다. 재발 방지 항목을 이렇게 정정한다: 워크트리 전환 전에는 (a) 커밋 여부뿐 아니라 (b) 그 커밋이 origin에 반영됐는지, 또는 baseRef 설정이 로컬 HEAD 기준인지도 함께 확인해야 한다.

배운 점
git worktree는 "같은 저장소의 다른 브랜치를 보는 창"이지 "같은 작업 디렉터리의 스냅샷"이 아니다. 커밋되지 않은 파일은 그 워크트리에만 속한다. 나아가 로컬에만 있고 origin에 push하지 않은 커밋도, 워크트리 도구가 기본적으로 origin 기준(`fresh`)으로 브랜치를 만든다면 새 워크트리에서 조용히 빠질 수 있다 — "커밋했다"와 "다른 워크트리에서 보인다"는 별개의 조건이다.

상태: 해결됨

증상
CV 구종 그룹 분류기 파일럿(`scripts/build_pitch_group_dataset.py`)을 실제 경기(game_pk=775294, 2024 WS G1) 하나로 처음 돌리자 데이터셋이 0행으로 나오고 중단됐다.

```
OCR 타임스탐프(65개)와 Statcast 투구 수(280개)가 달라 앞에서부터 65개만 매칭합니다.
game_pk=775294 OCR-Statcast 구종 그룹 일치율이 25.6%로 낮아 페어링 밀림이 의심됩니다. 이 경기 데이터를 제외합니다.
[중단] 생성된 데이터셋이 비어 있습니다. 위 경고 로그를 확인하세요.
```

재현 조건
환경: macOS, `yolo_detector.resolve_video_path()`로 받은 YouTube 영상(640x360, 29.97fps, 137분), tesseract OCR.
재현율: 항상.

원인
표면 - OCR이 280구 중 65구(23%)만 검출했고, 검출된 것마저 Statcast 구종 시퀀스와 25.6%만 일치했다.
근본 - `yolo_detector.resolve_video_path()`가 yt-dlp 포맷 셀렉터에 `height<=360`을 하드코딩하고 있었다. 이 함수는 원래 공 모션 감지 데모용(속도·용량 우선)으로 만들어졌고 OCR 판독을 고려한 적이 없다. 360p에서 Fox 스코어보드의 구속·구종 텍스트는 원본 크롭 기준 각각 약 12x80px, 16x205px로, 압축 노이즈와 모션 블러가 겹치면 tesseract가 프레임마다 다르게 오독한다. 그 결과 "MPH" 부분문자열 매칭과 "P:N" 정규식이 대부분의 샘플에서 조용히 빗나갔다.
확인 방법 - 스캔 로직(15프레임 간격 샘플링 + 해시 변화 감지 + 임계값 이진화)을 그대로 복제해 필터링 **전** 원시 OCR 출력을 구간별로 로깅했다. 1200~1500초 5분 구간에서 260샘플 중 "MPH"가 깨끗하게 잡힌 건 2건뿐이었고, 나머지 다수는 오버레이가 없는 게 아니라 콜론이 빠진 "PN", M이 빠진 "PH" 같은 오독이었다.

시도했지만 안 된 것
- 처음 세운 가설은 "크롭 위치가 잘못됐다"였다. 넓은 하단 크롭을 떠서 육안 확인했더니 실제 스코어보드("KNUCKLE CURVE / 82MPH / COLE / NYY 0 LAD 0")와 정확히 맞아 있었다 — 위치 문제가 아니었다.
- 두 번째 가설은 "360p면 무조건 못 읽는다"였는데, 프레임 한 장을 뽑아 5~6배 업스케일하니 사람 눈에는 읽혔다. 즉 "항상 불가"가 아니라 "프레임마다 되다 안 되다" 하는 문제였고, 이 구분이 원인 특정의 열쇠였다.

해결
`yolo_detector.py`는 기존 데모 파이프라인이 공유하고 설계 문서상 비범위(수정 금지)라 건드리지 않았다. 대신 파일럿 스크립트 안에 720p 다운로더 `resolve_video_hq()`를 새로 만들고, 캐시 파일명도 `pitchiq_hq_yt_<id>.mp4`로 분리해 기존 360p 캐시와 충돌하지 않게 했다.

검증
같은 1200~1500초 구간을 720p 영상으로 재계측: 원시 "MPH" 검출 2건 → 18건(9배). 이어 전체 경기 실행에서 OCR 검출이 65개 → **237개(280구 중 85%)**로 올라갔고, 일치율 게이트에 걸리지 않고 다음 단계로 진행됐다.

추후 관리
재발 방지 - OCR을 쓰는 경로와 모션 감지만 쓰는 경로는 요구 해상도가 다르다. 영상 획득 함수를 공유할 때 해상도 가정을 호출부가 아니라 함수 안에 숨겨두면 이런 식으로 조용히 어긋난다.
남은 리스크 - 여전히 15%는 미검출이다. 파일럿 표본 확보에는 충분하지만, 1080p 상향이나 크롭·전처리 튜닝 여지가 남아 있다. 720p 파일은 경기당 약 1.2GB로 360p(455MB)의 2.6배라 디스크 사용량이 늘어난다.

배운 점
파이프라인이 비어 있는 결과를 낼 때, 새로 만든 코드보다 **재사용한 기존 코드의 숨은 가정**을 먼저 의심해야 한다. 이번에 신규 패키지(`pitch_type_cv`)의 안전장치(일치율 50% 미만이면 해당 경기 제외)는 정확히 설계대로 작동해 오염된 데이터가 학습셋에 들어가는 것을 막았다 — 빈 데이터셋은 버그가 아니라 안전장치가 일한 결과였다. 또한 "읽히나?"를 한 장으로 확인하는 것과 "일관되게 읽히나?"를 분포로 확인하는 것은 전혀 다른 질문이다.

## TS-012 · 720p 전환 후 궤적 추출이 4배 느려짐 — 59.94fps와 MPS 미사용, 그리고 내림 연산이 샘플링을 무효화

날짜: 2026-08-05
영역: ML
심각도: Medium
상태: 해결됨

증상
TS-011 수정(720p 전환) 후 OCR은 237개까지 정상 검출됐으나, 그다음 궤적 추출 단계에서 진행이 거의 멈춘 것처럼 느려지고 아래 로그가 수백 줄 쏟아졌다.

```
[OCR] 7975.5s → Fastball Nonemph
[OCR] 완료: 237개 감지 (예상 0개)
OCR 타임스탐프(237개)와 Statcast 투구 수(280개)가 달라 앞에서부터 237개만 매칭합니다.
[h264 @ 0x340f54470] mmco: unref short failure
```

재현 조건
환경: macOS(Apple Silicon), 720p 59.94fps 영상, yolov8n, `extract_trajectory_window()` 기본 윈도우(t-3.0s ~ t-0.3s).
재현율: 항상.

원인
표면 - `mmco: unref short failure`가 계속 출력되며 느려 보였다.
근본 - 세 가지가 겹쳤고, **눈에 띈 로그는 원인이 아니었다**.
(1) `mmco` 경고는 임의 위치 시크 시 H.264 디코더가 참조 프레임을 잃으며 내는 무해한 경고다. 실측 결과 디코딩·시크는 투구당 0.8~1.0초로 전체의 4%에 불과했다. 나머지 96%는 YOLO 추론이었다.
(2) 720p 다운로드는 **59.94fps**였다(360p는 29.97fps). 같은 2.7초 윈도우가 81프레임 → 163프레임으로 두 배가 됐다. 원 설계는 30fps 기준(`yolo_detector.DEFAULT_FPS = 30`)이었으므로 이는 의도치 않은 배증이다.
(3) Ultralytics는 macOS에서 MPS를 자동 선택하지 않아 CPU로 돌고 있었다(125ms/frame).
확인 방법 - 한 윈도우에 대해 디코딩 시간과 YOLO 시간을 분리 계측하고, CPU/MPS × 전체프레임/절반샘플링 × 1장씩/배치16의 6개 조합을 실측 비교했다.

시도했지만 안 된 것
- **배치 추론(batch=16)**: 이론상 가장 유망해 보였으나 실측에서 오히려 느렸다(MPS 기준 절반샘플링 3.10s → 8.80s). `WARNING ⚠️ NMS time limit 2.050s exceeded`가 뜨는 것으로 보아 NMS가 병목이었다. 채택하지 않았다.
- **첫 수정이 조용히 무효였다**: `target_fps` 샘플링을 넣고 유닛 테스트 37개가 전부 통과했는데, 실제 영상에서 궤적 포인트가 61/32/72로 **수정 전과 완전히 동일**했다. 원인은 `step = int(fps / target_fps)` — `59.94 / 30.0 = 1.998`을 내림하면 **1**이 되어 샘플링이 통째로 사라진다. 합성 테스트 영상은 정확히 60.0fps라 `2`가 나와 통과해버렸다. NTSC 프레임레이트(29.97/59.94)는 정수 배수에서 미세하게 어긋난다는 점을 놓친 것이다.

해결
`yolo_detector.py`·`pose_detector.py`는 설계상 비범위라 그대로 두고, 파일럿 범위 안에서만 고쳤다.
- `frames_in_window()`/`extract_trajectory_window()`에 `target_fps: float | None = None` 추가(기본값 None이라 기존 호출부 5곳 전부 동작 불변). 건너뛸 프레임은 `grab()`만 호출해 BGR 변환·복사를 생략.
- 스텝 계산을 `_sampling_step()` 순수 함수로 분리하고 **내림 대신 반올림**으로 교체. NTSC 케이스(59.94/30 → 2, 29.97/30 → 1, 30/60 → 1)를 검증하는 회귀 테스트 추가.
- 파일럿 스크립트에서 `torch.backends.mps.is_available()`일 때 `yolo_model.to("mps")`, `target_fps=30.0` 전달.
- `OPENCV_FFMPEG_LOGLEVEL=-8`을 cv2 import 전에 설정해 무해한 h264 경고 로그만 억제.

검증
유닛 테스트 37개 전부 통과. 실제 영상 3개 윈도우 실측에서 궤적 포인트가 61/32/72 → 30/16/37로 정확히 절반이 되어 샘플링 적용을 확인했고, 투구당 20.3초 → 9.8초(237투구 환산 80분 → 39분)로 개선됐다.

추후 관리
재발 방지 - 프레임레이트가 걸린 계산은 합성 60.0fps 영상만으로 검증하면 안 된다. 실제 방송 영상은 NTSC(29.97/59.94)다.
남은 리스크 - 벤치 예측은 12분이었으나 실측은 39분이었다. 차이는 디코딩 비용으로, 82프레임을 고르려면 163프레임을 모두 디코딩해야 하기 때문이다. 키프레임 기반 시크나 윈도우 축소(설계 문서가 "첫 경기로 실측 보정 필요"라고 명시한 t-3.0s~t-0.3s 범위)로 더 줄일 여지가 있다.

배운 점
가장 시끄러운 로그가 가장 중요한 원인인 경우는 드물다 — `mmco` 경고는 수백 줄이 떴지만 비용의 4%였고, 조용한 CPU 폴백이 96%였다. 그리고 **유닛 테스트 통과가 수정 적용을 보장하지 않는다**. 합성 픽스처가 실제 데이터의 성질(NTSC 프레임레이트)을 갖고 있지 않으면, 테스트는 통과하면서 프로덕션에서는 아무 일도 일어나지 않는다. 이번에는 실제 영상으로 사후 실측을 한 덕에 잡았다.

## TS-013 · COCO 'sports ball' 오탐으로 궤적의 65%가 랜덤워크였고, 그 노이즈가 가짜 그룹 분리를 만들어냄

날짜: 2026-08-05
영역: ML
심각도: High
상태: 우회 적용

증상
TS-012 수정 후 첫 데이터셋(233샘플)이 정상 생성됐고, 그룹별 특징 중앙값이 아래처럼 크게 갈렸다. 이 시점에는 "궤적 특징이 구종 그룹을 구분한다"는 신호로 보였다.

```
group      curvature_ratio  vertical_drop_px
FASTBALL              7.09              65.5
BREAKING             20.75              29.7
```

그러나 곡률비(궤적 총길이 ÷ 시작-끝 직선거리) 분포를 보니 실제 투구에서 나올 수 없는 값이었다.

```
곡률비  중앙값 6.79   최댓값 511
곡률비 > 5.0 : 152개 = 65.2%
```

실제 투구 궤적은 거의 직선이라 곡률비가 1.0~1.5다. 6.79는 공이 프레임마다 화면을 되짚어 다니고 있다는 뜻이다.

재현 조건
환경: macOS(Apple Silicon), 720p 59.94fps 중계 영상, `yolov8n.pt`(COCO 사전학습), 클래스 `sports ball`, 윈도우 t-3.0s ~ t-0.3s, 30fps 샘플링.
재현율: 항상. 233샘플 중 152개.

원인
표면 - 궤적 특징이 그룹별로 달라 보였다.
근본 - COCO 사전학습 YOLO의 `sports ball`은 야구 중계 화면에서 공이 아닌 둥근 물체(관중석 조명, 로고, 헬멧, 스코어보드 요소 등)를 자주 잡는다. 프레임마다 다른 물체를 최고 신뢰도로 고르면 궤적이 화면을 가로지르는 **랜덤워크**가 된다. 그 랜덤워크의 통계적 성질이 장면 구성(카메라 앵글, 배경)에 따라 달라지고, 장면 구성은 구종과 상관이 있다(브레이킹볼은 헛스윙·포수 미트 클로즈업이 잦다). 그래서 **구질이 아니라 장면이 그룹을 갈랐다**.
확인 방법 - 신뢰도 필터와 연속성 필터를 임계값별로 나눠 6개 투구에 실측 적용했다.

```
타임스탬프  원시  conf>=.25      jump40      jump60     jump100
   223.7   40점       40점  22점/곡률2.0  22점/곡률2.0  24점/곡률20.6
   246.5   45점       45점  24점/곡률8.8  29점/곡률3.4  29점/곡률3.4
   275.5   53점       53점  12점/곡률2.2  12점/곡률2.2  12점/곡률2.2
   290.3   30점       30점  11점/곡률1.9  11점/곡률1.9  12점/곡률2.2
   307.1   42점       42점  13점/곡률1.2  13점/곡률1.2  13점/곡률1.8
   327.6   27점       27점  15점/곡률1.3  15점/곡률1.3  15점/곡률1.3
```

시도했지만 안 된 것
- **신뢰도 임계값 필터(conf >= 0.25)**: 가장 먼저 떠오르는 대응이었으나 **한 점도 걸러내지 못했다**(40/40, 45/45, 53/53...). `detect_ball_in_frame`이 이미 0.15 하한으로 필터링해 반환하는데, 오탐들이 전부 0.25를 넘는 신뢰도로 검출되고 있었다. 즉 **YOLO는 오탐을 확신하고 있었고, 신뢰도에는 판별력이 전혀 없었다.** `MIN_BALL_CONF`는 0.15 그대로 두었다.
- **jump 임계값 100px**: 너무 관대해 223.7s에서 오탐 구간을 다시 받아들였다(곡률 2.0 → 20.6).
- **jump 임계값 40px**: 너무 빡빡해 246.5s의 실제 궤적을 중간에서 잘랐다(29점/곡률3.4 → 24점/곡률8.8).

해결
설계상 `yolo_detector.py`는 비범위이므로 파일럿 범위 안에서만 처리했다.
- `longest_smooth_run(trajectory, max_jump_px)`를 `trajectory_features.py`에 추가. 연속 프레임 간 이동거리가 임계값 이하인 **최장 구간만** 남긴다. 실제 공은 프레임 사이를 순간이동하지 않는다는 물리적 사실이 유일한 근거다.
- `MAX_JUMP_PX = 60.0` (720p·30fps 기준). 위 실측 표에서 40과 100 양쪽 실패를 피하는 값으로 선택했다.
- `extract_trajectory_points()`를 추가해 `(x, y, conf)` 원시 좌표를 반환하고, 파일럿 스크립트가 투구 단위로 JSONL에 append 저장한다. 임계값을 다시 조정할 때 영상 재처리(경기당 39분) 없이 캐시 위에서 재계산할 수 있다.

검증

추후 관리
재발 방지 - **모델 성능을 보기 전에 입력 데이터가 물리적으로 가능한 값인지 먼저 본다.** 곡률비 511은 어떤 투구에서도 나올 수 없는 값이었고, 그 한 줄만 봤어도 그룹별 차이표를 신호로 읽지 않았을 것이다.
남은 리스크 -
(1) 필터는 "매끄러운 최장 구간"을 남길 뿐, 그 구간이 **공**인지 **투구**인지는 보장하지 않는다. 매끄럽게 움직이는 다른 물체(주자, 배트, 팬)일 수 있다.

그리고 가장 자연스러운 대응이 항상 효과적인 건 아니다 — 오탐에 대한 첫 반응은 신뢰도 임계값이었지만 판별력이 0이었다. YOLO는 틀린 물체를 자신 있게 잡는다. 실제로 통한 건 모델의 확신이 아니라 **물리적 제약(공은 순간이동하지 않는다)** 이었다.

후속 - 이 항목의 "곡률비 2.18로 개선" 결론은 **틀렸다**. 곡률비가 낮아진 이유는 궤적이 깨끗해져서가 아니라, 필터가 공 대신 매끄럽게 움직이는 투수 글러브를 골랐기 때문이다. TS-014 참고.

## TS-014 · YOLO가 공을 한 번도 잡은 적이 없었다 — 감지 713건 전부 글러브·선수 몸통

날짜: 2026-08-05
영역: ML
심각도: Critical
상태: 미해결

증상
TS-013의 연속성 필터로 곡률비가 정상 범위(중앙값 2.18)로 들어왔는데도 분류 성능이 기준선을 넘지 못했다.

```
최빈값 기준선(항상 BREAKING) : 0.496
RF 5-fold CV (누수 허용 상한): 0.517 +- 0.051
특징 중요도                   : 7개 전부 0.13~0.16 (평평)
그룹별 곡률비 중앙값          : BREAKING 2.24  FASTBALL 2.14  OFFSPEED 2.32
```

정확도가 낮은 것보다 **중요도가 평평한 것**이 이상했다. 신호가 약할 때는 특정 특징에 중요도가 몰리고 정확도만 낮다. 7개가 균등하다는 건 어느 특징에도 정보가 없다는 뜻이다.

재현 조건
환경: macOS(Apple Silicon), 720p 중계 영상(중계 기본 센터필드 와이드 앵글), `yolov8n.pt` COCO 사전학습, 클래스 `sports ball`.
재현율: 항상. 100%.

원인
표면 - 특징 공학이나 모델 선택 문제로 보였다.
근본 - **YOLO가 공을 단 한 번도 잡지 않았다.** COCO의 `sports ball`은 축구공·농구공·테니스공 크기의 물체로 학습됐다. 중계 와이드 앵글에서 야구공은 720p 기준 5~10px에 불과해 이 클래스의 학습 분포 밖이다. 대신 크기·형태가 유사한 **투수 글러브**를 높은 신뢰도로 잡았고, 글러브는 투구 동작 내내 화면에 있으며 매끄럽게 움직인다.
그 결과 TS-013의 `longest_smooth_run`이 상황을 **더 정교하게 악화**시켰다 — 공은 설령 잡혀도 궤적이 짧은데, 글러브는 82프레임 내내 연속적이다. "가장 매끄러운 최장 구간"을 고르는 규칙이 구조적으로 글러브를 선택한다. 곡률비 2.18은 투구 궤적이 아니라 **투수 팔 스윙의 곡률**이었다.
확인 방법 - 숫자를 더 보는 대신 프레임을 직접 렌더링해 감지 박스를 그렸다. 그다음 박스 크기를 정량화했다.

```
투구 15개 · 감지 713건
박스 최대변(px): 최소 23  25% 44  중앙값 49  75% 56  최대 202
12px 이하(실제 공 크기): 0건 = 0.0%
25px 초과(공일 수 없음): 711건 = 99.7%
```

신뢰도는 오히려 높았다 — 글러브 감지가 conf 0.94, 0.74, 0.70으로 나온다.

시도했지만 안 된 것
- **신뢰도 임계값**(TS-013): 판별력 0. 오탐이 정탐보다 신뢰도가 높다.
- **연속성 필터**(TS-013): 곡률 지표는 개선했으나 잡는 대상은 글러브로 고정시켰다. 지표가 좋아지는 것과 문제가 풀리는 것은 다르다.
- **경기 수 확대 검토**: 6경기(약 4시간) 추가 추출을 고려했으나, 착수 전 윈도우 검증을 먼저 한 덕에 헛수고를 피했다. 표본을 10배로 늘려도 글러브 궤적은 구종을 구분하지 않는다.
- **프로젝트 자체 학습 모델(`models/baseball_detector.pt`)로 교체**: 이 저장소에 이미 커스텀 학습된 야구공 탐지 모델이 있었고(`docs/ROADMAP.md`에 "완성된 것"으로 등재), 파일럿은 `load_model()`을 인자 없이 호출해 COCO로 폴백하고 있었다. 교체해봤더니 **더 나빴다**.

```
                감지된 프레임    박스 최대변 중앙값   12px 이하(실제 공)
COCO yolov8n     575/1230 (47%)        49px            0건
커스텀            41/1230 ( 3%)        73px (최대 636)  0건
```

  원인은 학습 데이터의 도메인이었다. `models/baseball_detector-2/val_batch0_pred.jpg`를 열어보니 학습셋이 **야구공 제품 사진·사인볼 수집품·리틀리그 스냅샷·공을 든 인물 사진**이었다. 중계 와이드 앵글에서 날아가는 5~10px 공은 한 장도 없다. 학습 지표는 좋았지만(precision 0.866 / recall 0.909 / mAP50 0.852, epoch 42) 그건 **그 데이터셋에서의 점수**다. 클래스명도 `{0: '0', 1: '1'}`로 의미가 없다.

해결
없음. 근본 원인이 파일럿 설계의 전제("사전학습 YOLO로 중계 화면의 야구공을 추적할 수 있다")에 있어, 이 파일럿 범위 안에서는 고칠 수 없다. COCO든 자체 학습 모델이든 **중계 앵글의 소형 공으로 학습된 적이 없다**는 점에서 동일하다.

검증
윈도우 자체는 정상이었다 — 컨텍스트 시트(t-6s ~ t+2s)에서 t-3s에 투수 와인드업, t-2s경 릴리스, t+0s에 결과 장면으로, `t-3.0s ~ t-0.3s` 윈도우는 실제 투구 순간을 정확히 담고 있었다. **윈도우가 아니라 감지기가 문제였다.**

추후 관리
재발 방지 - **모델 성능을 의심하기 전에 입력을 눈으로 본다.** 감지 박스를 프레임에 그려보는 데 10분이 걸렸고, 그 10분이 앞선 몇 시간의 특징 튜닝·필터 설계를 모두 대체했다. 곡률비·정확도·중요도 어느 지표도 "글러브를 보고 있다"를 말해주지 못했지만 이미지 한 장이 즉시 말해줬다.
남은 리스크 / 선택지 -
(1) **중계 도메인 프레임으로 재학습.** ROADMAP이 이미 목표로 삼은 방향이고, 빠진 것은 모델이 아니라 데이터의 도메인이다. 학습셋 재료는 이미 있다 — 720p 경기 영상, OCR 타임스탬프 237개, 검증된 윈도우. 라벨링 비용이 관건.
(2) 감지 대신 프레임 차분·광류 기반 소형 고속 물체 추적. 사전학습 모델 불필요하나 중계 컷 전환에 취약.
(3) 궤적을 포기하고 자세 추정 기반 특징으로 선회. 단, `src/pose_detector.py`는 이름과 달리 실제로는 프레임 차분 모션 감지다(ROADMAP 27행에 기록됨) — 실제 포즈 추정을 하려면 별도 구현이 필요하다.
(4) 파일럿을 음성 결과로 종료.
TS-013에서 만든 궤적 JSONL 캐시와 `longest_smooth_run`은 감지기를 교체해도 그대로 재사용할 수 있다. `detect_ball_in_frame`은 이미 `CONF_THRESHOLD = 0.15`, `BALL_CLASS_NAMES = None`으로 커스텀 모델을 받도록 준비돼 있어, 감지기 교체 시 호출부에 경로만 넘기면 된다.

배운 점
**지표가 좋아지는 것과 문제가 풀리는 것은 다르다.** 곡률비를 6.79에서 2.18로 낮췄고 그건 진짜 개선처럼 보였지만, 실제로 한 일은 "엉뚱한 물체를 더 일관되게 추적하기"였다. 지표는 자기가 무엇을 측정하는지 모른다.
그리고 **파이프라인의 가장 밑단 가정을 가장 먼저 검증해야 한다.** "YOLO가 공을 잡는다"는 이 프로젝트 전체가 딛고 선 전제였는데, 아무도 확인하지 않은 채 그 위에 특징 공학·필터·분류기·평가를 쌓았다. 전제가 틀리면 그 위 모든 층의 작업은 정교할수록 낭비다.
**학습 지표는 학습 도메인 안에서만 유효하다.** 자체 학습 모델의 mAP50 0.852는 진짜 점수였지만, 그 검증셋은 사인볼 클로즈업과 리틀리그 사진이었다. 배포 도메인(중계 와이드 앵글)에서는 감지율 3%다. 지표를 볼 때 "몇 점인가"보다 "무엇에 대해 몇 점인가"를 먼저 물어야 한다 — 이번에는 `val_batch0_pred.jpg` 한 장이 results.csv 43줄보다 많은 것을 말해줬다.
마지막으로, **가진 자산을 먼저 확인한다.** 커스텀 탐지 모델이 저장소에 있었고 ROADMAP에 "완성"으로 적혀 있었는데, 파일럿은 `load_model()`을 인자 없이 호출해 COCO로 폴백하고 있었다. 결과적으로 그 모델도 답은 아니었지만, 그걸 확인하는 데 5분이면 됐을 일을 며칠 뒤에야 했다.

## TS-015 · 감지점 중심 크롭이 움직임을 지워, 정상 추적을 "정지 물체 오탐"으로 오판

```
   48  -1.40s   719  258   23  0.42
   49  -1.37s   713  257   22  0.56
   50  -1.33s   709  256   21  0.59
   51  -1.30s   706  257   21  0.88
```

판단이 정반대로 뒤집혔다. 싱커는 x가 750→680으로 이동하다 멈추는 동안 y가 287→331로 **낙차가 가속**하고, 패스트볼은 x 734→703 이동에 y가 270→258로 **거의 평평**하다. 정지 물체가 아니라 구종별로 형태가 다른 실제 투구 궤적이다.

시도했지만 안 된 것
- **컨택트 시트를 더 많이 열어보기**: 투구 3개를 봤지만 전부 같은 인상을 줬다. 표본을 늘려도 시각화 자체가 움직임을 지우므로 몇 장을 보든 결론이 같다. 잘못된 렌더링은 반복 관찰로 교정되지 않는다.

해결
원좌표(`cx`, `cy`)를 프레임 인덱스와 함께 표로 출력해 판단했다. 크롭 타일은 "박스 안의 것이 공인가"(정체 확인)에만 쓰고, "움직이는가"(궤적 확인)는 좌표로 본다 — 두 질문에 서로 다른 도구가 필요하다.

검증
두 투구의 좌표열이 물리적으로 타당했다: 프레임 간 이동량이 연속적이고(순간이동 없음), 릴리스에서 플레이트 방향으로 단조 이동하며, 수직 낙차가 시간에 대해 가속한다. 구종 라벨(Sinker/Fastball)과 궤적 형태가 일치했다.

추후 관리
재발 방지 - **시각화가 답해줄 수 있는 질문의 범위를 먼저 정한다.** 정규화·정렬·중심맞춤이 들어간 그림은 그 축의 정보를 지운다. 감지점 중심 크롭은 위치를, 프레임 정규화는 밝기를, 궤적 정렬은 시작점을 지운다.
남은 리스크 - 투구 #158의 f42~f47에 `(640,307)` 부근 고정 좌표 오탐이 공과 동시에 잡히고 있다(`n_det=2`). 현재 추출 로직이 프레임마다 `max(conf)`를 고르므로 가끔 이 오탐을 선택한다. TS-013의 `longest_smooth_run`은 이걸 못 거른다 — 정지 물체도 "매끄럽다"는 조건을 만족하기 때문이다. 학습 완주 후에도 남으면 **직전 프레임 위치와의 연속성**으로 후보를 고르는 방식으로 바꿔야 한다.

배운 점
**틀린 결론을 만든 것은 감지기가 아니라 내 시각화였다.** TS-014의 교훈은 "숫자 말고 이미지를 봐라"였고 그건 옳았지만, 이번엔 그 이미지가 거짓말을 했다. 시각화도 코드이고, 코드처럼 검증 대상이다.
**"정지해 보인다"는 관찰은 좌표 없이는 주장이 될 수 없다.** 나는 배경이 비슷하다는 인상만으로 정지를 결론냈다. 실제로는 크롭 창이 대상을 따라다녔기 때문에 배경이 비슷했던 것이고, 이건 오히려 대상이 **움직이고 있다**는 증거였다.

## TS-016 · 백그라운드 학습 프로세스가 크래시 없이 사라짐

날짜: 2026-08-06
영역: Infra
심각도: Medium
상태: 해결됨

증상
YOLO 파인튜닝을 백그라운드로 띄운 뒤 약 21분(에폭 3의 59% 지점)에 학습이 중단됐다. 같은 시각에 진행 상황을 폴링하던 별도 백그라운드 작업도 함께 죽었다.

재현 조건
환경: macOS(Apple Silicon), 에이전트 하네스의 백그라운드 Bash 실행 기능 사용.
재현율: 미확인. 1회 발생.

원인
표면 - 학습이 실패한 것처럼 보였다.
근본 - **크래시가 아니다.** 로그에 트레이스백·에러·OOM 메시지가 전혀 없고, 마지막 줄이 정상 진행 상황(`3/50 ... 127/214 2.2s/it`)에서 그대로 끊겼다. 두 백그라운드 작업이 **동시에** 죽은 점으로 보아 개별 프로세스 실패가 아니라 하네스 수준의 백그라운드 작업 정리로 판단했다. 두 작업 모두 하네스가 추적·관리하는 대상이었다.
확인하지 않은 것 - 정확히 어떤 시그널로 종료됐는지는 확인하지 못했다. 종료 코드나 시그널 로그가 남지 않았다.

시도했지만 안 된 것
- **`nohup setsid ... &`**: macOS에는 `setsid` 바이너리가 없다. `nohup: setsid: No such file or directory`로 즉시 실패했고, 프로세스가 아예 뜨지 않았다. Linux 기준 관용구를 그대로 옮긴 실수다.

해결
Python 안에서 `os.setsid()`를 호출해 프로세스 그룹을 분리하고, 하네스가 추적하지 않는 방식으로 띄웠다.

```bash
nohup venv/bin/python3 -c "
import os
os.setsid()
from ultralytics import YOLO
YOLO('runs/detect/runs/ball_broadcast/weights/last.pt').train(resume=True)
" > train2.log 2>&1 < /dev/null & disown
```

에폭마다 체크포인트가 저장돼 있어 `resume=True`로 에폭 3부터 이어서 돌렸다. 처음부터 다시 학습하지 않았다.

검증
재개 후 로그에 `3/50 ... 1/214`부터 정상 진행이 찍히고, `ps aux | grep "[t]rain(resume"`로 프로세스 1개가 살아있음을 확인했다.

추후 관리
재발 방지 - **긴 학습은 하네스가 관리하는 백그라운드 작업으로 띄우지 않는다.** 프로세스 그룹을 분리하고, 진행 상황은 파일(`results.csv`)을 폴링해서 읽는다.
남은 리스크 - macOS에는 `setsid`가 없다. 셸 관용구를 옮길 때 플랫폼을 먼저 확인해야 한다 (`coreutils` 설치 시 `gsetsid`로 존재).

재발 사례 (2026-08-06, 같은 원인)
클립 데이터셋 빌드(`scripts/build_pitch_group_clips_dataset.py`, 1193투구·약 100분)를 하네스 백그라운드로 띄웠다가 같은 방식으로 정리됐다. 로그에 에러 없이 끊겼고 상태가 `killed`로 보고됐다. 위 재발 방지 항목을 학습에만 적용하고 **데이터 처리에는 적용하지 않은 것이 원인**이다 — 기준은 "학습이냐"가 아니라 "하네스 작업 수명보다 오래 걸리냐"다.

손실은 없었다. 감지 후보를 투구 1건마다 JSONL에 append하도록 만들어 둔 덕에 672투구분이 남아 있었고, 재기동 시 캐시 적중으로 건너뛰었다. 재기동은 `runpy`로 CLI를 그대로 실행하되 `os.setsid()`를 먼저 호출하는 형태를 썼다 — `exec(open(...).read())`는 `__file__`이 정의되지 않아 스크립트의 `ROOT` 계산이 깨진다.

```bash
nohup venv/bin/python3 -c "
import os, runpy
os.setsid()
runpy.run_path('scripts/build_pitch_group_clips_dataset.py', run_name='__main__')
" > output/pitch_type_cv/build_clips.log 2>&1 < /dev/null & disown
```

배운 점
**"죽었다"와 "실패했다"는 다르다.** 트레이스백이 없다는 사실 자체가 진단 정보다. 원인을 코드에서 찾기 전에 로그의 마지막 줄이 정상이었는지, 다른 프로세스도 같이 죽었는지를 먼저 봐야 한다.
**긴 작업은 중간 산출물이 있으면 사고가 사고로 끝난다.** Ultralytics가 에폭마다 `last.pt`를 남긴 덕에 21분치를 그대로 살렸고, 그 체크포인트로 계획보다 일찍 실전 검증까지 돌려 TS-015를 앞당겨 발견했다.

## TS-017 · 물리적으로 통과 불가능한 게이트를 세웠고, 고치니 정지 오탐이 그 게이트를 통과했다

날짜: 2026-08-06
영역: ML
심각도: High
상태: 부분 해결

증상
Roboflow 중계 도메인 데이터셋으로 파인튜닝한 감지기가 통과 기준을 계속 못 넘었다. 학습 지표는 크게 좋아지는데 실전 감지율만 제자리였다.

```
              mAP50      실전 감지율   박스 최대변 중앙값
에폭 2        0.502        16.5%           26px
에폭 15       0.912        18.3%           24px
```

mAP50이 82% 뛰는 동안 감지율은 11% 올랐다. TS-014("학습 지표는 학습 도메인 안에서만 유효하다")와 같은 형태로 보였다.

재현 조건
환경: macOS(Apple Silicon), 720p 중계 영상, 궤적 윈도우 `t-3.0s ~ t-0.3s`(2.7초, 30fps 샘플링 시 82프레임).
재현율: 항상.

원인 (1) — 게이트의 분모가 틀렸다
표면 - 감지기 성능이 부족해 보였다.
근본 - **"윈도우 프레임 대비 감지율 30%"는 물리적으로 달성 불가능한 기준이었다.** 윈도우는 2.7초인데 공이 실제로 날아가는 시간은 0.45초뿐이다(90mph로 18.44m). 30fps에서 약 14프레임, **윈도우의 17%**다. 나머지 83%는 와인드업과 포구 후 장면이라 날아가는 공이 애초에 화면에 없다. 완벽한 감지기도 이 지표로는 17%가 상한이고, 실측 18.3%는 이미 그 근처였다.
확인 방법 - 감지가 **언제** 일어나는지 프레임 인덱스와 함께 봤다. 감지가 윈도우 전체에 흩어진 게 아니라 t-1.5s ~ t-0.9s 구간에 몰려 있었고, 그 구간 길이가 공의 비행 시간과 일치했다.

원인 (2) — 고친 지표를 정지 오탐이 통과했다
분모를 궤적 품질로 바꾸자(연속 이동 사슬 길이) 7/8투구가 통과했다. 그런데 궤적 좌표를 보니 절반이 가짜였다.

```
투구 #135 Slider — 원시 후보
  f 29~f 44 : (405,453) 부근 16프레임 연속, conf 0.25~0.41   <- 화면 고정 오탐
  f 45      : (432,345|0.57)  (405,453|0.26)                 <- 공과 오탐이 동시에
  f 46      : (455,332|0.67)                                  <- 진짜 공
```

근본 - **정지 오탐은 궤적 필터를 구조적으로 통과한다.** TS-013의 `longest_smooth_run`은 "연속 프레임 간 이동이 작은 최장 구간"을 고르는데, 정지 물체는 이 조건을 **완벽하게** 만족한다. 게다가 신뢰도도 실제 공보다 높은 경우가 있어(0.71 vs 0.45) 프레임별 `max(conf)` 선택이 공을 버리고 오탐을 집는다. TS-013에서 글러브가 이긴 것과 완전히 같은 구조다.
추가로 - 감지 누락을 잇기 위한 `max_gap_frames=2` 관용 때문에, 정지 오탐이 110px 점프로 공에 이어붙었다. 사슬 **전체** 변위가 크므로 "실제로 이동하는가" 조건도 통과해버렸다.

시도했지만 안 된 것
- **`longest_smooth_run` 재사용**: TS-013 자산을 그대로 쓰려 했으나 정지 물체에 무력하다. 매끄러움은 운동성을 함의하지 않는다.
- **신뢰도 임계값 상향**: TS-013에서 이미 판별력 0으로 확인됐고, 이번에도 오탐 conf가 공보다 높은 프레임이 있어 같은 결론이다.
- **정지 구간 트림의 첫 구현**: 이동량이 작은 앞뒤 구간을 잘라내되 **경계점을 남겼더니** 효과가 없었다. 정지 구간의 마지막 점이 남고, 거기서 다음 점으로의 "큰 이동"이 운동으로 잡혀 사슬이 그대로 통과했다. 경계점 자체가 정지 물체의 좌표이므로 함께 버려야 한다.

해결
`longest_moving_chain()`을 새로 만들었다 (`src/pitch_type_cv/trajectory_features.py`). 세 조건을 함께 건다.

1. **연속성** — 프레임 간 이동 ≤ `max_jump_px`(60), 간격만큼 비례 확대
2. **운동성** — 사슬 전체 변위 ≥ `min_total_move_px`(30). 정지 사슬은 길어도 탈락
3. **앞뒤 정지 구간 트림** — 프레임당 이동 < `min_step_px`(3.0)인 앞뒤 구간 제거, **경계점 포함**

프레임별 최고 신뢰도가 아니라 후보 전체를 받도록 `extract_trajectory_candidates()`도 추가했다. 정지 오탐과 공이 같은 프레임에 있을 때 신뢰도로 고르면 공을 잃기 때문이다.

검증
합성 케이스 6개로 단위 테스트를 먼저 작성해 RED 확인 후 구현했다 (정지 오탐 배제 / 전부 정지면 빈 결과 / 1프레임 누락 브리지 / 긴 정지보다 짧은 이동 선호 / 점프로 붙은 정지 머리 트림 / 미트 정지 꼬리 트림). 기존 41개 포함 **47개 전부 통과**.

실측 대조로 트림이 과잉이 아님을 확인했다. 트림 후 0프레임이 된 두 투구의 원시 후보를 직접 열어보니, 정말로 공 궤적이 없었다.

```
#135 : 정지 오탐 16프레임 + 공 2프레임(변위 26px < 30px)  -> 궤적 없음이 맞다
#217 : (663,314) 부근 4프레임 3px 이동 + 흩어진 단발       -> 비행 궤적 자체가 없다
```

트림 전 7/8 통과는 **가짜였고**, 실제는 5/8(62%)이다. 기준 75% 미달.

추후 관리
재발 방지 - **통과 기준을 세울 때 그 지표의 물리적 상한을 먼저 계산한다.** "30%"는 그럴듯해 보였지만 상한이 17%인 지표였다. 달성 불가능한 기준은 모델을 아무리 개선해도 실패로만 보이게 만들고, 실제 진전을 감춘다.
남은 리스크 -
(1) 현재 5/8(62%)로 기준 미달. 학습이 아직 진행 중(에폭 17/50)이라 최종 판정은 완주 후다.
(2) 궤적이 잡히는 투구와 안 잡히는 투구가 무작위가 아닐 수 있다. 감지가 되는 투구만으로 데이터셋을 만들면 **선택 편향**이 생긴다 — 예컨대 배경이 어두운 구장, 특정 카메라 앵글에서만 잡힌다면 그 조건이 구종과 상관될 수 있다. Phase 4 결과 해석 시 반드시 확인해야 한다.
(3) 정지 오탐의 정체를 아직 모른다. `(405,453)`, `(663,314)`, `(601,181)` 등 투구마다 다른 위치라 화면 고정 그래픽은 아니다. 경기장 내 흰 둥근 물체로 추정되나 확인하지 않았다.

배운 점
**기준을 세우는 것과 옳은 기준을 세우는 것은 다르다.** "사후 조정 금지"를 스스로 못 박았는데, 정작 그 기준이 물리적으로 불가능했다. 규율은 지켰지만 규율이 지킬 가치가 있는지는 검증하지 않았다. 기준을 정할 때 "이 지표의 최댓값은 얼마인가"를 먼저 물었어야 했다.
**같은 실패가 형태를 바꿔 세 번 반복됐다.** TS-013은 글러브, TS-014도 글러브, TS-017은 정지 오탐이다. 전부 "매끄럽고 오래 지속되는 엉뚱한 물체가 짧고 끊기는 진짜 공을 이긴다"는 하나의 구조다. 필터를 고칠 때마다 그 구조를 다시 만족하는 다른 물체가 등장했다. 증상이 아니라 구조를 봤어야 했다 — 필요한 조건은 "매끄러움"이 아니라 **"움직임"**이었다.
**필터를 강화하면 통과율이 떨어지는 게 정상이다.** 7/8 → 5/8은 후퇴가 아니라 앞의 7/8이 거짓이었다는 뜻이다. 지표가 나빠지는 방향의 변경을 받아들일 수 있어야 실제 상태를 볼 수 있다.

## TS-018 · CONF_THRESHOLD = 0.15가 한 번도 작동한 적이 없었다

날짜: 2026-08-06
영역: ML
심각도: Critical
상태: 해결됨

증상
파인튜닝이 진행될수록 검증 지표는 오르는데 실전 감지가 **줄었다**. 에폭 30이 에폭 18보다 나빴다.

```
              mAP50    recall    실전 게이트   #53 원시감지  #144   #217
에폭 18       0.935     0.869     5/8 (62%)        10          20     12
에폭 30       0.955     0.929     4/8 (50%)         1           1      1
```

검증셋 recall이 0.869에서 0.929로 올랐는데 우리 영상에서는 감지가 1건으로 붕괴했다. 도메인 갭이 벌어지는 것으로 보였다.

재현 조건
환경: macOS(Apple Silicon), 720p 중계 영상, `yolo_detector.detect_ball_in_frame`.
재현율: 항상. 100%.

원인
표면 - 학습이 진행되며 우리 도메인에 과적합 반대 방향으로 드리프트한 것으로 보였다.
근본 - **`CONF_THRESHOLD = 0.15`가 실행되지 않는 코드였다.** `detect_ball_in_frame`은 이렇게 되어 있었다.

```python
results = model(frame, verbose=False, imgsz=imgsz)[0]
for box in results.boxes:
    conf = float(box.conf[0])
    if conf < CONF_THRESHOLD:   # 0.15
        continue
```

Ultralytics `model()`의 기본 `conf`는 **0.25**다. 모델이 이미 0.25에서 잘라낸 결과를 받아 0.15로 다시 거르고 있었으니, 이 조건은 단 한 번도 참이 된 적이 없다. TS-013에서 "방송 화면 소형 야구공 감지용(기본 0.3은 너무 높음)"이라며 0.15로 낮춘 것도 효과가 없었다.

확인 방법 - 임계값을 0.15 → 0.08 → 0.04 → 0.02로 낮추며 감지 수를 셌다.

```
=== #53 — 임계값별 감지/사슬 ===
  conf>=0.15 : 원시    1  사슬  0프레임
  conf>=0.08 : 원시    1  사슬  0프레임
  conf>=0.04 : 원시    1  사슬  0프레임
  conf>=0.02 : 원시    1  사슬  0프레임
```

**임계값을 8분의 1로 낮췄는데 결과가 한 건도 안 변한다.** 이건 모델 특성이 아니라 그 코드가 실행되지 않는다는 뜻이다. 지금까지 관측된 최저 신뢰도가 정확히 0.25였던 것과도 일치한다. 모델에 `conf`를 직접 넘기자 결과가 즉시 달라졌다.

```
=== #53 — model(conf=...) 직접 지정 ===
  conf=0.25 : 원시    1  사슬  0프레임
  conf=0.10 : 원시    3  사슬  0프레임
  conf=0.05 : 원시   15  사슬  3프레임
```

시도했지만 안 된 것
- **임계값 스윕**(첫 시도): 위 표대로 0.02까지 내려도 무변화. 이때 "모델이 정말 공을 못 본다"로 결론냈다면 파일럿을 잘못 종료했을 것이다.
- **윈도우 확장**: 투구가 윈도우 밖에 있나 싶어 `t-3.0s`를 `t-5.0s`, `t-6.0s`로 넓혔다. #144는 원시 감지가 **11건으로 완전히 동일**했다. 윈도우 문제가 아니었다.

해결
`detect_ball_in_frame`에 `conf: float | None = None`을 추가해 모델에 직접 넘긴다. 기본값 `None`이면 인자를 아예 넘기지 않아 기존 데모 경로 동작이 그대로 보존된다.

```python
kwargs = {} if conf is None else {"conf": conf}
results = model(frame, verbose=False, imgsz=imgsz, **kwargs)[0]
```

`src/yolo_detector.py`는 설계 문서상 수정 비범위였으나, 우회하려면 감지 로직을 복제해야 해서 동작 불변인 선택적 인자만 추가했다.

추가로 **추론 해상도**를 바꿨다. 학습 데이터가 1280x720을 640x640으로 눌러 만든 것이라 640 추론은 공이 너무 작고, 1280은 학습 시점 대비 너무 커진다.

```

#144   원시 11/사슬 0   원시 13/사슬 3   원시 11/사슬 0
#217   원시 12/사슬 2   원시 33/사슬 7   원시 15/사슬 7
```

`imgsz=960`, `conf=0.05`로 게이트가 통과했다 — 7/8투구(88%), 사슬 중앙값 7.5프레임, 박스 최대변 중앙값 20.5px. 궤적의 물리적 타당성도 확인했다.

```
#209 싱커     y: 285 289 295 301 310 320 330 342       처음부터 단조 낙하
```

추후 관리
재발 방지 - **임계값을 바꿨는데 결과가 안 변하면 그 코드는 실행되지 않는 것이다.** 파라미터 튜닝 전에 그 파라미터가 실제로 영향을 주는지부터 확인한다. 스윕은 튜닝 도구이자 배선 검사 도구다.
남은 리스크 - 라이브러리 기본값이 우리 코드의 상수를 무력화하는 패턴은 다른 곳에도 있을 수 있다. `iou`, `max_det`, `agnostic_nms` 등 Ultralytics 기본값을 검토하지 않았다.

배운 점
**상수를 정의하는 것과 그 상수가 적용되는 것은 다르다.** `CONF_THRESHOLD = 0.15`는 코드에 있고, 주석까지 달려 있고, TS-013에서 근거를 들어 조정됐다. 전부 무의미했다. 파이프라인 밖의 기본값이 먼저 잘라내고 있었기 때문이다.
**모델이 나빠졌다는 결론에 도달하기 전에 배선을 의심한다.** 에폭 30이 에폭 18보다 나쁘다는 관측은 사실이었지만 원인은 학습이 아니었다. 학습이 진행되며 우리 도메인의 공 신뢰도가 0.25 아래로 밀려났고, 그 아래를 볼 수 없는 코드가 "감지 0건"으로 보고했다. 모델은 내내 공을 보고 있었다.

## TS-019 · 정지 오탐이 사슬 한가운데로 들어왔다 — 같은 구조의 네 번째 재발

날짜: 2026-08-06
영역: ML
심각도: High
상태: 해결됨

증상
TS-017에서 만든 `longest_moving_chain`이 게이트를 7/8로 통과시켰는데, 궤적 좌표를 열어보니 절반이 오염돼 있었다.

```
투구 #53 — 이동사슬 12프레임 (통과로 집계됨)
  f44 (720,357)  f46 (742,292)  f47 (738,276)   <- 진짜 공
  f48 (721,356)  f49 (721,356)  f50 (721,356)   <- 정지 오탐
  f51 (721,356)  f52 (722,356)
  f54 (706,246)  f55 (700,254)  f56 (694,263)   <- 다시 진짜 공
  f57 (687,276)  f59 (674,306)
```

재현 조건
환경: macOS(Apple Silicon), 720p 중계 영상, imgsz 960 / conf 0.05.
재현율: 항상.

원인
표면 - 사슬 필터가 정지 오탐을 못 걸렀다.
근본 - **TS-017의 트림이 사슬의 앞뒤만 보고 있었다.** `max_gap_frames=2` 관용 때문에 f47(공)에서 f49(정지 오탐)로 건너뛸 수 있고 — 두 점 사이 거리 81.8px은 gap 2에서 허용치 120px 이내다 — 정지 구간이 사슬 **한가운데** 박힌다. 앞뒤 트림은 원리적으로 여기 닿지 않는다.

부차 문제 - `chain_members`가 좌표만으로 매칭해, 사슬에 정지 좌표가 한 번 들어가면 그 좌표를 가진 **모든 프레임**이 출력·렌더링에 포함됐다. 실제 사슬보다 표가 길게 보였다.

시도했지만 안 된 것 (두 번 실패했다)
- **간선 최소 이동량 조건**: 정지 감지끼리 간선을 못 만들게 했다. 정지 구간이 길게 이어지는 건 막았지만, 정지 감지 **하나**가 큰 점프로 사슬 끝에 붙는 건 그대로였다. 그 점프는 이동량이 커서 조건을 통과한다.
- **속도 이상치 트림**: 끝점의 프레임당 속도가 주변 중앙값의 3배를 넘으면 자르게 했다. #53(55.8 vs 10대, 비율 5.5)은 잡혔지만 #135(55.8 vs 26.65, 비율 2.09)는 임계 미만이라 그대로 통과했다. 비율을 낮추면 정상적으로 가속하는 공의 끝부분이 잘려나간다.

  이 과정에서 별개 버그도 하나 찾았다. 이상치를 **원 이동거리**로 비교하니 감지가 한 프레임 빠진 구간(gap 2)의 스텝이 2배로 나와, 정상 가속 구간이 이상치로 잘렸다. 프레임당 속도로 정규화해 고쳤다.

해결
사후 필터링을 포기하고 **사슬을 만들기 전에** 정지 후보를 제거했다.

```python
def _drop_static_nodes(nodes, radius_px=3.0, min_repeats=3):
    """여러 프레임에서 사실상 같은 좌표에 나타나는 감지를 버린다."""
```

이게 정지 오탐의 정의다. 90mph 공은 30fps에서 포구 직전까지도 프레임당 3px 이상 움직이므로, 3픽셀 반경 안에 서로 다른 프레임의 감지가 3개 이상 모이면 공이 아니다. 사슬 구성 전에 빼면 앞·중간·뒤·전체 네 경우가 한 번에 사라진다.

간선 최소 이동량 조건과 앞뒤 트림은 다중 방어로 남겨뒀다 — 2회만 감지된 정지 물체는 사전 필터에 안 걸린다.

검증
합성 케이스 7개로 단위 테스트를 먼저 작성해 RED 확인 후 구현했다. 기존 41개 포함 **48개 전부 통과**.
실측 재검증에서 #53의 사슬이 12 → 9프레임으로 줄었다 (가짜 3프레임 제거). 게이트는 7/8(88%) 유지, 사슬 중앙값 7.0프레임, 박스 최대변 중앙값 21px.

추후 관리
재발 방지 - **거르려는 대상을 정의로 붙잡는다.** "정지 물체 = 여러 프레임에서 같은 좌표"는 정의이고, 그걸 직접 검사하면 발현 형태와 무관하게 잡힌다. "매끄러운 최장 구간"이나 "전체 변위"는 정의가 아니라 증상의 대리 지표였고, 그래서 매번 다른 형태로 빠져나갔다.
남은 리스크 - 2회 이하로만 감지되는 정지 물체는 사전 필터를 통과한다. 실측에서 문제되지 않았지만 다른 경기 영상에서는 확인이 필요하다.

배운 점
**같은 구조가 네 번 반복됐다.** TS-013(글러브) · TS-014(글러브) · TS-017(정지 오탐, 앞뒤) · TS-019(정지 오탐, 중간). 전부 "매끄럽고 오래 지속되는 엉뚱한 물체가, 짧고 끊기는 진짜 공을 이긴다"는 하나의 구조다. 필터를 고칠 때마다 그 구조를 다시 만족하는 형태가 등장했다.
**증상을 막는 필터는 증상만큼 필요하다.** 앞을 막으면 중간으로, 중간을 막으면 끝으로 온다. 세 번째 패치를 짜고 있다면 대상을 잘못 정의한 것이다. 네 번째에 와서야 정의로 돌아갔고, 그러자 한 함수로 끝났다.
**게이트 통과가 검증의 끝이 아니다.** 7/8 통과 후 좌표를 안 열어봤다면 오염된 궤적으로 Phase 4를 돌렸을 것이다. 통과했을 때야말로 결과를 의심해야 한다 — 실패는 알아서 눈에 띄지만 성공은 그렇지 않다.

표면 - `PITCH_GROUP_MAP`에 `KC`(너클커브)와 `FO`(포크볼) 키가 없어 `pitch_type_to_group`이 `None`을 돌려주고, `build_dataset_for_game`이 해당 샘플을 조용히 제외한다.

근본 - **같은 개념에 대한 매핑표가 두 벌이었고 한 벌에만 항목이 있었다.** 같은 파일 안에 `OCR_PITCH_NAME_GROUP_MAP`에는 `"Knuckle Curve": "BREAKING"`이 처음부터 있었다. OCR 경로만 쓰는 동안에는 그쪽만 참조되므로 너클커브가 정상 처리됐고, `PITCH_GROUP_MAP`의 구멍은 그룹 비율 대조(진단) 경로에서만 쓰여 눈에 띄지 않았다. 라벨 소스를 바꾸는 순간 참조되는 표가 바뀌면서 구멍이 드러나는 구조였다.

시도했지만 안 된 것
없다. 조사 단계에서 잡혀 디버깅이 필요 없었다. 다만 **이 조사를 안 했다면** 4경기 데이터셋을 만든 뒤 "BREAKING 표본이 예상보다 적다"는 형태로 나타났을 것이고, 원인을 매핑표에서 찾기까지 한참 걸렸을 것이다.

해결
`PITCH_GROUP_MAP`에 두 코드를 추가하고, 실측 근거를 주석에 남겼다.

```python
"SL": "BREAKING", "CU": "BREAKING", "ST": "BREAKING", "KC": "BREAKING",
"CH": "OFFSPEED", "FS": "OFFSPEED", "FO": "OFFSPEED",
```

검증
단위 테스트 2개를 먼저 작성해 RED 확인(`assert None == 'BREAKING'`) 후 구현했다. 전체 65개 통과.
실측 재조회에서 813026 경기의 미매핑 비율이 3.2% → 0%가 됐다 (222구 = 101 + 56 + 65로 전건 매핑).

추후 관리
재발 방지 - 매핑표를 늘릴 때는 **실제 데이터의 코드 분포를 먼저 세고**, 미매핑 항목을 0으로 만든 뒤 진행한다. 표를 눈으로 읽어 빠진 걸 찾는 방식은 이미 한 번 실패했다(ST는 TS 이전에 같은 이유로 뒤늦게 추가됐다).
남은 리스크 - `SV`(슬러브), `FA`(일반 패스트볼), `EP`(이퓨스) 등은 후보 7경기에 없어 추가하지 않았다. 다른 경기를 넣으면 미매핑 카운트를 다시 확인해야 한다.

배운 점
**조용한 탈락은 에러보다 비싸다.** 던져진 예외는 즉시 멈추지만, `None`을 돌려주고 건너뛰는 코드는 정상 동작처럼 보이면서 데이터를 깎는다. TS-018(`CONF_THRESHOLD`가 한 번도 작동 안 함)과 같은 부류다.
**같은 개념의 매핑표를 두 벌 두면 반드시 어긋난다.** 두 표가 나란히 있는데 한쪽에만 "Knuckle Curve"가 있었다. 코드 리뷰로는 안 잡힌다 — 두 표가 서로를 참조하지 않기 때문이다. 데이터로 대조하는 것만이 방법이었다.

## TS-021 · "사슬 확보율 93.3%"가 타구 비행까지 세고 있었다

날짜: 2026-08-06
영역: ML
심각도: Medium
상태: 해결됨

증상
투구별 클립에서 릴리스 위치를 찾기 위해 클립 앞 12초를 전부 스캔하고, 프레임별 감지 후보에서 `longest_moving_chain`으로 사슬을 뽑아 시작 시각 분포를 쟀다. 결과는 좋아 보였다.

```
사슬 확보 56/60 (93.3%)
FASTBALL  확보 17/20 (85.0%)  중앙값  3.03s  범위  2.92~ 8.13s
BREAKING  확보 19/20 (95.0%)  중앙값  3.22s  범위  2.92~ 6.10s
OFFSPEED  확보 20/20 (100.0%) 중앙값  3.24s  범위  2.95~ 6.10s
```

중앙값 3.0~3.2초에 몰려 있는데 범위 상단이 6~8초까지 벌어진다. 6.10초에서 시작하는 "투구"는 있을 수 없다 — 클립 프리롤이 고정이라면 릴리스는 3초 부근이다.

재현 조건
`--max-scan-sec 12.0`으로 클립 전체를 스캔할 때. 윈도우를 2초 이내로 좁히면 나타나지 않는다.

원인
표면 - 사슬 시작 시각의 꼬리가 6~8초까지 늘어졌다.

근본 - **확보율이 "투구 사슬을 찾았는가"가 아니라 "움직이는 사슬이 하나라도 있는가"를 재고 있었다.** 타구는 공이고 움직이므로 `longest_moving_chain`의 두 조건(연속성·운동성)을 완벽히 만족한다. 안타가 나온 클립에서는 타구 비행 구간이 투구 구간보다 길어 최장 사슬로 선택된다. 지표 이름은 "사슬 확보율"이었고 실제로 그걸 정확히 쟀지만, 알고 싶었던 건 "투구 궤적 확보율"이었다.

시도했지만 안 된 것
- **가설: 윈도우를 좁히면 타구 후보가 배제되므로 확보율이 오른다.** 틀렸다. 같은 60클립을 2.8~4.2초로 재스캔하니 93.3% → **90.0%**로 내려갔다. 좁힌 윈도우에서는 타구가 후보에서 빠지는 동시에, 원래 타구로 집계되던 클립 중 일부는 투구 사슬도 3점을 못 채워 탈락했다. 즉 93.3%는 오르내릴 수치가 아니라 **처음부터 다른 것을 세고 있던 수치**였고, 90.0%가 실제 값이다.

해결
스캔 윈도우를 클립 시작 기준 2.8~4.2초로 고정했다. 근거는 같은 실측의 다른 통계다 — 사슬 시작 시각의 5퍼센타일이 전 그룹 2.92초로 하한이 날카롭다(프리롤 고정). 그룹별 중앙값도 3.03/3.22/3.24초로 0.21초 안에 모여 구종별 위상 차이가 없다.

2.5~4.5초와 확보율이 54/60으로 동일하고, 사슬 점수 중앙값은 좁은 쪽이 낫고(OFFSPEED 10 대 8), 감지 프레임이 30% 적다.

검증
같은 60클립을 두 윈도우로 재스캔해 그룹별 확보율과 사슬 점수를 대조했다. 최종값 FASTBALL 85% / BREAKING 90% / OFFSPEED 95%, 전체 90.0%.
비교 기준: OCR 경로의 전체 확보율은 68%였다.

추후 관리
재발 방지 - 확보율 같은 비율 지표는 **분자와 분모가 각각 무엇을 세는지** 적어두고, 분자가 원하는 대상만 세는지 별도로 확인한다. 이번에는 "범위 상단 8.13초"라는 물리적으로 불가능한 값이 단서였다 — 요약 통계에 중앙값만 찍었다면 못 봤다.
남은 리스크 - 2.8~4.2초 밖에 릴리스가 오는 클립은 통째로 놓친다. 실측 60개에서는 하한 2.92초로 여유가 있었으나, 다른 시즌·다른 중계사 클립은 프리롤이 다를 수 있어 경기를 추가할 때 재확인이 필요하다.

배운 점
**지표가 통과했다고 측정이 맞은 게 아니다.** TS-017에서 게이트 기준의 분모를 잘못 잡았고, TS-019에서 게이트를 통과한 사슬이 오염돼 있었다. 이번엔 게이트도 사슬도 정상인데 **지표가 다른 대상을 셌다.** 셋 다 "숫자가 좋아 보였다"에서 출발한다.
**분포의 꼬리를 본 게 유일한 단서였다.** 중앙값 3.03초만 보면 완벽한 결과다. 범위를 같이 찍었기 때문에 8.13초가 눈에 들어왔다.
**가설이 틀렸을 때 수치가 왜 움직였는지까지 설명해야 한다.** "좁히면 오른다"가 틀렸을 때 90.0%를 그냥 채택했다면, 3.3%p 하락을 손실로 오해했을 것이다. 실제로는 잘못 세던 것을 빼낸 것이다.

## TS-022 · venv의 urllib만 SSL 인증서 검증에 실패 — curl과 requests는 정상

날짜: 2026-08-06
영역: Build
심각도: Low
상태: 해결됨

증상
MLB StatsAPI 생존 확인 스크립트가 첫 요청에서 죽었다.

```
  File ".../urllib/request.py", line 1322, in do_open
    raise URLError(err)
urllib.error.URLError: <urlopen error [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed:
unable to get local issuer certificate (_ssl.c:1032)>
```

에러만 보면 네트워크 차단이나 방화벽을 의심하게 된다. 실제로는 같은 URL이 다른 도구로는 정상이었다.

```
$ curl -s -o /dev/null -w "%{http_code}\n" "https://statsapi.mlb.com/api/v1.1/game/775294/feed/live"
200
$ venv/bin/python3 -c "import certifi, requests; print(certifi.where())"
/Users/tina/Project/baseball-pitch-predictor/venv/lib/python3.13/site-packages/certifi/cacert.pem
```

재현 조건
환경: macOS, python.org 배포판 Python 3.13 기반 venv. 표준 라이브러리 `urllib.request`로 HTTPS 요청 시 항상.

원인
표면 - 인증서 검증 실패.
근본 - **`urllib`은 OpenSSL의 기본 신뢰 저장소를 보고, `requests`는 `certifi` 번들을 본다.** macOS의 python.org 배포판은 시스템 키체인을 OpenSSL 신뢰 저장소로 연결하지 않는다(그래서 `Install Certificates.command`를 따로 실행하게 돼 있다). 이 venv에서는 그 단계를 거치지 않았고, `certifi`는 `requests` 의존성으로 이미 설치돼 있었다. `curl`은 아예 별개로 시스템 저장소를 쓰므로 셋의 결과가 갈렸다.

시도했지만 안 된 것
없다. `curl`과 `certifi` 확인 한 번으로 갈렸다. 다만 **`curl`로 먼저 확인하지 않았다면** 네트워크 차단으로 오진하고 프록시 설정을 뒤졌을 가능성이 크다.

해결
일회성 프로브를 `urllib` 대신 `requests`로 바꿨다. 리포에 남는 코드(`scripts/calibrate_clip_window.py`, `scripts/build_pitch_group_clips_dataset.py`)도 전부 `requests`를 쓴다.

```python
# 안 됨
import urllib.request
data = json.load(urllib.request.urlopen(url))

# 됨 — certifi 번들을 사용
import requests
data = requests.get(url, headers={"User-Agent": UA}, timeout=60).json()
```

`requests`는 이미 의존성에 있어 추가 설치가 없었다.

검증
전환 후 StatsAPI 조회 280/280 성공, Savant 클립 페이지·mp4 다운로드도 정상(4,989,652바이트, `video/mp4`).

추후 관리
재발 방지 - 이 프로젝트에서 HTTP 요청은 `requests`로 통일한다. 표준 라이브러리라는 이유로 `urllib`을 쓰지 않는다.
남은 리스크 - venv 자체의 신뢰 저장소는 고치지 않았다. `urllib`을 쓰는 서드파티 라이브러리를 새로 넣으면 같은 증상이 날 수 있다. 근본 해결은 `/Applications/Python 3.13/Install Certificates.command` 실행이다.

배운 점
**"네트워크가 안 된다"는 결론은 도구를 바꿔 확인하기 전까지 성립하지 않는다.** 에러 메시지가 SSL을 가리켰지만 원인은 그 프로세스의 인증서 경로였다. `curl` 한 줄이 범위를 절반으로 줄였다.

## TS-023 · 특징을 더하니 전체 정확도는 올랐는데 겨냥한 클래스는 나빠졌다

날짜: 2026-08-07
영역: ML
심각도: Medium
상태: 해결됨

증상

OFFSPEED(체인지업·스플리터) f1 0.14를 올리려고 궤적 좌표에서 특징 7개를 새로 뽑아 붙였다. 결과는 겉보기에 성공이었다.

```
[기준(7)]   정확도 0.587 (기준선 대비 +0.103)  중요도비  3.75
            OFFSPEED  p=0.24 r=0.10 f1=0.14
[+시간(10)] 정확도 0.600 (기준선 대비 +0.117)  중요도비  7.31
            OFFSPEED  p=0.09 r=0.05 f1=0.06
[+기하(11)] 정확도 0.673 (기준선 대비 +0.190)  중요도비 24.31
            OFFSPEED  p=0.14 r=0.07 f1=0.10
[전체(14)]  정확도 0.673 (기준선 대비 +0.190)  중요도비 21.96
            OFFSPEED  p=0.10 r=0.05 f1=0.07
```

정확도 +8.6%p, 중요도비 3.75 → 24.31. 판정 지표 세 개 중 둘이 큰 폭으로 좋아졌다. 그런데 **이 작업의 목적이었던 OFFSPEED f1은 0.14에서 0.07로 반토막 났다.**

재현 조건

클래스 사전확률이 크게 불균형한 상태(FASTBALL 48% / BREAKING 38% / OFFSPEED 13%)에서 소수 클래스를 겨냥해 특징을 추가할 때. 홀드아웃 300개 중 OFFSPEED는 40개라, 40개를 전부 틀려도 전체 정확도는 0.87배까지만 떨어진다.

원인

표면 - 특징을 늘렸는데 목표 클래스의 f1이 내려갔다.

근본 - **추가한 특징이 FASTBALL·BREAKING의 분리에만 기여했고, 그 결과 모델이 OFFSPEED를 더 확실하게 버리게 됐다.** 임계값과 무관한 one-vs-rest AUC로 재면 이게 그대로 보인다.

```
                기준(7)  ->  전체(14)
FASTBALL AUC     0.792   ->   0.851   (+0.059)
BREAKING AUC     0.725   ->   0.819   (+0.094)
OFFSPEED AUC     0.641   ->   0.648   (+0.007)   <- 사실상 제자리
```

혼동행렬에서는 OFFSPEED 40개 중 2개만 맞고 나머지가 FASTBALL 19 / BREAKING 19로 갈린다. 다른 두 클래스의 경계가 선명해질수록, 사전확률 13%짜리 클래스를 argmax로 뽑을 이유는 오히려 줄어든다.

물리적으로는 예상된 결과였다. 체인지업·스플리터를 패스트볼과 가르는 것은 **속도**인데, 픽셀 좌표만으로는 절대 속도를 복원할 수 없다. 새로 넣은 7개는 전부 좌표에서 파생된 것이라 OFFSPEED에 넣을 정보가 애초에 없었다.

시도했지만 안 된 것

- **가설: 시간 계열 특징(`frame_span`, `end_frame`, `speed_ratio_late_early`)이 속도 대리 지표가 되어 OFFSPEED를 가른다.** 틀렸다. `+시간(10)`은 정확도 0.587 → 0.600으로 거의 안 움직였고 OFFSPEED f1은 0.14 → 0.06으로 내려갔다. 정확도 상승분은 전부 기하 계열 4개, 그중 `vertical_accel_px` 하나(중요도 0.42)가 끌었다.
- **가설: 결정 규칙만 고치면(클래스 가중치) 목표를 통과한다.** 수치상으로는 통과하지만 새 정보가 아니다. 가중치를 올리면 f1이 오르는 대신 전체 정확도가 정확히 원위치한다 — 같은 ROC 곡선 위에서 동작점만 옮긴 것이고, AUC가 안 움직였다는 사실과 일치한다.

```
OFFSPEED 가중치  1: 전체정확도 0.673  p=0.14 r=0.07 f1=0.10
OFFSPEED 가중치  3: 전체정확도 0.607  p=0.21 r=0.35 f1=0.26
OFFSPEED 가중치  8: 전체정확도 0.587  p=0.25 r=0.57 f1=0.35
OFFSPEED 가중치 12: 전체정확도 0.597  p=0.27 r=0.65 f1=0.38
```

해결

두 가지를 갈라 처리했다.

1. **정확도 개선은 진짜다** — 경기 단위 leave-one-game-out 4폴드로 재확인했다. 홀드아웃 1경기의 우연이 아니다.

```
기준(7)    정확도 0.613 (경기별 0.66 / 0.59 / 0.62 / 0.59)  기준선 대비 +0.165
+기하(11)  정확도 0.661 (경기별 0.66 / 0.63 / 0.68 / 0.67)  기준선 대비 +0.212
전체(14)   정확도 0.659 (경기별 0.66 / 0.64 / 0.65 / 0.67)  기준선 대비 +0.210
```

2. **OFFSPEED는 좌표로 안 된다는 것이 확정됐다** — 그래서 박스 크기(공이 카메라에 가까워지는 속도)로 넘어간다. 캐시가 `(frame_idx, [cx, cy, conf])`만 담고 mp4는 처리 후 지우므로 재수집이 필요하다. 재수집을 두 번 하지 않도록 `extract_trajectory_candidates`가 `(x, y, conf, w, h)`를 남기게 먼저 고치고, v1 캐시 히트로 건너뛰어지지 않도록 `clip_trajectory_cache_v2/`로 분리했다.

검증

- 특징 확장 전후로 기존 7개 컬럼이 1030행 전부 비트 단위 동일 (`np.allclose(equal_nan=True)`) — 신규 특징이 기존 계산을 건드리지 않았다
- 재수집 전 클립 1개 스모크 테스트에서 박스 크기가 실제로 잡히고(`(683.0, 328.0, 0.204, 13.0, 19.0)`) 좌표·신뢰도가 v1 캐시와 정확히 일치 — 재수집이 같은 궤적을 재현한다
- 전체 테스트 79개 통과

추후 관리

재발 방지 - **소수 클래스를 겨냥한 작업은 전체 정확도로 판정하지 않는다.** 판정 지표에 대상 클래스의 one-vs-rest AUC를 넣는다. AUC는 임계값·클래스 가중치와 무관해서 "정보가 늘었나"와 "동작점을 옮겼나"를 갈라준다. f1만 보면 둘이 섞인다.

남은 리스크 - `vertical_accel_px` 하나가 중요도 0.42로 지배적이다. 4경기 4폴드에서 일관되긴 하나, 중계 카메라가 다른 시즌·다른 구장에서도 유지되는지는 확인 안 됐다.

배운 점

**"지표 셋을 함께 본다"는 규칙만으로는 부족하다. 그 셋이 목표와 같은 것을 재는지도 확인해야 한다.** 이번에 정확도와 중요도비는 정직하게 개선을 가리켰다. 다만 그 개선이 다른 클래스에서 왔을 뿐이다. TS-021에서 "사슬 확보율"이 타구 비행을 세고 있었던 것과 같은 구조다 — 지표는 자기가 정의한 것을 정확히 쟀고, 그게 알고 싶던 것이 아니었다.

## TS-024 · 속도 대리 지표의 물리적 전제가 이 카메라에서 성립하지 않았다

날짜: 2026-08-07
영역: ML
심각도: Medium
상태: 해결됨

증상

TS-023에서 "픽셀 좌표로는 절대 속도를 복원할 수 없으니 박스 크기(공이 카메라에 가까워지는 속도)가 유일한 속도 대리 지표"라고 결론짓고, 1193개 클립을 전부 재다운로드·재감지했다(약 100분). 박스 특징 2개를 붙인 결과는 이렇다.

```
[기준(7)]     홀드아웃 0.590  LOGO 0.614  OFFSPEED LOGO AUC 0.710
[+기하(11)]   홀드아웃 0.670  LOGO 0.659  OFFSPEED LOGO AUC 0.730
[좌표전체(14)] 홀드아웃 0.657  LOGO 0.654  OFFSPEED LOGO AUC 0.724
[+박스(16)]   홀드아웃 0.700  LOGO 0.665  OFFSPEED LOGO AUC 0.728
```

전체 정확도는 홀드아웃 0.700으로 최고를 찍었다. 그런데 **OFFSPEED AUC는 0.710 → 0.728, +0.018로 사전에 정한 기준 0.03에 못 미쳤다.** 박스 특징을 넣기 전인 `+기하(11)`의 0.730보다도 낮다. FASTBALL·BREAKING AUC도 0.861 → 0.850, 0.827 → 0.822로 미세하게 내려갔다. 정확도만 오르고 정보량은 늘지 않은 것이다.

재현 조건

중견수 뒤에서 홈플레이트를 향해 잡는 표준 중계 카메라. Baseball Savant 투구별 클립은 전부 이 앵글이다.

원인

표면 - 박스 크기 변화율이 OFFSPEED를 가르지 못한다.

근본 - **"공이 카메라에 가까워진다"는 전제가 이 앵글에서 틀렸다.** 카메라가 투수 뒤에 있으므로 공은 던져지는 순간부터 카메라로부터 **멀어진다**. 실측된 `box_growth_per_frame`은 평균 −0.148 px/frame(표준편차 0.312)로 음수다.

크기 문제도 겹친다. 궤적 하나가 약 10프레임이므로 총 변화량은 1.5px 남짓인데, 박스 자체가 평균 17.0px(표준편차 1.8)이고 YOLO 박스 좌표는 정수로 양자화된다. **재려는 신호가 측정 단위보다 작다.**

```
release_box_size        평균 17.03  표준편차 1.81
box_growth_per_frame    평균 -0.15  표준편차 0.31   <- 10프레임 누적 1.5px
```

시도했지만 안 된 것

- **가설: 끝점 차분이 양자화에 취약하니 최소제곱 기울기로 바꾸면 신호가 산다.** 실제로 `_box_growth_per_frame`을 끝점 차분에서 전체 점 최소제곱 적합으로 구현했다. 기울기 추정은 안정됐지만 AUC는 안 움직였다. 추정 방법의 문제가 아니라 신호 자체가 없었다.
- **조기 신호를 무시하고 완주했다.** 재수집이 69개 쌓였을 때 `box_growth_per_frame` 단변량 OFFSPEED AUC가 0.540(무신호)이었다. 그 시점에 중단할 수 있었으나 부분 표본이라 판단을 유보하고 끝까지 돌렸다. 최종 수치는 조기 신호와 일치했다.

해결

3분류를 접고 **FASTBALL vs BREAKING 2분류로 문제를 재정의했다.**

```
경기 단위 leave-one-game-out (n=857)
 game_pk    n   정확도  기준선   AUC
  775294  211   0.735  0.592  0.857
  813024  247   0.794  0.425  0.901
  813026  139   0.827  0.597  0.912
  813027  260   0.777  0.558  0.852
평균          0.783  0.543  (+0.240)   평균 AUC 0.881
```

3분류 LOGO 0.665보다 높고 경기별 편차도 작다. OFFSPEED를 억지로 끼워 셋 다 흐리게 만드는 것보다, **중계 영상으로 되는 것과 안 되는 것의 경계를 명시하는 쪽**이 정직한 결론이다.

박스 특징 2개는 코드에서 빼지 않았다. 전체 정확도 기준으로는 최고 집합이고(홀드아웃 0.700), `box_growth_per_frame`은 중요도 3위(0.054)다. OFFSPEED에 정보를 안 넣었을 뿐 무용하지는 않다.

검증

- 재수집 다운로드 실패 0건, 1193투구 중 궤적 1029개(86.3%) — v1의 1030개와 1개 차이. 재수집이 같은 궤적을 재현했다
- 박스 컬럼이 궤적 확보 1029행 전부에 0이 아닌 값으로 채워짐 (미수집 상태의 0.0 폴백과 구분됨)
- 전체 테스트 84개 통과

추후 관리

재발 방지 - **대리 지표를 도입할 때는 그 물리적 전제가 이 데이터에서 성립하는지 먼저 한 클립으로 잰다.** 이번 건은 클립 하나에서 박스 크기 시계열만 찍어봤어도 부호가 음수인 것을 100분 전에 알 수 있었다.

남은 리스크 - 2분류로 좁혔을 뿐 OFFSPEED 문제 자체는 미해결이다. 절대 속도가 필요하면 중계 영상이 아니라 트래킹 데이터(Statcast `release_speed`)를 라벨이 아닌 입력으로 쓰는 경로를 따로 검토해야 한다. 그 경우 "영상만으로 예측"이라는 전제가 깨진다.

배운 점

**대리 지표는 "무엇을 대신하는가"보다 "그 대신이 이 측정 조건에서 성립하는가"가 먼저다.** 박스 크기가 거리를 반영한다는 것 자체는 맞다. 다만 이 카메라에서는 부호가 반대고 변화량이 측정 해상도 아래였다. TS-023이 "지표가 목표와 다른 것을 쟀다"였다면, 이번은 "지표가 잴 수 있는 크기가 아니었다"다.

## TS-025 · 클립에서 되던 분류기가 전체 중계 영상에서 무신호였다

날짜: 2026-08-07
영역: ML
심각도: High
상태: 부분 해결 (판정률은 고침, 정확도는 미해결)

증상

2분류 모델을 앱에 붙였다. Savant 투구별 클립에서는 LOGO 4폴드 정확도 0.783 / 확보율
86.3%였다. 같은 모델을 전체 중계 영상(데모 경기 775300, 학습 4경기에 없는 경기)에서
재니 이렇게 나왔다.

```
창 3.0~1.6s  판정률 30.2% (16/53)  정확도 43.8%
창 2.6~1.2s  판정률 30.2%          정확도 50.0%
창 2.2~0.8s  판정률 35.8% (19/53)  정확도 47.4%
창 1.8~0.4s  판정률 32.1%          정확도 58.8%
창 1.4~0.0s  판정률 26.4%          정확도 28.6%
```

최빈값 기준선이 0.547(BREAKING 29 / FASTBALL 24)이다. 최고값 58.8%는 n=17이라
기준선과 구분되지 않는다. 확보율은 실험실의 3분의 1이다.

재현 조건

학습 데이터를 고정 규격으로 잘린 클립에서 만들고, 배포는 잘리지 않은 원본 영상에서
할 때. Savant 클립은 투구가 항상 2.8~4.2초에 오도록 잘려 있어서, 그 규격이 모델의
암묵적 전제가 됐다.

원인

**문제가 하나가 아니라 둘이었고, 처음에는 그게 안 보였다.**

표면 - 판정률이 낮고 정확도가 기준선 수준이다.

근본 (1) **고정 창을 쓸 수 없다.** 넓은 창(t-8 ~ t+2초)으로 공이 실제로 어디 있는지
찍어보니 오버레이 시각으로부터의 간격이 흩어져 있었다.

```
공 시작 오프셋: 0.41 / 0.63 / 1.44 / 1.51 / 1.64 / 2.14 / 3.71 / 7.40초
넓은 창 확보율: 8/10 (80%)   <- 공은 잘 잡힌다
```

폭 1.4초짜리 창을 어디에 놓아도 절반 이상을 놓친다. 창 위치 5개에서 판정률이 30%
근처로 평평했던 것이 이 신호였다 — 위치가 문제라면 어딘가에서 봉우리가 생겨야 한다.

근본 (2) **도메인 격차.** (1)을 고쳐 판정률을 73.6%까지 올렸는데도 정확도는 41.0%
(16/39)로 오히려 내려갔다. 기준선 아래이고 동전 던지기와 구분되지 않는다.

시도했지만 안 된 것

- **가설: 창 위치만 잘못 잡았다.** 절반만 맞았다. 창을 넓히니 판정률은 32% → 74%로
  올랐지만 정확도는 안 따라왔다. 창은 "공을 찾는 문제"였고 정확도는 별개였다.
- **가설: 영상 규격이 학습 클립과 다르다.** 틀렸다. 1280x720 / 59.94fps로 완전히 동일하다.
- **가설: 넓은 창이 포수의 송구를 잡아서 수직 부호가 뒤집힌다.** 틀렸다. 학습 데이터
  자체에 위로 가는 궤적이 39.1%(402/1029) 있다. 방향으로는 갈리지 않는다.
- **초기 판정 착오**: 41%를 "체계적으로 반대로 맞힌다"고 읽었다. n=39에서 16/39는
  동전 던지기와 통계적으로 구분되지 않는다(p≈0.19). "역상관"이 아니라 "무신호"다.
  같은 이유로 그 전의 58.8%(n=17)도 신호가 아니었다.

해결

**(1)은 고쳤다.** 넓은 창(t-4.0 ~ t+0.5초)으로 찾고, 사슬을 찾은 뒤 프레임 인덱스를
평행이동해 `end_frame`을 학습 중앙값 21에 맞춘다.

프레임 인덱스의 절대값에 의존하는 특징은 `end_frame` 하나뿐이다 — `frame_span`, 속도비,
수직가속(2차 계수), 박스 기울기는 전부 평행이동 불변이다. 테스트로 확인했다.
이 처리로 `end_frame`은 앱에서 상수가 되어 판별력(중요도 0.042)을 잃는다. 앱에는
신뢰할 창 원점이 없어 애초에 정보가 없었으므로, 학습 중앙값이 가장 덜 해로운 대입값이다.

**(2)는 미해결이다.** 기능은 남기되 앱 UI에 "실험적" 배지와 실측 수치를 함께 띄운다.
기준선 수준 숫자를 성능처럼 보여주지 않기 위해서다.

검증

- **배선 버그가 아니다.** 캐시된 학습 궤적을 새 추론 경로(넓은 창 + 재색인)로 통과시키니
  정확도 0.942(245/260)가 나왔다. 특징 계산이나 재색인이 깨졌다면 이 값도 같이 무너진다.
  (이 0.942는 학습셋 정확도다 — 모델이 4경기 전부로 학습돼 홀드아웃이 아니다.
  일반화 성능이 아니라 "경로가 살아 있는가"만 답한다.)
- OCR 정답 라벨 매핑 확인: 65개 중 53개가 2분류에 해당, 미판독 9 / OFFSPEED 3.
  매핑 누락 없음
- 전체 테스트 95개 통과
- 창 진단 결과는 `output/pitch_type_cv/app_window_diagnosis.json`에 남겼다

추후 관리

재발 방지 - **학습 데이터를 균일 규격으로 자를 때, 그 규격이 배포에서도 성립하는지
먼저 확인한다.** 클립의 고정 오프셋은 데이터를 깔끔하게 만들지만 모델의 암묵적 전제가
된다. 이번에는 `end_frame`이 그 전제를 그대로 담고 있었다(학습 21±4, 앱에서는 의미 없음).

남은 리스크 - 넓은 창은 사슬 알고리즘이 "가장 긴 움직임"을 고를 뿐 그게 투구라는 보장이
없다. 리플레이·컷 전환·다른 앵글이 창 안에 들어온다. (2)를 풀려면 "이 사슬이 투구인가"를
판별하는 게이트가 따로 필요하다. 오프셋 7.40초짜리 사례는 직전 투구나 리플레이일 가능성이
높다.

배운 점

> **후속 (2026-08-10)**: 여기서 "도메인 격차"로 결론지은 (2)의 진짜 원인은 도메인이 아니라
> **프레임 샘플링 설정 불일치**였다. 학습은 매 2번째 프레임, 추론은 모든 프레임을 썼다.
> 그 한 줄을 맞추자 앱 정확도가 0.410 → 0.767로 올라 클립 단위 검증(0.783)과 같아졌다.
> 상세는 TS-028. 이 항목의 (1) 창 진단과 측정 절차는 그대로 유효하다.

**하나의 증상 뒤에 문제가 둘 있으면, 첫 번째를 고쳐도 숫자가 안 움직여서 고친 줄 모른다.**
판정률과 정확도를 따로 보지 않았다면 "넓은 창도 실패"로 결론 내고 되돌렸을 것이다.
실제로는 창 문제가 확실히 고쳐졌고(32% → 74%) 남은 것이 다른 문제였다.

그리고 이건 TS-014와 같은 범주다. 그때는 감지기가 제품 사진으로 학습돼 중계 영상에서
감지율 3%였고, 이번은 분류기가 균일하게 잘린 클립으로 학습돼 원본 영상에서 무신호다.
**학습 도메인과 배포 도메인이 다르면 실험실 수치는 약속이 아니다.**

> **정정 (2026-08-10)**: 이 마지막 문단의 진단은 틀렸다. 도메인 문제가 아니라 전처리
> 설정 불일치였다 (TS-028). 교훈 자체는 남기되, "도메인이 다르다"고 결론짓기 전에
> **양쪽 파이프라인의 설정이 같은지부터 확인해야 한다**는 것이 이번의 진짜 배움이다.

## TS-026 · 영상 서버가 Range를 지원한다고 광고만 하고 처리하지 않았다

날짜: 2026-08-09
영역: Infra
심각도: High
상태: 해결됨

증상

데모 영상(1.1GB, 2시간 17분)이 재생 버튼을 눌러도 `0:00`에서 멈춘 채 진행되지 않았다.
콘솔에 영상 관련 오류는 없었고, `<video>` 요소는 `readyState 0`(메타데이터 없음),
`networkState 2`(다운로드 중)에 머물렀다.

재현 조건

`streamlit_app/app.py`의 `_get_video_server`가 띄우는 로컬 HTTP 서버로 큰 영상을 재생할 때.

원인

표면 - 브라우저가 영상을 받지 못한다.

근본 - **핸들러가 `Accept-Ranges: bytes` 헤더를 보내면서 Range 요청은 처리하지 않았다.**
`http.server.SimpleHTTPRequestHandler`에는 Range 구현이 없다. 격리 테스트로 확인했다.

```
요청:  Range: bytes=0-1023        (1KB만 요청)
응답:  HTTP/1.0 200 OK            (206 Partial Content가 아님)
       Content-Length: 5000000
실제:  5,000,000 바이트 전부 수신
```

헤더가 없었으면 브라우저가 순차 다운로드로 폴백했을 텐데, **지원한다고 광고하니
되지도 않는 Range 기반 재생을 시도**했다. 1.1GB를 다 받기 전에는 재생도 탐색도 못 한다.

여기에 두 가지가 더 겹쳐 있었다.

- `socketserver.TCPServer`는 단일 스레드다. 브라우저는 영상에 커넥션을 여럿 여는데
  하나가 붙잡고 있는 동안 나머지가 전부 대기한다.
- `protocol_version`이 기본값 `HTTP/1.0`이었다. Chrome 미디어 스택은 바이트 레인지
  탐색에 지속 연결을 요구한다. `fetch()`로는 206과 바이트가 정상적으로 오는데
  `<video>`만 `readyState 0`에 머무는 상태가 이것 때문이었다.

시도했지만 안 된 것

- **가설: 영상 파일의 moov atom이 뒤에 있어 메타데이터를 못 읽는다.** 틀렸다.
  박스를 직접 파싱하니 `ftyp(0) → moov(32, 12.7MB) → free → mdat(1.1GB)`로
  faststart가 적용돼 있었다. 박스 크기 합도 파일 크기와 정확히 일치했다.
- **가설: 파일이 너무 크다.** 틀렸다. 같은 폴더의 434MB 영상도 동일하게 실패했다.
- **가설: 코덱 미지원.** 틀렸다. `canPlayType`이 H.264 baseline/high 모두 `probably`.

해결

핸들러에 Range 처리를 직접 구현하고, `ThreadingTCPServer`로 바꾸고,
`protocol_version = "HTTP/1.1"`로 올렸다. 교차 출처에서 `Content-Range`가 JS에
노출되도록 `Access-Control-Expose-Headers`도 추가했다.

검증

격리 테스트 5개 통과 — 중간 구간(206 + 정확한 바이트 수), 열린 구간, Range 없음(200),
범위 초과(416), **받은 바이트가 원본과 일치**. 실제 앱의 1.1GB 영상에서
`Content-Range: bytes 1000-1999/1185971584`, 처리량 915 MB/s. 사용자 브라우저에서 재생 확인.

추후 관리

남은 리스크 - 브라우저가 레인지 요청을 중간에 끊으면 `BrokenPipeError` 트레이스백이
로그에 찍힌다. 영상 스트리밍에서는 정상 동작이지만 로그가 지저분해진다.

배운 점

**헤더는 약속이다. 구현하지 않은 기능을 광고하면 클라이언트가 그 약속을 믿고 동작을 바꾼다.**
이 경우 헤더를 아예 안 보내는 쪽이 오작동보다 나았다.

## TS-027 · 재실행 폭주가 버튼 클릭을 삼켰다

날짜: 2026-08-09
영역: FE
심각도: High
상태: 해결됨

증상

`다음 투구` / `이전 투구` 버튼을 눌러도 아무 반응이 없었다. 투구 인덱스도 슬라이더도
그대로였다. 오류는 없었다.

재현 조건

영상 재생 중. 정지 상태에서는 간헐적으로 동작했다.

원인

표면 - 버튼이 안 먹는다.

근본 - **`st.button()`이 `True`를 돌려준 적이 한 번도 없었다.** 디버그 출력으로 확인했다.
스크립트 여러 곳의 폴링 루프가 `time.sleep(); st.rerun()`을 계속 걸어 초당 두 번꼴로
재실행되고 있었고, 위젯 클릭이 처리되기 전에 다음 재실행에 버려졌다.

```
16초에 재실행 31회
폴링상태 pose_tid=c9a876b8 pose_st=processing   <- 실시간 OCR 체크가 0.4초마다 재실행
```

두 번째 원인이 겹쳐 있었다. 버튼을 `on_click` 콜백으로 바꾼 뒤에도 인덱스가 되돌아왔는데,
콜백 안에서 슬라이더 위젯의 세션 키를 직접 쓴 것이 슬라이더 `on_change`와 얽혔기 때문이다
(실측: 버튼을 눌러도 `seek_to`가 0.0으로 잡혔다).

세 번째로, 버튼이 인덱스만 바꾸고 영상은 그대로 두면 시간 비례 자동 싱크가 영상 시각
기준으로 인덱스를 도로 끌고 간다. 재생 중에는 구조적으로 못 먹는 상태였다.

시도했지만 안 된 것

- **가설: 자동 싱크가 덮어쓴다.** 절반만 맞았다. 자동 싱크는 앞으로만 이동하므로
  `다음 투구`는 덮이지 않는다. 진짜 원인은 클릭이 아예 전달되지 않은 것이었다.
- **중복 폴링 루프 제거만으로는 부족했다.** 타임스탬프 싱크 폴링을 지웠는데도
  OCR 체크 폴링이 남아 재실행이 계속됐다.

해결

1. 버튼과 슬라이더를 **`on_click` / 값 비교 방식으로 전환**. 콜백은 위젯 이벤트를
   처리하는 시점에 실행되어 재실행에 밀리지 않는다.
2. 위젯 키는 **위젯을 만들기 전에** 맞춘다. 콜백 안에서 자기 위젯 키를 건드리지 않는다.
3. 이동 시 **영상도 함께 옮긴다** — 자동 싱크 식의 역함수로 `seek_to`를 계산해
   둘이 같은 값을 가리키게 한다. 재생 중에도 동작한다.
4. 중복이던 타임스탬프 싱크 폴링 루프 제거. 컴포넌트가 200ms마다 시각을 보고하고
   그 값 변경이 이미 재실행을 일으키므로 불필요했다.

검증

브라우저에서 클릭 → 진행 `1/320 → 2/320`, 슬라이더 이동, 실측 카드
`FF 포심 패스트볼 96mph ✓ 예측 적중`, 하단 통계 갱신까지 확인. 사용자 환경에서도 확인.

배운 점

**주기적 재실행이 있는 앱에서 위젯의 반환값에 의존하면 안 된다.** 클릭은 이벤트고,
이벤트는 콜백으로 받아야 한다. "버튼이 안 먹는다"를 로직 문제로 보고 조건을 뜯어보는
동안 실제로는 클릭이 도달조차 하지 않고 있었다 — 반환값을 한 번 찍어봤으면 즉시 알았다.

## TS-028 · 학습과 추론의 프레임 샘플링이 달라 가속도가 1/4로 눌렸다

날짜: 2026-08-10
영역: ML
심각도: Critical
상태: 해결됨

증상

2분류 모델이 Savant 클립에서는 정확도 0.783인데 원본 중계 영상에서는 0.410으로
최빈값 기준선(0.538) 아래였다. 예측이 한 클래스로 무너졌다.

```
예측 분포  FASTBALL 37 / BREAKING 2      정답 분포  BREAKING 21 / FASTBALL 18
BREAKING 21개 중 정답 0개
AUC 0.460 (학습 홀드아웃 0.852)   평균 확신도 0.900   <- 확신에 차서 틀린다
```

재현 조건

`build_pitch_group_clips_dataset.py`로 만든 학습 데이터와, `live_classifier`의
추론 경로가 같은 영상에서 서로 다른 프레임 간격을 쓸 때.

원인

표면 - 배포 환경에서 모델이 무너진다. TS-025에서는 이것을 "도메인 격차"로 결론지었다.

근본 - **도메인이 아니라 전처리 설정 불일치였다.**

```
학습 수집  extract_trajectory_candidates(..., target_fps=DETECT_FPS)   # 30.0
추론 경로  extract_trajectory_candidates(...)                          # 인자 없음 -> None
```

59.94fps 영상에서 `target_fps=30.0`은 매 2번째 프레임, `None`은 모든 프레임이다.
프레임 간격이 2배 다르면 **프레임 기준 물리량이 통째로 어긋난다.** 예측과 실측이 정확히 맞았다.

```
                              이론상 배율   실측(앱/학습)
속도   (px/frame)                 1/2        6.38/12.56 = 0.51
가속도 (px/frame^2)               1/4        0.36/1.32  = 0.27
```

하필 `vertical_accel_px`가 모델 중요도 1위(0.398)이고 변화구의 낙차를 재는 특징이다.
그것이 1/4로 눌리니 모든 궤적이 직구처럼 보였다.

시도했지만 안 된 것

원인을 찾기 전에 세 가지를 시도했고 전부 빗나갔다. **모두 증상을 건드린 것이었다.**

- **투구 판별 게이트** — 학습 분포를 닮은 사슬만 남기면 정확도가 오를 것으로 봤다.
  반대였다. 걸러낼수록 나빠졌다(0.410 → 0.200 → 0.000). 모든 사슬이 같은 배율로
  어긋나 있었으니 닮은 것을 고르는 기준 자체가 무의미했다.
- **라벨 짝 어긋남** — 넓은 창이 직전 투구를 잡아 라벨이 밀렸다고 봤다. 라벨을
  ±2칸까지 밀어봤으나 전부 기준선 이하(0.344~0.500)였다.
- **척도 정규화** — 절대 픽셀 특징을 현 길이로 나눠 재학습했다. **부분적으로 먹혔고
  그게 오히려 헷갈리게 했다** (앱 AUC 0.460 → 0.563, BREAKING recall 0.00 → 0.29).
  픽셀 척도를 나누자 시간축 오류의 일부가 상쇄된 것이었다. 사전에 정한 기준
  (앱 AUC 0.65, 정확도 0.60)에 미달해 채택하지 않은 것이 결과적으로 옳았다.

해결

`classify_video_pitch`가 `target_fps=DETECT_TARGET_FPS(30.0)`을 넘기도록 한 줄 수정.

검증

```
                    정확도    AUC     기준선   예측 분포
수정 전 (모든 프레임)  0.410   0.460   0.538   FASTBALL 37 / BREAKING  2
수정 후 (매 2번째)    0.767   0.780   0.581   FASTBALL 20 / BREAKING 23
실험실 (LOGO 4폴드)   0.783   0.881     -
```

- 학습에 쓰지 않은 경기(775300)의 원본 중계 영상, n=43
- BREAKING f1 0.00 → 0.79, FASTBALL f1 0.58 → 0.74
- 특징 분포도 붙었다: `vertical_accel_px` 0.36 → 1.67 (학습 1.32),
  `apparent_speed` 6.38 → 11.23 (학습 12.56), 마할라노비스 안쪽 84.6% → 93.0%
- 전체 테스트 95개 통과

추후 관리

재발 방지 - **전처리 설정은 학습과 추론이 같은 상수를 참조하게 한다.** 지금은
`DETECT_FPS`(수집 스크립트)와 `DETECT_TARGET_FPS`(추론 모듈)가 같은 값을 각자 들고 있다.
한쪽만 바뀌면 조용히 다시 어긋난다. 감지 설정(`imgsz`, `conf`)과 사슬 임계값도 같은 구조다.

남은 리스크 - 이 실패는 **에러 없이 성능만 떨어지는 형태**였고, 오히려 "도메인 격차"라는
그럴듯한 설명이 붙어 한동안 그쪽을 팠다.

배운 점

**"도메인이 다르다"고 결론짓기 전에 양쪽 파이프라인의 설정이 같은지부터 확인한다.**
도메인 격차는 검증하기 어렵고 비싼 가설이라, 맞다고 믿는 순간 재수집·재학습으로 직행한다.
반면 설정 불일치는 `grep` 한 번이면 확인된다. **싸고 확정적인 가설을 먼저 배제해야 한다.**

그리고 이번에 원인을 잡아낸 실마리는 특징들의 **비율**이었다. z-점수로는 1σ를 안 넘어
"분포가 비슷하다"고 판정됐지만, 속도가 정확히 0.51배, 가속도가 0.27배라는 것은
1/2과 1/4을 가리키고 있었다. **정수비가 보이면 물리량이 아니라 단위를 의심한다.**

## TS-029 · TS-027에서 증거로 적어놓고도 안 지운 폴링이 앱을 다시 멎게 했다

날짜: 2026-08-10
영역: FE
심각도: High
상태: 해결됨

증상

영상을 재생해도 투구 인덱스가 넘어가지 않고, `다음 투구` / `이전 투구`를 눌러도 화면이
그대로였다. 오류 메시지는 없었다. TS-027에서 고쳤다고 기록한 증상과 사실상 동일하다.

재현 조건

영상 재생 중. 정지 상태에서 버튼을 누르면 정상 동작했다.

원인

표면 - 버튼이 안 먹고 자동 싱크도 안 된다.

근본 - **스크립트가 위젯 구간에 도달하기 전에 매번 취소되고 있었다.** 원인이 둘 겹쳤다.

(1) `app.py` 말미에 남아 있던 폴링 루프.

```python
_active_tid = st.session_state.get("_pose_task_id")
if _active_tid and _pose_tasks.get(_active_tid, {}).get("status") == "processing":
    time.sleep(0.4)
    st.rerun()
```

OCR 검사는 0.5초 간격으로 걸리는데 1.19GB 영상에서 프레임 하나를 OCR 하는 데 그보다
오래 걸린다. 그래서 재생 중에는 태스크가 사실상 항상 `processing`이고 이 블록이 0.4초마다
스크립트를 통째로 재실행시켰다.

**이 루프는 TS-027 당시에 이미 발견돼 있었다.** TS-027 본문의 증거 블록에 그대로 적혀 있다 —
`pose_st=processing <- 실시간 OCR 체크가 0.4초마다 재실행`. 그런데 해결 항목에는 타임스탬프
폴링 제거만 들어갔고 이건 남았다.

(2) 컴포넌트의 200ms 보고. TS-027의 해결 4번은 "컴포넌트가 200ms마다 시각을 보고하고
그 값 변경이 이미 재실행을 일으키므로 불필요했다"며 폴링을 지웠다. 맞는 말이었지만,
그 200ms 자체가 더 빠른 재실행 폭풍이었다. `setComponentValue` 하나하나가 재실행을
요청하고 새 요청은 실행 중이던 스크립트를 취소한다. 이 앱의 한 번 실행은 0.05~0.7초다.

계측 결과:

```
실행 시작 120회 / 끝까지 도달 5회
[RUN] start 1786332956.32[RUN] start 1786332956.33   <- 같은 ms에 겹쳐 시작
vid_t=217.163106  (실제 영상은 325초)              <- Python이 보는 값이 얼어붙음
```

컴포넌트는 계속 정상 전송 중이었다(5초에 5건, 마지막 값 `{"time":408.12,"playing":true}`).
값은 올라가는데 스크립트가 그 값을 읽는 지점까지 못 갔다.

시도했지만 안 된 것

- **가설: 영상 서버가 죽었다.** 브라우저 `<video>`가 `readyState 0`에서 멈춰 있어 처음엔
  Range 처리를 의심했다. `fetch()`로는 206이 정상이고 `curl`은 1.19GB를 2.5초에 뱉었다.
  **원인은 자동화 탭이 `visibilityState: "hidden"`이었던 것** — 크롬은 숨은 탭에서 미디어
  로딩을 지연시킨다. 크롬을 앞으로 꺼내자 `readyState 4`, `duration 8230.7`로 정상이었다.
  이 관측 하나 때문에 서버·moov 위치·파일 크기를 한참 팠다.
- **가설: 스크립트 한 번 실행이 수십 초 걸린다.** 틀렸다. 계측하니 0.05~0.7초였다.
  느린 게 아니라 잘리는 것이었다.
- **가설: 컴포넌트가 값을 안 보낸다.** 틀렸다. postMessage를 후킹해 세어보니 정상이었다.
- **재렌더 0회로 "스크립트가 안 돈다"고 단정한 것도 틀렸다.** Streamlit은 인자가 같으면
  재렌더 메시지를 생략한다. Python 쪽에 언버퍼드 프린트를 넣고서야 실제를 봤다.

해결

1. `app.py`의 포즈/OCR 태스크 폴링 루프 제거. 재생 중에는 컴포넌트 보고가 재실행을
   일으키고 그 재실행이 완료된 태스크를 거둬간다. 정지 중에는 새 검사가 시작되지 않는다.
2. `local_video_player/frontend/index.html`의 보고 간격을 200ms → 2초로. 앱이 이 값으로
   하는 일은 투구 경계(약 25.7초에 하나) 판정이라 2초로 충분하다. 재생·정지·탐색은
   `play` / `pause` / `seeked` / `ended` 이벤트로 즉시 보고해 반응성을 유지한다.

검증

- 웹소켓 송신 후킹: 10초에 4건, 간격 정확히 2000ms (수정 전 200ms).
- 실행 완료율: 5/120 → 25/54.
- 자동 싱크 정확: `vid_t=134.48 → target=5 → c_idx=5`.
- 버튼 콜백 도달: `[CB] goto 1` 출력 후 `c_idx=1` 유지.
- **계측 제거 후 무간섭 재현** — 브라우저를 건드리지 않고 관찰한 구간에서 `vid_t`가
  끊김 없이 정확히 2초 간격으로 흐름:

```
121.99 → 123.99 → 125.99 → 129.99 → 131.99 → 133.99 → 138.99 → 140.99 → 143.00
```

- 같은 구간에서 화면이 스스로 `투구 1/320`에서 `투구 8/320`까지 전진하고, 방금 던진 구종
  `KC 너클커브 78mph ✗빗나감`과 카운트 3-0까지 따라옴.

추후 관리

- **같은 패턴이 하나 더 남아 있다.** `app.py`의 CV 판정 폴링(`time.sleep(1.5); st.rerun()`)과
  스캔 폴링(`time.sleep(2.0); st.rerun()`)이 같은 구조다. CV는 기본 꺼짐이라 지금은
  안 터지지만, 켜면 같은 증상이 난다.
- 자동화 브라우저로 이 앱을 검증할 때는 탭이 실제로 보이는 상태인지 먼저 확인해야 한다.
  숨은 탭에서는 크롬이 미디어 로딩과 `setInterval`을 모두 스로틀해 측정값이 전부 오염된다.

배운 점

**트러블슈팅 기록에 증거로 남긴 것을 해결 항목에 넣었는지 확인해야 한다.** TS-027은 이
루프를 정확히 지목해놓고 지우지 않은 채 "해결됨"으로 닫혔고, 하루 만에 같은 증상으로
돌아왔다. 원인을 찾는 것과 전부 제거하는 것은 다른 일이다.

그리고 **폴링을 없앨 때 "대신 이게 재실행을 일으켜준다"고 적었다면, 그 대체물의 주기가
한 번 실행 시간보다 긴지 재봐야 한다.** TS-027은 200ms 보고를 해결책의 근거로 삼았는데
그게 다음 사고의 원인이었다.

## TS-030 · 크롬이 백그라운드 탭의 setInterval을 늦춰 타임라인이 영상보다 뒤처졌다

날짜: 2026-08-10
영역: FE
심각도: High
상태: 해결됨

증상

영상은 계속 재생되는데 투구 인덱스가 그 자리에 멎어 있었다. 사용자 표현으로 "여전히
인식 안 됨". 같은 보고에 "투구 버튼도 안 됨"이 붙어 있었으나, 검증 결과 버튼은 정상이었다.

재현 조건

영상 재생 중 브라우저 탭을 백그라운드로 보낸다(다른 창을 보거나 터미널로 전환).
탭이 앞에 있는 동안에는 재현되지 않는다.

원인

표면 - 자동 싱크가 멎는다.

근본 - **크롬은 백그라운드 탭의 `setInterval`을 1분에 한 번까지 늦추지만, 이미 재생 중인
`<video>`는 그대로 재생한다.** 컴포넌트의 시각 보고는 `setInterval(sendState, 250)`에
얹혀 있었으므로 영상만 흘러가고 보고가 끊겼다. 앱은 보고가 와야 재실행되고, 재실행돼야
`index_at_time()`을 다시 계산하므로 인덱스가 그 자리에 남는다.

사용자 세션 로그가 그대로 보여준다. 같은 값이 정확히 120초 간격으로 두 번 올라왔고,
그 사이 영상은 42초에서 99초까지 나아가 있었다.

```
16:17:46  [SYNC] vid_t=42.446409 pl=False
16:19:46  [SYNC] vid_t=42.446409 pl=False
          [SYNC] vid_t=51.77921  pl=True
16:20:50  [SYNC] vid_t=99.63678  pl=False
```

8분 30초 동안 `[SYNC]`가 6줄이다. 2초 주기라면 250줄쯤 나와야 한다.

시도했지만 안 된 것

- **`[CLICK]` 로그가 한 줄도 없어서 버튼 콜백이 안 불린다고 판단했다.** 틀렸다.
  그 `print`는 TS-029 정리 때 이미 지워져 있었다. 없는 계측의 부재를 증거로 삼았다.
- **iframe 밖에서 `postMessage`로 가짜 보고를 넣어 재현하려 했다.** 서버 로그에 아무것도
  안 찍혔다. Streamlit이 `event.source`가 해당 컴포넌트의 `contentWindow`인지 검사하는데,
  최상위 컨텍스트에서 `iframe.contentWindow.parent.postMessage(...)`를 호출하면 `source`가
  최상위 창이 되어 걸러진다.
- **자동화 탭에서 영상 재생으로 재현하려 했다.** `document.visibilityState`가 `hidden`이라
  `readyState: 0`, `duration: null`로 영상이 아예 로드되지 않았다. TS-029의 추후 관리에
  이미 적어둔 함정인데 또 밟았다.

해결

보고를 타이머에서 미디어 이벤트로 옮겼다. `timeupdate`는 미디어 파이프라인이 직접 쏘는
이벤트라 타이머 스로틀을 받지 않는다.

```js
vid.addEventListener("timeupdate", function () { sendState(false); });

// 정지 중에는 timeupdate가 안 오므로 보조 타이머만 남긴다
pollInterval = setInterval(sendState, 1000);
```

`sendState` 안의 2초 간격 제한은 그대로 뒀다. TS-029에서 이 값을 200ms로 뒀다가 재실행
폭주가 났으므로, 보고 경로만 바꾸고 빈도는 건드리지 않았다.

검증

- 새 탭에서 `다음 투구`를 연속으로 눌러 `투구 1 → 2 → 3 → 4` 전진 확인. 카운트
  `0-0 → 1-0 → 2-1`, 방금 던진 구종 `FF 96mph → SL 89mph`, 슬라이더 손잡이까지 따라옴.
  **버튼은 처음부터 정상이었다.**
- `seek_to`가 앵커 매핑대로 꽂힘: 인덱스 1·2·3 → 21.221 / 42.442 / 63.664초.
  첫 앵커가 `(106.106s, 5)`이므로 `106.106 × k / 5`와 정확히 일치한다.
- 수정본이 서버에서 그대로 나가는지 확인 (컴포넌트 정적 파일이라 서버 재시작 불필요,
  브라우저 하드 리로드만 필요):

```
$ curl -s http://localhost:8501/component/local_video_player.local_video_player/index.html \
  | grep -n 'timeupdate\|setInterval(sendState'
84:      vid.addEventListener("timeupdate", function () { sendState(false); });
89:      pollInterval = setInterval(sendState, 1000);
```

추후 관리

- 백그라운드 탭에서도 이제 인덱스는 따라가지만, **탭을 처음부터 백그라운드로 두고 열면**
  영상 자체가 로드되지 않는다(`readyState 0`). 이건 크롬이 재생 시작 전 미디어를
  미루는 동작이라 프론트에서 못 고친다. 시연할 때는 탭을 앞에 두고 재생을 시작해야 한다.
- `_vid_pl`이 False면 자동 싱크가 통째로 걸러진다(`app.py:1343`). 사용자가 일시정지하고
  영상 스크러버로 직접 이동하면 인덱스가 안 따라간다. 지금 시연 흐름에는 없는 조작이라
  손대지 않았다.

배운 점

**"측정이 오염된다"고 적어둔 환경 특성이 제품 자체의 버그일 수 있다.** TS-029에서
백그라운드 탭의 `setInterval` 스로틀을 자동화 검증의 함정으로만 적어뒀는데, 같은 특성이
실사용자에게 그대로 증상으로 나타났다. 계측 도구를 방해하는 것은 대체로 제품도 방해한다.

**주기적으로 무언가를 관찰해야 한다면 그 대상이 이벤트를 쏘는지 먼저 확인한다.**
`<video>`는 `timeupdate`를 쏜다. 타이머로 폴링할 이유가 없었고, 폴링을 골랐기 때문에
브라우저의 타이머 정책을 그대로 물려받았다.

## TS-031 · 방송 오버레이 OCR로는 투구 타이밍을 못 맞춘다 — 정보가 늦게 생긴다

날짜: 2026-08-10
영역: FE / CV
심각도: High
상태: 해결됨

증상

타임라인이 실제 투구와 계속 어긋났다. 사용자 표현으로 "측정 및 예측 타이밍이 너무 느려".
TS-030에서 보고 경로를 고친 뒤에도 남았다.

재현 조건

고정 데모 영상 재생 중. 항상 재현됐다.

원인

표면 - 투구가 지나가고 한참 뒤에 화면이 따라온다.

근본 - **원인이 둘이고, 첫째는 코드로 못 고치는 것이었다.**

(1) 방송 오버레이는 공이 던져진 **뒤에** 뜬다.

| 단계 | 지연 |
|---|---|
| 투구 -> 구속 오버레이 등장 | +2.8~4.2초 (ADR-0010 스캔창) |
| 검사 주기 대기 | +0~0.5초 |
| OCR 1회 | +1.14초 (실측 중앙값) |
| 합계 | **최소 +4.4초** |

앞의 2.8초는 그 시점까지 영상에 정보가 존재하지 않는 구간이다. OCR을 최적화해도
이 밑으로 못 내려간다. 정보의 성질이지 구현 문제가 아니다.

(2) 그 늦은 결과가 앵커 타임라인을 덮어썼다. `app.py`의 실시간 OCR 소비 블록:

```python
_last_mlb = st.session_state.get("_last_ocr_mlb_idx", -1)
_best_idx = min(_last_mlb + 1, len(pitches) - 1)      # 영상 시각을 보지 않는다
st.session_state.current_pitch_idx = _best_idx + 1
```

드라이버가 둘이 됐다. 앵커 보간(영상 시각 기준, 지연 0)은 "더 크면만" 전진하므로
최종 인덱스가 `max(앵커, OCR 카운터)`가 된다. 어느 쪽이 이길지 정해져 있지 않아
구간마다 다르게 어긋났다. ADR-0013에서 앵커를 붙일 때 이 경로를 같이 정리하지 않은 것이다.

시도했지만 안 된 것

- **TS-030에서 보고 지연만 고치면 될 줄 알았다.** 보고 경로는 실제로 문제였지만
  (백그라운드 스로틀), 그걸 고쳐도 타이밍은 그대로였다. 증상이 하나여도 원인이
  하나라는 보장이 없다.
- **OCR 검사 주기를 줄이는 방향을 검토했다.** 0.5초 주기를 줄여도 오버레이 등장까지의
  2.8초는 그대로라 의미가 없다. 오히려 스레드만 늘어난다.

해결

재생 중 감지를 없애고 인덱스를 앵커 보간 하나가 정하게 했다.

- `_start_ocr_check` / `_run_ocr_check_bg` 제거 (호출부도 함께).
- 실시간 OCR 결과로 `current_pitch_idx`를 밀던 블록 제거.
- `pose_detector.ocr_check_pitch_overlay`는 남겼다 — 오프라인 앵커 생성
  (`scripts/build_timeline_anchors.py`)이 쓴다.

**데모 영상이 고정이라 실시간으로 감지할 이유가 없다.** 미리 찾아놓고 재생 중엔
조회만 하면 지연이 0이 된다.

검증

컴포넌트 iframe 안에 스크립트를 주입해 임의 시각을 보고시키고, 화면 인덱스를
`timeline_anchor.index_at_time()`을 파이썬에서 따로 계산한 값과 대조했다.
(iframe 밖에서 `postMessage`를 쏘면 Streamlit이 `event.source` 불일치로 버린다 — TS-030 참고.)

```
보고 시각    기대      실제
   53.05s   투구 3    투구 3
  800.00s   투구 30   투구 30
 4000.00s   투구 167  투구 167
 6500.00s   투구 266  투구 266
```

- 앱 로그에서 `[OCR실시간]` / `[싱크]` / `[PitchDetect]` **0건** — 재생 중 감지 스레드가
  실제로 사라졌다.
- 테스트 111개 통과, `py_compile` 통과.

추후 관리

- **앵커가 320구 중 33개뿐이다.** 사이는 여전히 직선 보간이고 최대 간격이 1139초
  (약 44구)다. 위 검증은 앵커 근처를 지났을 뿐 그 사이의 정확도를 보증하지 않는다.
  마운드 모션 감지(`pose_detector.detect_pitch_motion`, 현재 호출되는 곳 없음)로
  오프라인 전체 스캔을 돌려 320개를 다 채우면 보간 자체가 사라진다.
  ffmpeg 프록시(마운드 crop + 160x90 + 10fps) 실측 8배속 -> 전체 약 17분.
  원본 순차 디코드는 117.8분이라 프록시를 거쳐야 한다.
- 검증 중 **인덱스가 크게 점프하면 컴포넌트 iframe이 리마운트되는 것**을 봤다
  (`vid_t`가 6500 -> 0 -> 0.45 -> 3.63으로 리셋). 자동 싱크는 전진만 하므로 인덱스가
  되돌아가진 않았지만, 재생 중에 나면 영상이 처음으로 돌아간다. 별도 확인 필요.
- `video_pitch_data`가 이제 항상 비어 있다. 표시는 Statcast로 폴백하므로 동작에 문제는
  없다. 오프라인 스캔이 붙으면 여기를 다시 채운다.

배운 점

**"언제"를 알려주는 신호와 "무엇"을 알려주는 신호를 같은 것으로 쓰면 안 된다.**
오버레이는 구종·구속(무엇)에는 정확한 출처지만, 투구 시각(언제)에는 늦은 출처다.
하나로 둘 다 하려다 타이밍을 4.4초 잃었다. 지금은 시각은 앵커, 내용은 Statcast로 갈랐다.

**고정 입력에 실시간 파이프라인을 붙이고 있지 않은지 먼저 확인한다.** 데모 영상은
바뀌지 않는데 매 재생마다 같은 프레임을 다시 OCR 하고 있었다. 미리 계산할 수 있는
것을 실시간으로 하면 지연과 부하를 둘 다 낸다.

## TS-032 · 마운드 모션 차분으로는 투구를 못 찾는다 (미해결)

날짜: 2026-08-10
영역: CV
심각도: Medium
상태: 미해결 — 접근 폐기, 대안 대기

목표

타임라인 보간을 없애려고 투구 시각 320개를 오프라인으로 전부 확보하려 했다.
앵커가 33개뿐이라 최대 1139초(약 44구) 구간이 직선 보간으로 때워지고 있었다(TS-031).

시도한 것

`pose_detector.detect_pitch_motion`이 쓰던 마운드 크롭(y 3/8~7/8, x 2/8~6/8)으로
프레임 차분 시계열을 만들고 피크를 투구로 보려 했다.

원본 순차 디코드는 117.8분(실측)이라 불가능해서 ffmpeg 프록시를 거쳤다.

```
ffmpeg crop=iw/2:ih/2:iw/4:3*ih/8, scale=240:-2, fps=15
  -> 132MB / 8230.7초, 변환 약 12분 (실측 8배속)
모션 스캔 -> 123,459점, 36.4초
```

조밀 OCR도 검토했으나 탈락했다. **tesseract 1회가 1040ms**라 8231초를 1fps로만 훑어도
142.7분이다. 디코드가 아니라 tesseract 자체가 병목이다.

결과 — 실패

(1) 전역 상위 320개 피크: 앵커 대조 지연이 중앙값 -159.6초, 표준편차 198.1초.
    (기대는 +2.8~4.2초.) 모션 점수가 액션 많은 구간에서 통째로 높아, 개수만 전역으로
    맞추면 그런 구간에 피크가 몰리고 조용한 구간을 통째로 건너뛴다.

(2) 앵커 구간별로 투구 수를 고정해 다시 뽑았다. 홀드아웃으로 검증했다 — 오버레이
    65개 중 앵커로 쓴 33개를 빼고 남은 32개는 적합에 안 쓰였다.

```
                    n    중앙값   표준편차   창(+2~5s) 안
앵커(적합, 순환)    33    +3.4s     2.2s      23/33 = 70%
홀드아웃            32    -5.3s    24.9s       1/32 =  3%
균등 분할(기준선)   32    -0.9s     7.1s       3/32 =  9%
```

**홀드아웃에서 균등 분할보다 나쁘다** (표준편차 24.9s vs 7.1s). 앵커에서 70%가 나온 건
그 앵커로 맞췄기 때문이고, 정보가 아니다.

원인 (추정 — 검증 안 함)

크롭 영역이 마운드만이 아니다. 화면 중앙 50%에는 타자·포수·심판·관중이 같이 들어온다.
방송은 투구마다 카메라를 바꾸고 리플레이를 끼운다. 프레임 차분은 이걸 투구 동작과
구분하지 못한다. TS-025에서 "일반 감지기가 병목"이라고 결론지은 것과 같은 벽이다.

다음 후보 (미실행)

오버레이 박스만 잘라낸 프록시에서 **픽셀 변화 지점만 먼저 찾고**, 그 지점에만 OCR을
건다. 오버레이 등장/소멸은 픽셀 수준에서 값싸게 잡히고, tesseract 호출을 8231회에서
수백 회로 줄일 수 있다. P:N 판독은 이미 71%로 동작하는 검증된 경로다(ADR-0013).

배운 점

**홀드아웃 없이 봤으면 성공으로 착각했다.** 적합에 쓴 앵커에서는 70%가 나왔다.
같은 데이터로 맞추고 같은 데이터로 검증하면 언제나 좋아 보인다. 이 프로젝트는
TS-025에서 이미 같은 실수를 했다.

**기준선을 같이 재야 한다.** "표준편차 24.9초"만 보면 나쁜지 판단이 안 된다.
아무것도 안 한 균등 분할이 7.1초라는 걸 옆에 놓아야 폐기 결정이 나온다.

## TS-033 · 오버레이 박스 차분이 통째로 흔들렸다 — 반투명 바 배경이 글자를 덮었다

날짜: 2026-08-11
영역: CV
심각도: Medium
상태: 해결됨

증상

TS-032의 다음 후보였던 "오버레이 박스만 잘라 픽셀 변화 지점을 찾고 거기에만 OCR"이
1단계에서 막혔다. 프레임 차분 이벤트가 8231초에 1194개(7초에 1개) 나왔고, 알려진
투구 시각 65개에 대한 리콜이 어떤 임계값에서도 100%였다. 리콜 100%가 성능이 아니라
"아무 데나 이벤트가 있다"는 뜻이었다.

재현 조건

`ffmpeg crop=160:28:1120:551, fps=4, format=gray` 로 만든 프록시에서 인접 프레임
평균 절대차. 항상 재현됐다.

원인

표면 - 차분 분포가 상시 컸다. p50=1.41, 평균 9.00, 최대 200.55.

근본 - **원인이 둘이었고 둘 다 크롭을 잘못 잡은 것에서 나왔다.**

(1) 크롭 오른쪽 55px이 스코어버그 밖 중계 화면이었다. `_read_pitch_counter`가 쓰는
    좌표(h 0.766~0.803, w 0.875~1.0)를 그대로 가져왔는데, 그 폭은 OCR용이라
    여유가 붙어 있다. 카메라가 움직일 때마다 차분이 통째로 튀었다.

(2) 좁혀도 남았다. 스코어버그 바 자체가 반투명이라 배경 밝기가 프레임마다 흔들린다.
    24픽셀 높이 글자의 변화량보다 배경 흔들림이 커서 신호가 묻혔다.

시도했지만 안 된 것

- **임계값을 6단계로 훑었다** (1.0 ~ 6.0). 이벤트 수만 1194 -> 883으로 줄고 리콜은
  100%를 유지했다. 임계값으로는 신호 대 잡음이 안 바뀐다.
- **최소 간격을 6초/10초로 묶어봤다.** 이벤트가 611~753개로 줄었지만 오프셋
  표준편차가 오히려 1.5s -> 3.0s로 나빠졌다. 잡음 피크끼리 묶인 것이다.
- **안정 구간 길이로 MPH 상태를 가리려 했다.** MPH는 3초, P:N은 10초 이상이라
  길이로 갈릴 줄 알았는데 리콜이 65~86%에서 멈췄다.

해결

**글자만 이진화한 뒤 XOR 한다.** 배경 밝기가 어떻게 흔들리든 190 이상만 남기면
글자 픽셀만 비교하게 된다.

```
mask = frames > 190
xor  = (mask[1:] ^ mask[:-1]).mean(axis=(1,2))
```

크롭도 104px로 좁혀 스코어버그 안만 남겼다. 여기에 "바가 떠 있는가"(크롭 중앙값
< 100) 게이트를 붙여 광고·리플레이 구간을 뺐다.

이렇게 하면 변화점을 찾을 필요 자체가 없어진다. XOR가 작은 구간 = 내용이 안 바뀐
구간이므로, 그 구간마다 한 번씩 읽으면 된다. 847개 구간이 나왔다.

**그리고 원본이 아니라 프록시 프레임을 직접 OCR 했다.** 같은 20지점 실측:

| 경로 | 속도 | 판독률 |
|---|---|---|
| 영상 seek + `ocr_check_pitch_overlay` (기존) | 8s/건 | 11/20 |
| 프록시 프레임 직접 OCR | **1.0s/건** | **16/20** |

겹치는 11건 중 10건 일치. 어긋난 1건(t=866.9s)은 `build_timeline_anchors.py`가
주석에 "불가능한 값"이라고 적어둔 그 지점이고, 프록시 쪽(28 -> 33, 122초에 5구)이
물리적으로 맞다. 빠른 이유는 디코드를 안 하기 때문이다 — 기존 경로는 1.1GB 60fps
원본을 매번 seek 한다.

마지막으로 **오독 필터를 그리디에서 최장 증가 사슬로 바꿨다.** 관측 282개 중
129개가 전부 "인덱스 역행"으로 탈락하고 있었는데, 오독 하나가 뒤따르는 정상 관측을
줄줄이 막는 구조였다 (5 -> 12(오독) -> 6, 7, 8 이면 6, 7, 8 이 다 버려진다).

검증

홀드아웃 4겹. 관측을 4등분해 한 겹씩 빼고 적합하고, 뺀 겹에서만 쟀다.
단위는 초가 아니라 **구 수**다 — 사용자가 보는 건 "몇 번째 투구로 표시되는가"다.

```
방법              n   |오차| 중앙   평균    p90    ±1구   ±2구   초오차중앙
새 앵커          50      1.00    1.14    1.3    92%    95%      10.6
균등 분할(기준선) 50      7.38    7.74   14.7     8%    16%     180.9
기존 앵커 33개    50      1.00    3.27   10.7    64%    71%      16.9
```

- 앵커 33개 -> **200개**. 앵커 간 최대 간격 1139초(약 44구) -> **547초**.
- 독립 검사: 같은 투수 안에서 P:N이 1 늘면 인덱스도 1 늘어야 한다. 이 성질은 적합에
  쓰이지 않는다. **180/181 = 99%** 일치.
- 테스트 113개 통과(신규 2개 포함), `py_compile` 통과.

부호 오차가 -1에 몰린다(50건 중 대부분). 홀드아웃이 질의 지점의 앵커를 바로
빼기 때문에 생기는 구조적 하한이다. 실사용에서는 그 앵커가 있으므로 1.14구는
보수적 상한이다.

추후 관리

- 앵커가 커버하는 인덱스는 0~314다. 마지막 5구는 여전히 외삽이다.
- 스코어버그가 떠 있는 시간이 전체의 58.8%(4841초)다. 나머지 구간의 투구는 잡히지
  않는다. 320구 중 200구까지 온 것이 이 한계에서 나온다.
- 크롭 좌표(104:24:1120:551)는 이 중계 한 경기에만 맞다. 다른 중계는 다시 잡아야
  한다 — ADR-0013의 한계가 그대로 남는다.
- `output/timeline/overlay_frames.npy`(82MB)는 재생성 가능한 중간물이다. 임계값을
  다시 만질 일이 없으면 지워도 된다.

배운 점

**신호가 안 잡히면 임계값이 아니라 무엇을 재고 있는지를 본다.** 임계값 6단계와
묶음 간격 2종을 훑는 동안 결과는 안 바뀌었다. 재는 대상을 원시 픽셀에서 이진화한
글자로 바꾸자 한 번에 풀렸다.

**"검증된 경로"의 검증된 부분이 어디인지 구분한다.** 지시는 기존 OCR 함수를 쓰라는
것이었고 그 함수의 판독 규칙(임계값별 다수결, 정규식)은 실제로 검증된 자산이었다.
검증되지 않은 건 프레임을 가져오는 방법(원본 seek)이었다. 규칙은 그대로 가져오고
프레임 공급만 바꾸니 8배 빨라지고 판독률이 올랐다.

**TS-032가 남긴 다음 후보가 맞았다.** 폐기한 접근을 기록할 때 "다음 후보(미실행)"를
같이 적어둔 것이 이번 세션의 출발점이 됐다. 실패 기록에 방향을 남기는 값이 여기서 나왔다.

## TS-034 · 화면 전체가 한 구씩 밀렸다 — 앵커와 UI가 c_idx를 서로 다르게 썼다

날짜: 2026-08-11
영역: FE
심각도: High
상태: 해결됨

증상

사용자 보고 원문:

```
영상속 투구수보다 버튼이 1개 더 느려. 4개 던졌는데 버튼은 3개로 됨.
```

영상 1:32(=92초) 지점 실측:

| 항목 | 앱 | 영상 스코어버그 |
|---|---|---|
| 방금 던진 구종 | SL 87mph 인플레이(아웃) | FOUR-SEAM FASTBALL 95MPH |
| 볼카운트 · 아웃 | 0-0 · 1아웃 | 1-0 · 1아웃 |
| 타임라인 슬라이더 | 4 | P: 5 |

Statcast 원본에서 4구째(idx 3)가 SL 87.4 hit_into_play(field_out), 5구째(idx 4)가
FF 94.7 ball이다. 즉 앱이 5구까지 던진 지점에서 4구째를 "방금 던진 구"로 띄웠다.

재현 조건

고정 데모 경기(775300) 재생 중 언제나. 슬라이더로 이동해도 같다.

원인

표면 - 슬라이더 값이 0-based `c_idx`라 1-based 스코어버그와 한 칸 어긋나 보였다.

근본 - **`c_idx`의 의미가 두 군데에서 달랐다.**

UI는 `c_idx`를 **아직 안 던진 다음 공**으로 쓴다. Statcast의 `balls`/`strikes`는
그 공을 던지기 **전** 상태이므로 이 규약이어야 볼카운트가 맞는다.

```python
cur  = pitches[c_idx]        # 볼카운트·아웃·타자 HUD (투구 전 상태)
prev = pitches[c_idx - 1]    # "방금 던진 구종"
pred = _predict_next(pitches, c_idx)   # c_idx번 공을 예측
seen_so_far = pitches[:c_idx]
```

그런데 `resolve_anchors`는 `c_idx`를 **이미 던진 공**으로 줬다. `P:4`를 읽으면
그 투수의 4번째 투구인 인덱스 3을 앵커로 박았다. 두 규약이 정확히 하나 어긋나서
볼카운트·판정·예측·슬라이더가 한꺼번에 한 구씩 밀렸다.

TS-007/TS-008의 "타임라인이 공 한 개 느리다"와 증상이 같지만 원인은 다르다.
그때는 균등 분할 가정이었고, 이번엔 규약 불일치다. 앵커 200개를 넣어 보간 오차를
7.38구 -> 1.14구로 줄인 뒤에도 남아 있던 상수 오프셋이라 TS-033 작업 중에는
보간 오차에 묻혀 안 보였다.

시도했지만 안 된 것

- **처음엔 슬라이더 표기만의 문제로 봤다.** 0-based 값을 1-based로 바꾸면 끝날 줄
  알았는데, 그러면 슬라이더만 맞고 「방금 던진 구종」과 볼카운트는 그대로 밀린다.
  화면과 Statcast 원본을 나란히 놓고서야 표기가 아니라 규약 문제인 걸 알았다.
- **UI 쪽을 앵커에 맞추는 안을 검토했다가 접었다.** `c_idx`를 "던진 공"으로 통일하면
  볼카운트를 다음 행에서 끌어와야 하고(Statcast는 투구 전 카운트만 준다), 판정·예측·
  스트릭·누적 분포까지 전부 손대야 한다. 앵커 쪽 한 줄이 훨씬 좁다.

해결

`resolve_anchors`가 다음 차례 인덱스를 주도록 한 칸 올렸다.

```python
thrown = min(matches, key=lambda i: abs(i - guess))
candidates.append((t, min(thrown + 1, n - 1)))
```

`index_at_time` / `time_at_index`는 손대지 않았다. 두 방향이 같은 앵커를 쓰므로
역함수 관계가 유지되고(이동 후 자동 싱크가 도로 끌고 가지 않는다), 앵커 인덱스가
전부 균일하게 +1이라 홀드아웃 오차 수치도 변하지 않는다.

라벨은 반대로 `c_idx+1` -> `c_idx`로 되돌렸다. `c_idx`가 곧 "지금까지 던진 개수"라
스코어버그 P:N과 직접 비교된다. 슬라이더 손잡이 숫자와도 같은 값이 된다.

누적 구종 분포의 `pitches[:c_idx+1]`도 `pitches[:c_idx]`로 고쳤다 — 새 규약에서는
아직 안 던진 공이 분포에 섞이고, 그 공이 바로 예측 대상이었다.

검증

`venv/bin/python3 -m pytest tests/ -q` -> 115 passed (기존 113 + 신규 2).
브라우저 실측:

| 시점 | 앱 표시 | Statcast 원본 | 일치 |
|---|---|---|---|
| 로드 직후 | 진행 0/320, 0-0 0아웃, 타자 Torres, 방금 던진 없음 | 1구째 투구 전 | O |
| 2구 완료 | 진행 2, 1-1, 방금 던진 FF 94mph 파울 | idx1 = FF 94.4 foul -> 1-1 | O |
| 163구 지점 | 진행 163, 1-2, 방금 던진 SL 87mph 파울 | idx162 = SL 87.2 foul -> 1-2 | O |

추후 관리

- 앵커 사이 선형 보간 오차(홀드아웃 |오차| 중앙 1.00구, ±1구 이내 92%)는 그대로다.
  실측 중에도 161구 -> 163구 구간에서 영상보다 한 칸 앞선 순간이 있었다. 이번 건과
  별개이고 균등 분할(7.38구)보다는 훨씬 낫다.
- 앵커 시각은 방송 그래픽이 뜬 시각에서 지연 1.32초를 뺀 값이라, 앱이 스코어버그보다
  1.3초 정도 먼저 갱신된다. 결과가 화면에 뜨기 직전에 앱이 먼저 알려주는 셈이라
  거슬리면 지연을 빼지 않는 쪽으로 되돌릴 수 있다.

배운 점

**같은 변수를 두 모듈이 다르게 해석하면 테스트는 전부 통과한다.** `resolve_anchors`
테스트 13개는 자기 규약 안에서 전부 맞았고 앱도 죽지 않았다. 경계에 규약을 적어두지
않으면 이런 어긋남은 화면을 눈으로 보기 전까지 안 드러난다. 지금은 함수 docstring에
"대기 중인 투구"라고 못박아 뒀다.

시작했지만 슬라이더는 `c_idx`를 그대로 그렸을 뿐이다. 화면의 다른 값들(볼카운트,

## TS-035 · 자동 타임라인이 타석 끝나는 공마다 늦었다 — 카운터가 리플레이에 가려졌다

영역: CV

상태: 해결됨

증상

사용자 보고 원문:

```
4개째부터 제대로 안됨. 3구까지는 제대로 측정됐다. 버튼으로는 되는데 저절로 타임라인
이 넘 ㅜ늦게 올라감. 4ㄱ구째만
```

TS-034를 고친 뒤에도 남았다. 버튼·슬라이더로 옮기면 정확한데 재생 중 자동 진행만
느렸다. 1~3구는 멀쩡했다.

재현 조건

고정 데모 경기(775300) 재생. 타석이 끝나는 공마다 재현된다.

원인

표면 - 4구째 앵커가 87.68초인데 실제 투구는 62초 언저리였다.

근본 - **스코어버그 카운터가 리플레이에 가려지는 동안 투구가 일어난다.**

오버레이 판독 원본:

```
  49.75 ->  60.75  value=3
  61.50 ->  63.25  value=None      <- 사실은 87MPH (4구째)
  63.25 ->  89.00  (바 없음)        <- 인플레이 타구 -> 리플레이
  89.00 ->  90.25  value=4         <- 앵커가 여기 박혔다
```

4구째(SL 87.4)는 인플레이 타구로 아웃이 됐다. 방송이 리플레이로 넘어가면서 바가
사라졌고 `P: 4`는 다음 타자가 들어선 89초에야 보였다. 앵커는 "P:N이 **처음 보인**
시각"을 쓰므로 26초 늦게 박힌다.

한 번이 아니다. 카운터 전환 282번 중 **72번(26%)이 공백 10초 초과**다
(p90 35초, 최대 249.5초). 타석이 끝나는 공마다 난다. 8구째(볼넷)도 같았다 —
실제 146.5초, 카운터 표시 174초.

1~3구가 멀쩡했던 것도 같은 이유다. 그 구간은 바가 계속 떠 있어 공백이 3초 안쪽이었다.

버튼이 멀쩡한 이유는 인덱스를 직접 넣기 때문이다. 앵커 시각에 의존하는 건 자동
진행뿐이다.

시도했지만 안 된 것

**공백을 추론으로 메우려는 시도를 8가지 했고 전부 실패했다.** "직전 카운트가
마지막으로 보인 시각"을 하한으로 삼아, 공백 임계값 4종(6/8/10/15초), 중간점,
카운터가 정확히 1만 증가한 경우로 한정, 공백 상한 4종(30/40/60/90초)을 조합했다.
정답은 전체해상도 MPH 스캔 60개.

```
추정                          중앙     평균    p90     최소     최대  |오차|중앙
현재 (start-1.32)            4.07   11.02  37.01   -1.18   57.88     4.07
공백>8s -> prev_end          2.98   -3.19   7.61  -84.24    9.70     4.88
연속 증가 + 공백 8~40s        3.58    6.40  37.01  -32.11   57.88     4.49
중간점                        3.38    4.22  21.80  -38.87   34.45     4.75
```

전부 **늦는 꼬리를 빠른 꼬리로 바꿀 뿐**이고 |오차| 중앙값은 오히려 나빠졌다.
공백 안에 몇 구가 들어갔는지 모르니 당연하다. 이 데이터만으로는 정보가 없다.

해결

**같은 칸에 뜨는 구속 표시를 시각 소스로 썼다.** 스코어버그의 그 칸은 두 상태를
오간다 — 투구 직후 `87MPH`가 3초쯤 떴다가 `P: 4`로 돌아간다. 구속 표시는 인플레이
타구가 나와도 뜬다. 카운터가 못 보는 지점의 투구 시각을 구속 표시가 알려준다.

영상을 새로 훑지 않았다. 구속 OCR 좌표(h 0.769~0.800, w 0.875~1.0)가 카운터
좌표와 사실상 같아서, TS-033에서 만든 프록시(`overlay_frames.npy`)에 이미 다 들어
있었다. `read_overlay_counters.py`가 버린 307개 구간 중 **250개(81%)가 구속
표시**였다. 세그먼트 경계도 기존 것을 그대로 써서 두 판독이 같은 시간축에 놓인다.
소요 7.8분.

귀속 규칙 — N번째 공의 구속은 그 공 직후에 떴다가 `P:N`으로 돌아간다. 따라서
"직전 런이 끝난 뒤 ~ `P:N`이 뜨기 전" 구간의 **마지막** 구속 표시가 N번째 공의
것이다. 카운터가 정확히 1 증가한 경우에만 쓴다 — 2 이상 뛰면 그 사이에 몇 구가
들어갔는지 알 수 없다. 조건 없이 쓰면 최대 133.9초를 앞당겨 버렸다(조건을 걸면
최대 54.4초).

직접 눈으로 확인했다.

추후 관리

- 구속 표시가 검출되는 건 320구 중 250구(78%)다. 나머지는 카운터에 의존하므로

- `output/timeline/overlay_speeds.jsonl`은 재생성 가능하다(7.8분).

## TS-036 · CV 정확도 76.7%가 표본을 늘리자 66.4%로 내려앉았다

```
변형          판정   적중   정확도
offset 0       21     19    90.5%
+0.9s          24     21    87.5%
+1.8s          24     21    87.5%
```

가설은 절반만 맞았다. 확보율은 올랐지만(70% -> 80%) 조건부 정확도는 오히려 내렸다.
새로 살아난 3구가 전부 맞았는데도 그렇다 — 분모가 늘어서다. 전체 30구 중 맞힌
개수로 보면 19 -> 21이라 실질은 개선이다.

해결

창을 두 개 놓는다 (`WINDOW_OFFSETS = (0.0, 0.9)`). 첫 창이 실패한 것만 두 번째 창으로
다시 본다 — 정답을 보고 고르는 게 아니라 "창 A 실패 시 창 B"라 실제 파이프라인이
취할 전략이다. 실패 55구만 재시도해 6.7분에 끝났다(전체 재실행은 5.8시간).

화면 수치는 하드코딩을 걷어내고 `fixed_demo_cv.json`을 Statcast로 채점해 계산한다.
기준선도 그 채점 표본의 다수 클래스 비율로 낸다. 데이터를 갱신하면 화면도 따라간다.

검증

브라우저 실측으로 화면이 `66.4% (83/125)` · `대상 181구 중 137구 판정(76%) ·
채점 125구(OFFSPEED 제외) · 기준선 53.6%`를 표시한다. 별도 채점 스크립트 결과와 일치.
기준선 53.6% 대비 66.4%는 이항검정 p≈0.004로 유의하다.

추후 관리

- 남은 판정 불가 44구는 no_trajectory 27 · too_few_points 16 · no_detections 1이다.
  창을 옮겨도 안 잡히면 카메라 각도·가림 문제라 창 문제가 아니다. 세 번째 창은
  값어치가 없어 보인다.
- **신뢰도가 쓸모없다.** 적중 평균 0.83, 오답 0.79로 구분이 안 된다. 화면에 띄우고
  있지만 판단 근거로 쓰면 안 된다.
- 소요 시간 추정을 두 번 틀렸다. 전체 배치는 57분으로 봤는데 350.7분(1.1GB 영상
  뒤쪽 seek이 건당 14초 -> 116초로 느려짐), 재시도는 1.8시간으로 봤는데 6.7분이었다.

배운 점

**"이번 세션 x/y"를 실적으로 굳히면 안 된다.** 사용자가 본 투구만 채점되는 구조라
표본이 경기 초반에 치우쳤고, 그게 10%p 과대평가로 이어졌다. 화면에 실시간 집계를
띄우더라도 대표 수치는 별도의 고정 표본에서 뽑아야 한다.

**서로 다른 표본의 숫자를 나란히 적지 않는다.** 정확도는 앱 표본, 기준선은 실험실
표본이었다. 둘을 같은 줄에 적는 순간 비교로 읽힌다.

**확보율과 정확도는 같이 봐야 한다.** 창을 옮겨 정확도가 내렸다고 후퇴할 뻔했다.
어려운 공이 분모에 들어오면 조건부 정확도는 내려가는 게 정상이고, 봐야 할 건
"던진 공 중 몇 개에 맞는 답이 나오는가"다.

## TS-037 · BiLSTM 예측이 영원히 "계산 중"에 멈춰 통계 폴백만 보였다

날짜: 2026-08-13
영역: ML/Infra
심각도: Critical
상태: 해결됨

증상

시연 중 사용자가 "1구 이후부터 제대로 측정 및 예측이 안 된다"고 보고했다. 화면에는
어느 투구를 봐도 같은 예측이 떴다.

```
예측 · 통계 기반 예측 (BiLSTM 계산 중)
FF 포심 패스트볼
20% 신뢰도
```

`streamlit_app/.bilstm_cache/`는 비어 있었고, 앱 콘솔에는 아무 에러도 없었다.

재현 조건

앱을 띄우고 고정 데모(game_pk=775300)가 자동 로드되면 항상. 배지가 "BiLSTM 계산 중"
에서 절대 바뀌지 않는다.

원인

두 개가 겹쳐 있었고, 앞의 것이 뒤의 것을 가리고 있었다.

**근본 1 — `model.predict()`가 데드락에 걸렸다.** 155샘플 예측이 10분을 넘겨도 안
끝났다. `ps`로 보면 CPU 0.1%에 STAT `S`(sleeping)였다 — 계산 중이 아니라 잠들어 있다.
`sample`로 메인 스레드를 뜨니 tf.data prefetch 스레드가 absl Mutex에서 대기 중이다.

```
tensorflow::data::PrefetchDatasetOp::Dataset::Iterator::PrefetchThread(...)
  absl::lts_20250814::Mutex::lock()  (in libtensorflow_framework.2.dylib)
    ...
      AbslInternalPerThreadSemWait_lts_20250814  (in libarrow.2400.dylib)
        _pthread_cond_wait  (in libsystem_pthread.dylib)
          __psynch_cvwait  (in libsystem_kernel.dylib)
```

**마지막 두 줄의 `libarrow`가 핵심이다.** TensorFlow가 쓰는 absl 동기화 심볼이
TensorFlow 자신의 라이브러리가 아니라 pyarrow가 싣고 온 `libarrow.2400.dylib`에서
해결되고 있다. pandas 3.x가 pyarrow를 끌고 오고, 그게 TF보다 먼저 로드된다. 서로 다른
absl 두 벌이 한 프로세스에 올라와 mutex 구현이 어긋났다.

**근본 2 — 시퀀스 길이가 모델과 안 맞았다.** predict를 우회하고 모델을 직접 호출하니
그제서야 진짜 에러가 나왔다.

```
ValueError: Input 0 with name 'seq_input' of layer 'pitch_predictor' is incompatible
with the layer: expected shape=(None, 3, 6), found shape=(155, 5, 6)
```

`precompute_bilstm()`의 `_SEQ_LEN = 5`인데 학습된 `models/pitch_predictor.h5`의
`seq_input`은 `(None, 3, 6)`이다. 데드락이 없었어도 예측은 어차피 죽었다.

**표면 — 둘 다 화면에 안 나왔다.** `_run_bilstm_bg()`가 예외를 `_bilstm_tasks` dict에만
담고 아무 데도 안 알렸고, 앱은 `status == "done"`만 확인해 `"error"`는 무시했다.
그래서 `bilstm_status`가 `"computing"`에 영구히 머물렀다.

```python
except Exception as e:
    _bilstm_tasks[game_pk] = {"status": "error", "error": str(e)}   # 아무도 안 본다
```

시도했지만 안 된 것

**영상이 안 도는 걸 원인으로 봤다.** 브라우저에서 `<video>`가 readyState 0에 멈춰
있어 이걸 먼저 쫓았다. Range 요청을 curl·fetch로 검증했더니 둘 다 206에 15ms로
정상이었고, 앞부분 25MB를 blob으로 만들어 먹여도 metadata가 안 올라왔다. 마지막에
`document.hidden`을 찍어보니 `true`였다 — 자동화 탭이 백그라운드라 크롬이 미디어
로딩을 미룬 것이고, 사용자 브라우저와 무관한 현상이었다. 여기서 30분을 썼다.

**`다음 투구` 버튼도 먹통이라는 보고를 TS-027 재발로 봤다.** 실제로 눌러보니
0 -> 1 -> 2로 정상 동작했고 슬라이더도 50까지 정확히 옮겨졌다. 버튼은 멀쩡했고,
"예측이 안 바뀐다"가 "버튼이 안 먹는다"로 보였던 것이다.

**print가 로그에 안 찍혀 한참 헤맸다.** `nohup ... > log`로 띄우면 stdout이 파일이라
블록 버퍼링이 걸린다. streamlit 자체 로그(stderr)만 보이고 앱의 `print()`는 전부
버퍼에 갇혀 있었다. `PYTHONUNBUFFERED=1`과 `python -u`를 붙이고 나서야 `[FixedDemo]`,
`[SYNC]` 줄이 나왔다.

해결

`streamlit_app/app.py` 세 군데.

1. `_SEQ_LEN = 5` -> `3` (모델 규격에 맞춤)
2. `model.predict(...)` -> `model(..., training=False)` 직접 호출. tf.data를 아예 안
   거치므로 데드락 경로가 사라진다. 155샘플이면 배치를 나눌 이유도 없다.
3. 실패를 화면까지 올린다. `_run_bilstm_bg`에서 `traceback.print_exc()`, 앱에서
   `status == "error"`면 `bilstm_status = "error"`, 배지 문구를 상태별로 분기.

검증

```
$ ls -la streamlit_app/.bilstm_cache/
-rw-r--r--  20481  8 13 12:17 775300.pkl

total 320 | BiLSTM 채워짐 173
예시 {'next_pitch': 'FF', 'confidence': 0.6858843564987183, ...}
예측 분포: {'FF': 126, 'OTHER': 20, 'SL': 11, 'CH': 7, 'SI': 6, 'CU': 3}
```

브라우저 실측 — 8번째 투구에서 배지가 `예측 · BiLSTM 모델 예측 — 직전 투구 흐름 기반`,
카드가 `OTHER 57% 신뢰도`, 확률 막대가 OTHER 57 / FF 22 / SL 17 / CH 4 / SI 1로 뜬다.
고정 20%가 아니라 투구마다 값이 달라진다.

추후 관리

- **320구 중 173구만 BiLSTM이 나온다.** 나머지는 (a) 그 투수의 2025 학습 데이터가
  없거나 — Cole(543037)·660813·664776 세 명, 합쳐서 120구 — (b) 시퀀스 3구가 아직 안
  쌓인 구간(45구)이다. 설계상 그런 것이고 화면에도 "이 투수는 학습 이력 부족"으로
  적었다. 없는 예측을 지어내지 않는다.
- **pyarrow/absl 충돌은 우회했을 뿐 없앤 게 아니다.** tf.data를 쓰는 코드를 새로
  넣으면 같은 자리에서 다시 멈춘다. 근본 해결은 import 순서를 고정하거나 pandas를
  2.x로 내리는 쪽인데, 둘 다 부작용이 커서 지금은 안 건드린다.
- `scaler.pkl`이 scikit-learn 1.8.0에서 저장됐는데 현재 1.9.0이라
  `InconsistentVersionWarning`이 뜬다. 지금은 동작하지만 언젠가 깨진다.

배운 점

**예외를 dict에 담고 끝내면 그 기능은 조용히 죽는다.** `status: "error"`를 아무도
읽지 않아서, 명백한 shape 오류가 "계산 중"이라는 정상적인 문구 뒤에 숨었다. 사용자
눈에는 "예측이 이상하다"로만 보였고 원인을 찾는 데 도구 호출 40회가 넘게 들었다.
백그라운드 작업의 실패는 최소한 콘솔에는 남기고, 화면 상태는 실패를 표현할 수 있어야
한다.

**"CPU를 안 쓰면서 안 끝나는 것"은 느린 게 아니라 멈춘 것이다.** 처음엔 155샘플
예측이 오래 걸리나 싶어 기다렸는데, `ps`의 %CPU 0.1이 그게 아니라고 말해주고 있었다.
`sample <pid>`로 스택을 뜨는 데는 2초면 된다.
