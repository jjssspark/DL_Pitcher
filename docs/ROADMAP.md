# PitchIQ 5-Day 고도화 로드맵

작성일: 2026-07-27
목표: 지금의 프로토타입을 **① 실제로 돌아가는 서비스**, **② 취업용 포트폴리오**로 완성한다.
진행 방식: "day1 진행해줘" / "day2 진행해줘" 라고 말하면 이 문서를 기준으로 그 날짜의 작업을 이어서 진행한다. 각 day는 코드 작업 + 블로그(기술 정리) 작업을 세트로 묶어서 진행한다.

---

## 0. 현재 상태 진단 (파일 확인 결과)

생각보다 훨씬 많이 진행되어 있다. "처음부터 만드는" 로드맵이 아니라 "다듬고 배포하는" 로드맵으로 잡았다.

### 이미 완성된 것

| 영역 | 상태 |
|---|---|
| 데이터 수집 (`src/data_collector.py`) | pybaseball로 MLB Statcast 2025 시즌 전체 수집 완료 (`data/raw/statcast_2025_full.csv`, 약 87MB) |
| 피처 엔지니어링 (`src/feature_engineering.py`) | 시퀀스(직전 5구) + 상황 컨텍스트 + **투수 성향 피처(구종 비율, 카운트별 최빈구종, 상대전적)**까지 반영된 꽤 정교한 설계 |
| 예측 모델 (`src/model.py`) | BiLSTM + 투수/타자 Embedding + 컨텍스트 Dense 결합 구조. 학습 완료 (`models/pitch_predictor.h5`, `scaler.pkl`) |
| 모델 성능 (`src/evaluate.py`) | Random 12.5% → 46.14% (baseline 대비 약 3.7배). 혼동행렬/클래스별 정확도 스크립트 존재 |
| 객체 탐지 (`src/yolo_detector.py`) | YOLOv8 커스텀 학습된 야구공 탐지 모델 (`models/baseball_detector*`), 적응형 프레임 샘플링으로 속도 최적화 |
| 파이프라인 (`src/pipeline.py`) | YOLO 이벤트 → BiLSTM 예측 연결하는 통합 클래스(`PitchPipeline`) 구현 완료 |
| 웹 서비스 (`streamlit_app/app.py`) | **1,537줄** 규모. 실제 MLB 경기 선택, YouTube 영상 연동/캐싱, 백그라운드 스레드 기반 실시간 스캔, OCR 체크, 다이아몬드/카운트 시각화 등 — README에 적힌 것보다 훨씬 고도화되어 있음 |

### 확인이 필요하거나 정리가 안 된 것

- **`src/pose_detector.py`가 이름과 실제 구현이 다름.** "포즈 감지"라는 이름인데 실제로는 MediaPipe 등 포즈 모델이 아니라 프레임 차이 기반 모션 감지로 구현되어 있다. 아마 포즈 추정을 시도했다가 성능/정확도 문제로 방향을 튼 것으로 보이는데, 이 배경을 본인 확인 후 블로그 트러블슈팅 소재로 쓰면 좋다.
- **`requirements.txt` / `Dockerfile` / `pyproject.toml`이 전혀 없다.** 지금 상태로는 본인 컴퓨터가 아니면 아무도 설치·재현할 수 없다. 포트폴리오 심사자가 클론해서 못 돌리면 감점 요인.
- **`.git` 저장소가 약 2GB.** 과거 커밋에 대용량 CSV(수십 MB × 6개월치), YOLO 모델(.pt), 학습된 모델(.h5) 등이 이력에 남아있다. 지금은 `.gitignore`로 막아뒀지만 이미 커밋된 이력은 그대로 남아있어서 클론 시 매우 무겁다. GitHub 저장소(`jjssspark/DL_Pitcher`)가 public인데, 정작 최근 로컬 변경사항(`app.py` 수정, `local_video_player` 신규 파일)은 커밋도 안 된 상태.
- **커밋이 총 4개뿐**이라 지금까지의 개발 과정이 커밋 히스토리에 거의 안 남아있다. 히스토리 자체가 포트폴리오에서 "어떻게 발전시켰는지"를 보여주는 자료가 될 수 있는데 지금은 그 스토리가 비어있다.
- **배포된 곳이 없다.** 로컬 Streamlit 실행만 가능. "실사용 서비스"가 되려면 링크 하나로 누구나 접근 가능해야 한다.
- **README가 초기 기획 수준으로만 적혀 있고 실제로 구현된 실시간 앱 기능(YouTube 연동, 백그라운드 스캔, 시각화 UI 등)은 전혀 반영이 안 됨.**
- 테스트 코드 없음, 블로그/기술 문서 0건.

## 2. Day별 상세

### Day 1 — 기반 정리 & 재현성 확보

**왜 먼저 해야 하나:** 지금 상태로는 남이 클론해도 못 돌리고, git 저장소도 너무 무겁다. 이후 4일 작업의 토대이므로 가장 먼저 처리한다.

- Git 정리
  - 현재 미커밋 변경사항(`app.py`, `local_video_player`) 확인 후 의미 단위로 커밋
  - `git filter-repo` 또는 BFG로 과거 이력의 대용량 파일(csv, .pt, .h5, .mp4) 제거 여부 결정 (public repo이므로 신중하게 — 히스토리를 살릴지 새 repo로 갈지 결정 필요)
- `requirements.txt` (또는 `environment.yml`) 생성 — 버전 고정
- 대용량 모델 파일(.h5, .pt) 배포/공유 전략 결정 (Git LFS vs 릴리즈 아티팩트 vs 클라우드 스토리지)
- README 전면 개편: 실제 구현된 아키텍처(YOLO + 모션감지 + BiLSTM + 실시간 Streamlit 앱) 반영, 설치/실행 방법 추가
- **블로그**: 프로젝트 목표, 왜 "다음 구종 예측"을 선택했는지, MLB Statcast 데이터가 무엇인지, 전체 아키텍처(데이터→모델→영상분석→서비스) 개요

**완료 기준**: `git clone` 후 `pip install -r requirements.txt`만으로 환경이 재현되고, README만 봐도 프로젝트 전체 그림이 이해된다.

### Day 2 — 예측 모델 심화 정리

- `feature_engineering.py`, `model.py`, `evaluate.py` 코드 정리 (타입힌트/주석/재현 가능한 학습 스크립트화)
- 성능 개선 실험 1~2개 시도하고 결과 기록 (예: 클래스 불균형 보정 효과 검증, 시퀀스 길이 튜닝, 피처 추가/제거 ablation)
- `evaluate.py` 재실행하여 혼동행렬·클래스별 정확도 최신화, README에 반영
- **블로그**: BiLSTM + Embedding 구조를 선택한 이유, 피처 엔지니어링에서의 설계 결정(투수 성향 피처를 왜 넣었는지 등), 46.14%라는 수치가 8-class 문제에서 갖는 의미, 클래스 불균형 등 트러블슈팅

**완료 기준**: 모델 성능 실험 결과가 표/그래프로 정리되고, 왜 이런 구조를 택했는지 설명할 수 있다.

### Day 3 — 영상 처리 파이프라인 검증

- `yolo_detector.py`(공 탐지), `pose_detector.py`(모션 감지), `pipeline.py`(YOLO→BiLSTM 연결) 실제 영상으로 end-to-end 테스트
- 처리 속도 벤치마크 (프레임 샘플링 전략이 실제로 얼마나 빨라지는지 수치화)
- 예외 상황 처리 보강 (영상 없음, 모델 없음, 공 미탐지 등)
- **블로그**: 왜 포즈 추정에서 모션 감지로 전환했는지(트러블슈팅 스토리), YOLOv8 커스텀 학습 과정, 적응형 프레임 샘플링으로 속도를 최적화한 이유와 결과

**완료 기준**: 실제 영상 파일로 처음부터 끝까지(공 탐지 → 구종 예측) 에러 없이 동작하고, 처리 속도가 수치로 남는다.

### Day 4 — 서비스 배포

- `app.py`(1,537줄) 구조 정리 — 필요시 기능별 모듈 분리
- 배포 플랫폼 결정 및 배포 (Streamlit Community Cloud가 1순위 후보이나, 대용량 모델 파일·YouTube 다운로드·백그라운드 스레드 등이 무료 플랫폼 제약과 충돌할 수 있어 Day 1에서 확인한 모델 배포 전략과 함께 재검토 필요)
- 로딩 상태/에러 UX 보강
- **블로그**: Streamlit로 실시간성 있는 서비스를 만들며 겪은 문제(세션 상태, 캐시, 백그라운드 스레드), 배포 과정 트러블슈팅, 최종 아키텍처 다이어그램

**완료 기준**: 링크 하나로 접속해서 실제 기능(구종 예측 데모)을 체험할 수 있다.

### Day 5 — 포트폴리오 마무리

- 배포된 서비스 기준 통합 테스트 (실제 사용 시나리오 재현)
- 데모 GIF/짧은 영상 제작
- README 최종본 (배지, 데모 링크, 아키텍처 다이어그램, 회고 섹션)
- 이력서/포트폴리오용 프로젝트 요약 작성 (3줄 요약 + 정량적 임팩트 수치)
- **블로그**: 프로젝트 전체 회고 — 잘한 점, 아쉬운 점, 다음에 시도해볼 것(Future Work와 연결), 이 프로젝트로 어필하고 싶은 역량 정리

**완료 기준**: 링크 클릭 한 번으로 "서비스 데모 + README + 블로그 5편"이 모두 보이는 상태.

## 3. 진행하면서 참고할 가정 / 확인 필요 사항

- 배포 플랫폼은 일단 **Streamlit Community Cloud**를 기본 후보로 잡았다. 다만 대용량 모델(.h5, .pt)과 YouTube 다운로드(yt-dlp) 기능이 무료 플랫폼에서 그대로 돌아갈지는 Day 1~4 사이 확인이 필요하고, 안 되면 Docker + Render/Fly.io 등 대안으로 전환한다.
- 블로그는 어느 플랫폼(velog, tistory, 개인 블로그 등)에 올릴지 정해진 게 없어서, 일단 마크다운 초안을 매일 만들어두고 실제 게시는 원하는 플랫폼에 복붙하는 방식으로 진행하면 된다. 원하는 플랫폼이 있으면 알려주면 그에 맞게 포맷을 맞출 수 있다.
- git 히스토리 정리(대용량 파일 제거)는 되돌리기 어려운 작업이라 Day 1에 진행 여부를 한 번 더 확인하고 진행한다.
