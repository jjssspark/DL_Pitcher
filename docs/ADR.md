## ADR-0001 · 야구공 탐지에 YOLOv8n 채택

- 날짜: 2026-07-27 (Day 1 정리 기준, 최초 결정 시점은 이전)
- 상태: 채택됨
- 관련 근거: src/yolo_detector.py, src/train_yolo.py, models/baseball_detector.pt, docs/blog/day1.md

배경

- 중계 영상에서 투구 타이밍을 자동으로 잡아내려면 화면 속 작은 객체(야구공)를 실시간에 가까운 속도로 탐지해야 한다
- 커스텀 학습(자체 라벨링한 야구공 데이터셋)도 필요했다

검토한 대안

- 더 큰 YOLOv8 변형(s/m/l)
  - 정확도는 높지만 Streamlit 무료 배포 환경 등 리소스 제약 환경에서 추론 속도가 떨어진다
- 범용 사전학습 객체탐지 모델 그대로 사용
  - 야구공처럼 작고 빠르게 움직이는 객체는 COCO 등 범용 데이터셋 기준 사전학습 가중치만으로는 탐지율이 낮다

> 결정
> 가볍고 커스텀 학습이 쉬운 YOLOv8n을 base로 선택하고, 야구공 데이터로 자체 파인튜닝(train_yolo.py)해 baseball_detector.pt를 만들었다. 추론 시에는 적응형 프레임 샘플링으로 속도를 추가로 최적화했다.

결과

- 실시간에 가까운 속도로 공 탐지가 가능해졌다
- nano 모델이라 정확도 상한은 더 큰 모델보다 낮을 수 있다. 현재는 이 트레이드오프를 리소스 제약 하에서 감수하는 쪽을 택했다
- 이후 투구 타이밍 감지 자체는 YOLO 단독이 아니라 ADR-0004(모션 감지)와 병행하는 구조로 진화했다

## ADR-0002 · 다음 구종 예측에 BiLSTM + Embedding 구조 채택

- 날짜: 2026-08-03 (Day 2 재정리 기준)
- 상태: 채택됨
- 관련 근거: src/model.py, src/feature_engineering.py, docs/blog/day2.md

배경

- 다음 구종 예측에는 두 종류의 정보가 섞여 있다
  - 순서가 있는 정보: 직전 몇 구의 시퀀스
  - 순서가 없는 정형 정보: 카운트·주자·점수차
  - 투수/타자별 성향(고차원 범주형)

검토한 대안

- 단방향 LSTM
  - 실시간 추론이라면 미래 정보를 볼 수 없어 자연스러운 선택이지만, 이 문제는 이미 완결된 직전 시퀀스를 통째로 넣고 다음 구종을 맞히는 구조라 양방향 문맥을 다 쓰는 게 유리하다고 판단했다
  - 다만 실제 A/B 비교는 하지 않았다 (후속 실험 후보로 남김)
- 투수/타자 ID 원-핫 인코딩
  - MLB 투수가 수백 명이라 차원이 폭발하고, 투수 간 유사성도 반영되지 않는다
- 통계 피처만 사용 (Embedding 없이)
  - 표본이 적은 신인 투수에게는 안정적이지만, 표본이 많은 투수의 미묘한 성향 차이를 담기 어렵다

> 결정
> BiLSTM + 투수/타자 Embedding(16차원) + 상황 컨텍스트 Dense 브랜치를 병렬로 결합하는 구조를 채택했다. 여기에 통계적으로 계산된 투수 성향 피처(구종 비율, 카운트별 최빈 구종, 상대전적)를 추가로 넣어 Embedding과 상호보완시켰다.

결과

- 시퀀스 방향성, 정형 컨텍스트, 개인화(Embedding)를 한 모델에서 함께 다룰 수 있게 됐다
- 알려진 한계: 등판 표본이 적은 신인 투수의 Embedding은 잘 학습되지 않을 가능성이 크다
- 알려진 한계: 투수 성향 통계 피처가 시즌 전체 데이터로 계산되어, 시즌 중 실시간 서비스에서는 미래 정보 누수(data leakage) 소지가 있다. 예측 시점 이전 데이터만 누적 반영하도록 고치는 작업이 로드맵에 남아 있다
- 단방향 LSTM과의 정량 비교는 아직 수행하지 않았다

## ADR-0003 · 서비스 프로토타입에 Streamlit 채택

- 날짜: 2026-07-27 (Day 1 정리 기준, 최초 결정 시점은 이전)
- 상태: 채택됨
- 관련 근거: streamlit_app/app.py, docs/blog/day1.md

배경

- BiLSTM 구종 예측과 YOLOv8+모션 감지 기반 영상 분석, 두 파이프라인을 하나의 실사용 가능한 데모로 빠르게 묶어서 보여줄 방법이 필요했다

검토한 대안

- FastAPI/Django + 별도 프론트엔드
  - 유연하지만 백그라운드 스레드·세션 상태·실시간 갱신 UI를 처음부터 직접 구현해야 해서 프로토타이핑 속도가 느리다
- Jupyter/Gradio
  - 빠르지만 다이아몬드·카운트 시각화 같은 커스텀 대시보드 레이아웃을 만들기엔 제약이 크다

> 결정
> 빠르게 프로토타입을 서비스 형태로 보여줄 수 있는 Streamlit을 선택했다. streamlit_app/app.py(1,500줄 이상)에 MLB 경기 선택, YouTube 영상 연동/캐싱, 백그라운드 스레드 기반 실시간 스캔, OCR, 다이아몬드/카운트 시각화까지 구현했다.

결과

- 단기간에 실사용 가능한 대시보드를 완성할 수 있었다
- Streamlit의 세션 상태·rerun 모델과 백그라운드 스레드·캐시 관리 사이에서 겪은 어려움이 있었다 (자세한 내용은 배포 단계 트러블슈팅으로 별도 정리 예정)
- 무료 배포 환경(Streamlit Community Cloud)의 리소스 제약으로 YouTube 연동·실시간 스캔이 로컬만큼 안정적으로 동작하지 않을 수 있다는 한계를 README의 Known Limitations에 명시했다

## ADR-0004 · 투구 타이밍 감지: 포즈 추정 대신 프레임 차이 기반 모션 감지

- 날짜: 2026-08-03 (README 갱신 기준, 최초 전환 시점은 이전)
- 상태: 채택됨
- 관련 근거: src/pose_detector.py, README.md ("Phase 2에서 포즈 추정을 시도했다가 정확도/속도 문제로 모션 감지로 전환")

배경

- 투구 타이밍을 자동으로 인식하려면 투수의 투구 동작을 영상에서 감지해야 한다
- 모듈명은 pose_detector.py이지만 실제 구현은 포즈 추정(관절 keypoint 추정)이 아니라 OpenCV 프레임 차이 기반 모션 감지다

검토한 대안

- 포즈 추정 모델 (MediaPipe 등 keypoint 기반)
  - README에 명시된 대로 Phase 2에서 실제로 시도했으나, 정확도/속도 문제로 채택되지 않았다
  - 구체적인 실패 지표는 별도 devlog로 아직 문서화되지 않음. 재현 가능한 수치가 확보되면 트러블슈팅 기록으로 승격할 것
- YOLO 단독으로 공의 등장/사라짐만 추적
  - 방송 화면 앵글이 매번 다르고 공이 작아 놓치는 경우가 있어, 마운드 영역의 큰 모션 변화를 함께 보는 편이 더 안정적이었다

> 결정
> 투수 마운드 영역에서 프레임 간 픽셀 차이가 임계값을 넘고, 순간적인 카메라 전환(단발 고모션)과 구분되는 지속적인 모션 패턴이 나타나는 시점을 투구 타이밍으로 판단하는 detect_pitch_motion()을 채택했다. load_pose_model() 등 기존 인터페이스 이름은 호환을 위해 그대로 남겨뒀다.

결과

- keypoint 모델 없이도 순수 OpenCV만으로 실시간에 가까운 속도로 동작한다
- 모듈/함수 이름(pose_detector, load_pose_model)이 실제 구현(모션 감지)과 불일치해 코드를 처음 보는 사람에게 혼동을 줄 수 있다. 코드 상단 docstring에 "OpenCV 프레임 차이 기반 모션 감지"라고 명시해 최소한의 안내를 남겨뒀다
- 카메라 앵글이 크게 바뀌는 영상에서는 오탐(false positive) 가능성이 있어, 카메라 전환 필터(max가 avg의 2배 이상) 조건으로 일부 보정하고 있다

## ADR-0005 · 시퀀스 길이(SEQUENCE_LENGTH) 기본값 5 → 3 변경

- 날짜: 2026-08-03
- 상태: 채택됨 (실험 근거 있음)
- 관련 근거: src/feature_engineering.py, docs/blog/day2.md, 커밋 f75371d

배경

- 기존 SEQUENCE_LENGTH=5가 왜 5인지 코드/문서에 근거가 남아있지 않았다
- build_sequences()는 한 타석 안에서 직전 seq_len구 + 다음 1구가 있어야 학습 샘플 하나를 만들기 때문에, seq_len이 커질수록 조건을 만족하는 타석 수 자체가 줄어든다는 구조적 트레이드오프가 있다

검토한 대안

2025 시즌 전체 데이터(69만 5천 투구)로 seq_len 3 / 5(기존) / 8을 직접 비교했다.

- seq_len 3
  - 시퀀스 개수 227,235개 · 전체 정확도 48.4% · Macro F1 43.4%
- seq_len 5 (기존)
  - 시퀀스 개수 61,318개 · 전체 정확도 46.6% · Macro F1 39.2%
- seq_len 8
  - 시퀀스 개수 3,494개 · 전체 정확도 38.5% · Macro F1 16.3%
  - 검증셋 샘플이 너무 적어 recall 0%인 클래스가 다수 발생, 신뢰하기 어려운 수치

> 결정
> SEQUENCE_LENGTH 기본값을 3으로 변경했다. 이 값으로 재학습한 모델(전체 정확도 48.5%, Macro F1 43.4%)로 models/pitch_predictor.h5를 교체했다.

결과

- 정확도·Macro F1 모두 개선됐다
- CU(21.9%→27.1%), FS(39.1%→52.0%), OTHER(29.1%→41.6%) 등 소수 클래스 recall도 함께 상승해, 단순히 다수 클래스 쏠림이 심해진 결과가 아님을 확인했다
- 문맥을 더 준다고 항상 좋아지는 게 아니라, 그 문맥을 만들기 위해 버려지는 데이터가 더 큰 손해일 수 있다는 것이 정량적으로 확인됐다
- README와 notebooks/figures/의 성능 표·그래프도 이 모델 기준으로 갱신했다

## ADR-0006 · 클래스 불균형 보정(class weight) 미사용 유지

- 날짜: 2026-08-03
- 상태: 채택됨 (실험 근거 있음)
- 관련 근거: src/model.py (_compute_class_weights(), train(..., use_class_weight=True)), docs/blog/day2.md

배경

- 구종 분포가 균등하지 않다 (FF 34.3% ~ FS 3.3%)
- model.py에는 이미 _compute_class_weights()가 구현돼 있었지만 train()에서 실제로 호출되지는 않고 있었다

검토한 대안

같은 시즌 데이터, seq_len=5, 동일 train/val split, 동일 EarlyStopping 조건으로 class weight 적용 여부를 비교했다.

- class weight 없음 (baseline)
  - 전체 정확도 46.6% · Macro F1 39.2% · FF recall 70.5% · FS recall 39.1% · CU recall 21.9%
- class weight 적용 (balanced)
  - 전체 정확도 37.4% · Macro F1 38.4% · FF recall 15.9% · FS recall 79.9% · CU recall 51.9%

class weight를 켜면 희귀 구종(FS 39%→80%, CU 21.9%→51.9%) recall은 크게 오르지만, 최다 구종 FF의 recall이 70.5%→15.9%로 무너지면서 전체 정확도는 물론 Macro F1까지 함께 하락했다. 보통 기대하는 "정확도는 내려가도 Macro F1은 오르는" 트레이드오프조차 성립하지 않았다.

> 결정
> use_class_weight=False를 기본값으로 유지한다. _compute_class_weights()와 옵션 자체는 코드에 남겨 다른 시도(가중치 상한, focal loss 등)의 여지를 열어둔다.

결과

- 현재 모델은 다수 클래스(FF 등) 위주로 학습되며, 희귀 구종(FS, CU) recall은 상대적으로 낮게 유지된다
- balanced 가중치가 FF-FS 간 빈도 차이(약 10배)를 그대로 loss에 반영하면서, 원래 구별이 쉬운 구종(구속·무브먼트 차이 큼)까지 과소예측하도록 편향시켰을 가능성이 있다. 이는 재현된 관측이지 결론이 확정된 가설은 아니다
- 후속 실험 후보로 가중치 상한 설정, focal loss 대체가 로드맵에 남아 있다

## ADR-0007 · Git 히스토리 재시작(squash)

- 날짜: 2026-07-27
- 상태: 채택됨
- 관련 근거: 커밋 85298e6 (Restart project history with a clean, reproducible snapshot), docs/blog/day1.md, docs/TROUBLESHOOTING.md의 TS-001

배경

- 커밋이 4개뿐인 저장소인데도 .git이 2GB에 가까웠다 (docs/TROUBLESHOOTING.md TS-001 참고)
- 원인은 이전 커밋들에 반복적으로 커밋된 대용량 Statcast CSV, YOLO 사전학습 가중치, 학습된 모델이었다

검토한 대안

- git filter-repo로 과거 이력에서 대용량 blob만 제거
  - 이력을 그대로 유지할 수 있지만, 이미 public 저장소라 필터링 과정에서 실수할 경우 이력이 꼬일 위험이 있고, 커밋이 4개뿐이라 얻는 이득도 적었다
- 현재 상태 기준으로 새 히스토리 시작
  - 이력은 짧아지지만, public 저장소의 과거 이력에 민감정보가 없는지 다시 검토해야 했고, 기존 히스토리를 로컬 브랜치로 보존하면 완전히 잃는 것도 아니었다

> 결정
> 새 root 커밋으로 히스토리를 재시작했다. 데이터 수집, 피처 엔지니어링, BiLSTM 모델, YOLOv8 공 탐지, 모션 기반 투구 타이밍 감지, Streamlit 대시보드까지의 이전 작업을 하나의 재현 가능한 스냅샷 커밋으로 스쿼시했다. 기존 히스토리는 별도 로컬 브랜치로 보존했다.

결과

- 새 클론 시 저장소 용량이 크게 줄어든다
- 커밋 히스토리 자체가 개발 과정을 보여주는 자료로서의 가치를 갖기 어려워졌다. 이후 docs/blog/로 개발 일지를 남겨 이 공백을 보완하는 방향을 택했다
- 이 시점부터 서비스 필수 모델 3종만 Git LFS로 추적한다 (ADR-0008)

## ADR-0008 · 서비스 필수 모델 3종만 Git LFS로 추적

- 날짜: 2026-07-27
- 상태: 채택됨
- 관련 근거: .gitattributes, .gitignore, docs/blog/day1.md

배경

- Git 히스토리를 재시작하면서(ADR-0007), 어떤 대용량 파일을 다시 저장소에 넣을지 결정해야 했다
- 모델 가중치(.h5, .pt)와 스케일러(.pkl)는 일반 Git blob으로 커밋하면 diff 관리도 안 되고 저장소가 다시 무거워진다

검토한 대안

- 모든 산출물을 그대로 Git에 커밋
  - 이전에 .git이 2GB까지 커졌던 것과 같은 문제가 재발한다
- 모델 파일을 아예 저장소에서 제외하고 별도 다운로드 스크립트 제공
  - 재현성은 확보되지만, 클론 직후 바로 앱을 실행해볼 수 없어 포트폴리오/데모 목적에는 마찰이 크다
- 재수집·재학습 가능한 모든 산출물(원본 CSV, YOLO 학습셋, 사전학습 체크포인트)까지 LFS로 추적
  - 서비스 실행에 필요하지 않은 파일까지 LFS 용량을 차지하게 된다

> 결정
> 서비스(streamlit_app/app.py, src/pipeline.py)가 실제로 로드해서 쓰는 모델 3개만 Git LFS로 추적한다.
>
> ```
> models/pitch_predictor.h5
> models/scaler.pkl
> models/baseball_detector.pt
> ```
>
> 재수집/재학습 가능한 원본 데이터(Statcast CSV), YOLO 학습 데이터셋, 사전학습 체크포인트, 학습 실험 산출물(runs/)은 .gitignore로 계속 제외한다.

결과

- 클론 후 git lfs pull만으로 서비스 실행에 필요한 모델을 바로 받을 수 있어 재현성이 확보된다
- 저장소 크기가 재수집 가능한 대용량 데이터로 다시 불어나는 것을 막는다
- LFS 자체의 대역폭/용량 제한(호스팅 플랫폼 정책)에는 의존하게 된다. 현재 3개 파일 규모에서는 문제가 되지 않았다
