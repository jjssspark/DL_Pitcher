## ADR-0001 · 야구공 탐지에 YOLOv8n 채택

- 날짜: 2026-07-27 (Day 1 정리 기준, 최초 결정 시점은 이전)
- 상태: **대체됨 — ADR-0009 (2026-08-06)**
- 관련 근거: src/yolo_detector.py, src/train_yolo.py, models/baseball_detector.pt, docs/blog/day1.md

> **주의 — 아래 "결과"는 사실이 아님이 확인됐다.**
> 2026-08-05 실측에서 `models/baseball_detector.pt`의 중계 영상 감지율은 3%였고,
> 12px 이하(중계 앵글에서의 실제 공 크기) 감지는 **0건**이었다. 이 ADR이 "공 탐지가
> 가능해졌다"고 적은 근거는 학습 데이터셋 내부의 검증 지표(mAP50 0.852)였는데, 그
> 데이터셋은 야구공 제품 사진·사인볼 수집품·리틀리그 스냅샷이었다. 배포 도메인(중계
> 와이드 앵글)의 이미지는 한 장도 없었다.
> 상세: docs/TROUBLESHOOTING.md TS-014. 대체 결정: ADR-0009.

배경

- 중계 영상에서 투구 타이밍을 자동으로 잡아내려면 화면 속 작은 객체(야구공)를 실시간에 가까운 속도로 탐지해야 한다
- 커스텀 학습(자체 라벨링한 야구공 데이터셋)도 필요했다

검토한 대안

- 더 큰 YOLOv8 변형(s/m/l)
  - 정확도는 높지만 Streamlit 무료 배포 환경 등 리소스 제약 환경에서 추론 속도가 떨어진다
- 범용 사전학습 객체탐지 모델 그대로 사용
  - 야구공처럼 작고 빠르게 움직이는 객체는 COCO 등 범용 데이터셋 기준 사전학습 가중치만으로는 탐지율이 낮다

> 결정
> 가볍고 커스텀 학습이 쉬운 YOLOv8n을 base로 선택하고, 야구공 데이터로 자체 파인튜닝(train_yolo.py)해 baseball_detector.pt를 만들었다. 추론 시에는 적응형 프레임 샘플링으로 속도를 추가로 최적화했다.

결과

- ~~실시간에 가까운 속도로 공 탐지가 가능해졌다~~ → **틀렸다.** 속도는 맞았지만 탐지가 안 됐다. 중계 영상 감지율 3%, 실제 공 크기 감지 0건 (TS-014)
- nano 모델이라 정확도 상한은 더 큰 모델보다 낮을 수 있다. 현재는 이 트레이드오프를 리소스 제약 하에서 감수하는 쪽을 택했다
  - → nano 선택 자체는 문제가 아니었다. 같은 yolov8n을 **중계 도메인 데이터로** 재파인튜닝하니 동작했다 (ADR-0009). 병목은 모델 크기가 아니라 학습 데이터 도메인이었다
- 이후 투구 타이밍 감지 자체는 YOLO 단독이 아니라 ADR-0004(모션 감지)와 병행하는 구조로 진화했다
  - → 이 "진화"는 설계 개선이 아니라 **공 탐지 실패에 대한 무의식적 우회**였을 가능성이 크다. 공이 잡히지 않으니 모션 감지에 의존하게 됐고, 그 사실이 드러나지 않은 채 아키텍처로 굳었다

이 ADR에서 배운 것

- **"검토한 대안"에서 범용 사전학습 모델을 "탐지율이 낮다"고 배제한 판단은 옳았다.** 그런데 자체 파인튜닝한 모델도 같은 이유로 실패한다는 것은 검증하지 않았다. 데이터셋을 바꿨을 뿐 **도메인이 여전히 배포 환경과 달랐기 때문**이다
- 결정 자체(YOLOv8n base + 자체 파인튜닝)는 유효했다. 틀린 것은 "자체 학습했으니 우리 도메인에 맞다"는 암묵적 전제였다

## ADR-0002 · 다음 구종 예측에 BiLSTM + Embedding 구조 채택

- 날짜: 2026-08-03 (Day 2 재정리 기준)
- 상태: 채택됨
- 관련 근거: src/model.py, src/feature_engineering.py, docs/blog/day2.md

배경

- 다음 구종 예측에는 두 종류의 정보가 섞여 있다
  - 순서가 있는 정보: 직전 몇 구의 시퀀스
  - 순서가 없는 정형 정보: 카운트·주자·점수차
  - 투수/타자별 성향(고차원 범주형)

검토한 대안

- 단방향 LSTM
  - 실시간 추론이라면 미래 정보를 볼 수 없어 자연스러운 선택이지만, 이 문제는 이미 완결된 직전 시퀀스를 통째로 넣고 다음 구종을 맞히는 구조라 양방향 문맥을 다 쓰는 게 유리하다고 판단했다
  - 다만 실제 A/B 비교는 하지 않았다 (후속 실험 후보로 남김)
- 투수/타자 ID 원-핫 인코딩
  - MLB 투수가 수백 명이라 차원이 폭발하고, 투수 간 유사성도 반영되지 않는다
- 통계 피처만 사용 (Embedding 없이)
  - 표본이 적은 신인 투수에게는 안정적이지만, 표본이 많은 투수의 미묘한 성향 차이를 담기 어렵다

> 결정
> BiLSTM + 투수/타자 Embedding(16차원) + 상황 컨텍스트 Dense 브랜치를 병렬로 결합하는 구조를 채택했다. 여기에 통계적으로 계산된 투수 성향 피처(구종 비율, 카운트별 최빈 구종, 상대전적)를 추가로 넣어 Embedding과 상호보완시켰다.

결과

- 시퀀스 방향성, 정형 컨텍스트, 개인화(Embedding)를 한 모델에서 함께 다룰 수 있게 됐다
- 알려진 한계: 등판 표본이 적은 신인 투수의 Embedding은 잘 학습되지 않을 가능성이 크다
- 알려진 한계: 투수 성향 통계 피처가 시즌 전체 데이터로 계산되어, 시즌 중 실시간 서비스에서는 미래 정보 누수(data leakage) 소지가 있다. 예측 시점 이전 데이터만 누적 반영하도록 고치는 작업이 로드맵에 남아 있다
- 단방향 LSTM과의 정량 비교는 아직 수행하지 않았다

## ADR-0003 · 서비스 프로토타입에 Streamlit 채택

- 날짜: 2026-07-27 (Day 1 정리 기준, 최초 결정 시점은 이전)
- 상태: 채택됨
- 관련 근거: streamlit_app/app.py, docs/blog/day1.md

배경

- BiLSTM 구종 예측과 YOLOv8+모션 감지 기반 영상 분석, 두 파이프라인을 하나의 실사용 가능한 데모로 빠르게 묶어서 보여줄 방법이 필요했다

검토한 대안

- FastAPI/Django + 별도 프론트엔드
  - 유연하지만 백그라운드 스레드·세션 상태·실시간 갱신 UI를 처음부터 직접 구현해야 해서 프로토타이핑 속도가 느리다
- Jupyter/Gradio
  - 빠르지만 다이아몬드·카운트 시각화 같은 커스텀 대시보드 레이아웃을 만들기엔 제약이 크다

> 결정
> 빠르게 프로토타입을 서비스 형태로 보여줄 수 있는 Streamlit을 선택했다. streamlit_app/app.py(1,500줄 이상)에 MLB 경기 선택, YouTube 영상 연동/캐싱, 백그라운드 스레드 기반 실시간 스캔, OCR, 다이아몬드/카운트 시각화까지 구현했다.

결과

- 단기간에 실사용 가능한 대시보드를 완성할 수 있었다
- Streamlit의 세션 상태·rerun 모델과 백그라운드 스레드·캐시 관리 사이에서 겪은 어려움이 있었다 (자세한 내용은 배포 단계 트러블슈팅으로 별도 정리 예정)
- 무료 배포 환경(Streamlit Community Cloud)의 리소스 제약으로 YouTube 연동·실시간 스캔이 로컬만큼 안정적으로 동작하지 않을 수 있다는 한계를 README의 Known Limitations에 명시했다

## ADR-0004 · 투구 타이밍 감지: 포즈 추정 대신 프레임 차이 기반 모션 감지

- 날짜: 2026-08-03 (README 갱신 기준, 최초 전환 시점은 이전)
- 상태: 채택됨
- 관련 근거: src/pose_detector.py, README.md ("Phase 2에서 포즈 추정을 시도했다가 정확도/속도 문제로 모션 감지로 전환")

배경

- 투구 타이밍을 자동으로 인식하려면 투수의 투구 동작을 영상에서 감지해야 한다
- 모듈명은 pose_detector.py이지만 실제 구현은 포즈 추정(관절 keypoint 추정)이 아니라 OpenCV 프레임 차이 기반 모션 감지다

검토한 대안

- 포즈 추정 모델 (MediaPipe 등 keypoint 기반)
  - README에 명시된 대로 Phase 2에서 실제로 시도했으나, 정확도/속도 문제로 채택되지 않았다
  - 구체적인 실패 지표는 별도 devlog로 아직 문서화되지 않음. 재현 가능한 수치가 확보되면 트러블슈팅 기록으로 승격할 것
- YOLO 단독으로 공의 등장/사라짐만 추적
  - 방송 화면 앵글이 매번 다르고 공이 작아 놓치는 경우가 있어, 마운드 영역의 큰 모션 변화를 함께 보는 편이 더 안정적이었다

> 결정
> 투수 마운드 영역에서 프레임 간 픽셀 차이가 임계값을 넘고, 순간적인 카메라 전환(단발 고모션)과 구분되는 지속적인 모션 패턴이 나타나는 시점을 투구 타이밍으로 판단하는 detect_pitch_motion()을 채택했다. load_pose_model() 등 기존 인터페이스 이름은 호환을 위해 그대로 남겨뒀다.

결과

- keypoint 모델 없이도 순수 OpenCV만으로 실시간에 가까운 속도로 동작한다
- 모듈/함수 이름(pose_detector, load_pose_model)이 실제 구현(모션 감지)과 불일치해 코드를 처음 보는 사람에게 혼동을 줄 수 있다. 코드 상단 docstring에 "OpenCV 프레임 차이 기반 모션 감지"라고 명시해 최소한의 안내를 남겨뒀다
- 카메라 앵글이 크게 바뀌는 영상에서는 오탐(false positive) 가능성이 있어, 카메라 전환 필터(max가 avg의 2배 이상) 조건으로 일부 보정하고 있다

## ADR-0005 · 시퀀스 길이(SEQUENCE_LENGTH) 기본값 5 → 3 변경

- 날짜: 2026-08-03
- 상태: 채택됨 (실험 근거 있음)
- 관련 근거: src/feature_engineering.py, docs/blog/day2.md, 커밋 f75371d

배경

- 기존 SEQUENCE_LENGTH=5가 왜 5인지 코드/문서에 근거가 남아있지 않았다
- build_sequences()는 한 타석 안에서 직전 seq_len구 + 다음 1구가 있어야 학습 샘플 하나를 만들기 때문에, seq_len이 커질수록 조건을 만족하는 타석 수 자체가 줄어든다는 구조적 트레이드오프가 있다

검토한 대안

2025 시즌 전체 데이터(69만 5천 투구)로 seq_len 3 / 5(기존) / 8을 직접 비교했다.

- seq_len 3
  - 시퀀스 개수 227,235개 · 전체 정확도 48.4% · Macro F1 43.4%
- seq_len 5 (기존)
  - 시퀀스 개수 61,318개 · 전체 정확도 46.6% · Macro F1 39.2%
- seq_len 8
  - 시퀀스 개수 3,494개 · 전체 정확도 38.5% · Macro F1 16.3%
  - 검증셋 샘플이 너무 적어 recall 0%인 클래스가 다수 발생, 신뢰하기 어려운 수치

> 결정
> SEQUENCE_LENGTH 기본값을 3으로 변경했다. 이 값으로 재학습한 모델(전체 정확도 48.5%, Macro F1 43.4%)로 models/pitch_predictor.h5를 교체했다.

결과

- 정확도·Macro F1 모두 개선됐다
- CU(21.9%→27.1%), FS(39.1%→52.0%), OTHER(29.1%→41.6%) 등 소수 클래스 recall도 함께 상승해, 단순히 다수 클래스 쏠림이 심해진 결과가 아님을 확인했다
- 문맥을 더 준다고 항상 좋아지는 게 아니라, 그 문맥을 만들기 위해 버려지는 데이터가 더 큰 손해일 수 있다는 것이 정량적으로 확인됐다
- README와 notebooks/figures/의 성능 표·그래프도 이 모델 기준으로 갱신했다

## ADR-0006 · 클래스 불균형 보정(class weight) 미사용 유지

- 날짜: 2026-08-03
- 상태: 채택됨 (실험 근거 있음)
- 관련 근거: src/model.py (_compute_class_weights(), train(..., use_class_weight=True)), docs/blog/day2.md

배경

- 구종 분포가 균등하지 않다 (FF 34.3% ~ FS 3.3%)
- model.py에는 이미 _compute_class_weights()가 구현돼 있었지만 train()에서 실제로 호출되지는 않고 있었다

검토한 대안

같은 시즌 데이터, seq_len=5, 동일 train/val split, 동일 EarlyStopping 조건으로 class weight 적용 여부를 비교했다.

- class weight 없음 (baseline)
  - 전체 정확도 46.6% · Macro F1 39.2% · FF recall 70.5% · FS recall 39.1% · CU recall 21.9%
- class weight 적용 (balanced)
  - 전체 정확도 37.4% · Macro F1 38.4% · FF recall 15.9% · FS recall 79.9% · CU recall 51.9%

class weight를 켜면 희귀 구종(FS 39%→80%, CU 21.9%→51.9%) recall은 크게 오르지만, 최다 구종 FF의 recall이 70.5%→15.9%로 무너지면서 전체 정확도는 물론 Macro F1까지 함께 하락했다. 보통 기대하는 "정확도는 내려가도 Macro F1은 오르는" 트레이드오프조차 성립하지 않았다.

> 결정
> use_class_weight=False를 기본값으로 유지한다. _compute_class_weights()와 옵션 자체는 코드에 남겨 다른 시도(가중치 상한, focal loss 등)의 여지를 열어둔다.

결과

- 현재 모델은 다수 클래스(FF 등) 위주로 학습되며, 희귀 구종(FS, CU) recall은 상대적으로 낮게 유지된다
- balanced 가중치가 FF-FS 간 빈도 차이(약 10배)를 그대로 loss에 반영하면서, 원래 구별이 쉬운 구종(구속·무브먼트 차이 큼)까지 과소예측하도록 편향시켰을 가능성이 있다. 이는 재현된 관측이지 결론이 확정된 가설은 아니다
- 후속 실험 후보로 가중치 상한 설정, focal loss 대체가 로드맵에 남아 있다

## ADR-0008 · 서비스 필수 모델 3종만 Git LFS로 추적

- 날짜: 2026-07-27
- 상태: 채택됨
- 관련 근거: .gitattributes, .gitignore, docs/blog/day1.md

배경

- Git 히스토리를 재시작하면서(ADR-0007), 어떤 대용량 파일을 다시 저장소에 넣을지 결정해야 했다
- 모델 가중치(.h5, .pt)와 스케일러(.pkl)는 일반 Git blob으로 커밋하면 diff 관리도 안 되고 저장소가 다시 무거워진다

검토한 대안

- 모든 산출물을 그대로 Git에 커밋
  - 이전에 .git이 2GB까지 커졌던 것과 같은 문제가 재발한다
- 모델 파일을 아예 저장소에서 제외하고 별도 다운로드 스크립트 제공
  - 재현성은 확보되지만, 클론 직후 바로 앱을 실행해볼 수 없어 포트폴리오/데모 목적에는 마찰이 크다
- 재수집·재학습 가능한 모든 산출물(원본 CSV, YOLO 학습셋, 사전학습 체크포인트)까지 LFS로 추적
  - 서비스 실행에 필요하지 않은 파일까지 LFS 용량을 차지하게 된다

> 결정
> 서비스(streamlit_app/app.py, src/pipeline.py)가 실제로 로드해서 쓰는 모델 3개만 Git LFS로 추적한다.
>
> ```
> models/pitch_predictor.h5
> models/scaler.pkl
> models/baseball_detector.pt
> ```
>
> 재수집/재학습 가능한 원본 데이터(Statcast CSV), YOLO 학습 데이터셋, 사전학습 체크포인트, 학습 실험 산출물(runs/)은 .gitignore로 계속 제외한다.

결과

- 클론 후 git lfs pull만으로 서비스 실행에 필요한 모델을 바로 받을 수 있어 재현성이 확보된다
- 저장소 크기가 재수집 가능한 대용량 데이터로 다시 불어나는 것을 막는다
- LFS 자체의 대역폭/용량 제한(호스팅 플랫폼 정책)에는 의존하게 된다. 현재 3개 파일 규모에서는 문제가 되지 않았다

## ADR-0009 · 야구공 탐지기를 중계 도메인 데이터셋으로 재파인튜닝 (ADR-0001 대체)

                  감지된 프레임    박스 최대변 중앙값   12px 이하(실제 공)
  COCO yolov8n     575/1230 (47%)        49px            0건
  커스텀            41/1230 ( 3%)        73px            0건
  ```

  두 모델 모두 공이 아니라 투수 글러브를 잡고 있었다. 궤적 기반 구종 분류의 성능이

검토한 대안

- **직접 라벨링해 학습셋 구축**

  - 중계 컷 전환에도 취약하다
- **궤적을 포기하고 자세 추정 기반 특징으로 선회**
  - `src/pose_detector.py`는 이름과 달리 실제로는 프레임 차분 모션 감지라(ADR-0004),
    진짜 포즈 추정을 하려면 별도 구현이 필요하다
- **공개된 중계 도메인 데이터셋으로 재파인튜닝** ← 채택
  - Roboflow `pitchtracking/baseball-detection-2` v4를 육안 확인했다. MLB 중계 센터필드
    앵글, 클래스 `baseball` 1개, CC BY 4.0, 4,153장

> 결정
> 같은 yolov8n base를 유지하되 학습 데이터를 중계 도메인으로 교체했다. 다운로드 직후
> 라벨 박스 크기 분포를 정량 확인하고(최대변 중앙값 13px, 25px 이하 100%, 49px 초과 0%),
> GT 박스를 렌더링해 6개 구장·중계사의 센터필드 앵글임을 눈으로 확인한 뒤 학습에 들어갔다.
>
> ```
> 모델   models/ball_broadcast_v1.pt  (yolov8n 33에폭, mAP50 0.960)
> 추론   imgsz=960, conf=0.05         <- 둘 다 필수
> 궤적   longest_moving_chain(candidates, max_jump_px=60, min_total_move_px=30)
> ```

추론 설정이 기본값이 아닌 이유

- **imgsz 960**: 데이터셋 전처리가 1280x720을 640x640으로 눌러(stretch) 만든 것이라 640
  추론은 공이 너무 작고, 1280은 학습 시점 대비 과대하다. 실측에서 960이 궤적 사슬 최대였다
- **conf 0.05**: Ultralytics `model()`의 기본 임계값은 0.25인데 이 도메인의 공은 그 아래로
  내려간다. `yolo_detector.CONF_THRESHOLD = 0.15`는 모델이 이미 0.25에서 잘라낸 결과를 다시
  거르고 있어 **한 번도 작동한 적이 없었다** (TS-018). 실제로 낮추려면 모델에 직접 넘겨야 한다

결과

- 감지 게이트 통과: 8투구 중 **7개(88%)**에서 이동 사슬 5프레임 이상 확보, 사슬 길이 중앙값
  7프레임, 박스 최대변 중앙값 21px
- 궤적이 물리적으로 타당하다. 너클커브는 최고점 후 낙차가 가속하고(y: 245 241 240 242 246
  254 263 276 306), 싱커는 처음부터 단조 낙하한다(y: 285 289 295 301 310 320 330 342)
- 구종 분류가 처음으로 기준선을 유의하게 넘었다: 홀드아웃 **0.612 vs 최빈값 기준선 0.510**,
  5-fold CV 0.664 ± 0.077, 순열검정 1000회 **p = 0.017**
- 특징 중요도가 집중됐다. 최대/최소 비 **4.95** (TS-014 당시 1.23으로 완전히 평평했다).
  상위는 `apparent_speed_px_per_frame` 0.301, `curvature_ratio` 0.250으로 구속과 휘어짐 —
  구종을 가르는 물리량이 맞다

- **선택 편향**. 궤적 확보율이 FASTBALL 63.1% / BREAKING 71.6% / OFFSPEED 86.7%로 균일하지
  않다. 빠른 공일수록 프레임 간 이동이 커서 사슬이 끊긴다. 현재 수치는 전체 투구가 아니라
  "궤적이 잡히는 68%"를 대표한다
- **1경기뿐**이라 `game_pk` 단위 홀드아웃이 불가능하고, 현재 수치는 누수 허용 상한이다
- **가중치가 저장소에 없다**. 24MB라 `.gitignore`의 `*.pt`에 걸린다. ADR-0008의 LFS 3종에
  추가할지는 파일럿이 서비스에 통합될 때 결정한다. 재학습 명령은 docs/NEXT_SESSION.md에 있다
- 궤적 필터가 여러 차례 우회당했다. 정지 오탐이 사슬의 앞·중간·뒤·전체 어디로든 들어왔고,
  최종적으로 사슬 구성 **전에** 정지 후보를 제거하는 방식으로 해결했다 (TS-017, TS-019)

- **학습 지표는 학습 도메인 안에서만 유효하다.** ADR-0001의 mAP50 0.852는 진짜 점수였지만

  먼저 물어야 한다
- **그래서 이번에는 학습 전에 데이터셋을 검증했다.** 라벨 박스 크기 분포를 정량화하고 GT를
  렌더링해 눈으로 봤다. 이 10분이 ADR-0001의 실패를 반복하지 않게 했다
- **모델 교체 후에도 실제 영상에 박스를 그려 확인하는 것을 통과 기준으로 삼았다**
  (`scripts/verify_ball_detector.py`). mAP 숫자만 보고 넘어가지 않는다

## ADR-0010 · 구종 데이터 수집을 중계 OCR에서 StatsAPI + Savant 투구별 클립으로 전환

- 날짜: 2026-08-06
- 상태: 채택됨 (실측 근거 있음)
- 관련 근거: src/pitch_type_cv/savant_clips.py, src/pitch_type_cv/clip_dataset.py, scripts/calibrate_clip_window.py, scripts/build_pitch_group_clips_dataset.py, docs/TROUBLESHOOTING.md TS-020 / TS-021

배경

- ADR-0009로 감지기 문제가 해결된 뒤 병목이 **데이터 규모**로 옮겨갔다. 남은 한계 세 개가
  전부 "1경기뿐"에서 나왔다
  - `game_pk`가 하나뿐이라 경기 단위 홀드아웃이 불가능 → 수치가 누수 허용 상한
  - 궤적 확보율이 그룹마다 달라 선택 편향 (FASTBALL 63% / BREAKING 72% / OFFSPEED 87%)
  - 홀드아웃 49개, OFFSPEED는 4개라 f1이 0.00
- OCR 경로는 경기 확장 비용이 크다. 경기당 720p 풀경기 다운로드 + 전체 스캔에 2시간대이고,
  **OCR 판독률 85%가 구조적 상한**이라 나머지 15%는 라벨을 얻을 수 없다
- 별개로 **위상 정렬 문제**가 있었다. OCR 타임스탬프와 실제 릴리스 사이 간격이 투구마다
  달라, 감지된 구간이 비행의 서로 다른 부분(초반/중반/종반)에 해당했다.
  `apparent_speed_px_per_frame`이 최상위 특징(0.301)인데 원근 압축 때문에 이 왜곡을
  직접 받는다 — 노이즈가 아니라 체계적 왜곡이다

검토한 대안

- **기존 OCR 경로 확장** (`GAME_LIST` 주석 해제로 6경기 추가)
  - 코드 변경이 없고 파이프라인이 이미 검증돼 있다
  - 경기당 2시간대 × 6경기 = 반나절. OCR 85% 상한과 위상 misalignment는 그대로 남는다
  - 공식 채널 FULL GAME 업로드가 있는 경기로 후보가 묶인다 — 구종 분포로 경기를 고를 수 없다
- **StatsAPI + Savant 투구별 클립** (채택)
  - 라벨을 `feed/live`의 `playEvents[].details.type.code`에서 직접 받는다. 후보 7경기 실측에서
    투구 전건(280/280 등)이 `playId`와 구종 코드를 모두 보유
  - 투구 1개 = 클립 1개(1280x720, 약 59.6fps, 4~5MB)라 타임스탬프 탐색이 불필요

결정

수집 경로를 (B)로 전환하되, **기존 OCR 경로는 삭제하지 않고 병렬로 남긴다**
(`dataset.py` ↔ `clip_dataset.py`, `build_pitch_group_dataset.py` ↔ `build_pitch_group_clips_dataset.py`).
감지 설정(imgsz 960 / conf 0.05 / `longest_moving_chain` 임계값)은 양쪽을 동일하게 맞춘다.

스캔 윈도우는 클립 시작 기준 **2.8~4.2초 고정**. 실측(775294, 60투구)에서 사슬 시작 시각의
5퍼센타일이 전 그룹 2.92초로 하한이 날카롭고(프리롤 고정), 그룹별 중앙값이
3.03 / 3.22 / 3.24초로 0.21초 안에 모여 구종별 위상 차이가 없다.

결과

| 지표 | OCR 경로 (1경기) | 클립 경로 (4경기) |
|---|---|---|
| 라벨 확보 | 85% (OCR 판독률 상한) | **100%** |
| 궤적 확보율 | 68% | **86.3%** |
| 사슬 점수 중앙값 | 7 | **11** |
| 학습 샘플 | 161 | **1030** |
| 홀드아웃 | 49 (투구 단위 분할, 누수) | **300 (game_pk 단위)** |
| 홀드아웃 OFFSPEED | 4 | **40** |
| 정확도 vs 기준선 | 0.612 vs 0.510 (+10.2%p) | 0.587 vs 0.483 (**+10.3%p**) |
| 순열검정 | p = 0.017 | **p < 0.001** |
| 특징 중요도 최대/최소 비 | 4.95 | 3.75 |

- **누수를 제거해도 성능 차이가 유지됐다.** +10.2%p → +10.3%p. 이전 수치가 누수로 부풀려진
  것이 아니었음을 확인한 것이 이번 측정의 핵심이다
- **위상 정렬 효과가 특징 순위에 나타났다.** 체계적 왜곡을 받던
  `apparent_speed_px_per_frame`이 1위(0.301)에서 4위(0.128)로 내려가고, 물리적으로 구종을
  가르는 `horizontal_deviation_px`(0.261)가 1위가 됐다
- **선택 편향은 남았다.** FASTBALL 80.9% / BREAKING 91.5% / OFFSPEED 90.5%. 다만 경기별로
  분해하면 FASTBALL이 71.4~92.4%로 편차가 21%p이고, 813027에서는 BREAKING(88.5%)을
  넘어선다. "빠른 공이라 사슬이 끊긴다"는 단일 설명으로는 맞지 않는다
- 부수 효과로 경기 선택이 자유로워져 OFFSPEED 비율이 높은 경기(813026, 29.3%)를 고를 수
  있었다. YouTube 풀경기 업로드 유무에 묶이지 않는다

## ADR-0011 · 궤적 캐시에 박스 크기를 남기고 v2로 분리

- 날짜: 2026-08-07
- 상태: 채택됨 (실측 근거 있음)
- 관련 근거: src/pitch_type_cv/trajectory_features.py, scripts/build_pitch_group_clips_dataset.py, scripts/eval_feature_sets.py, docs/TROUBLESHOOTING.md TS-023

배경

- ADR-0010으로 데이터 규모 문제가 풀린 뒤 남은 병목은 OFFSPEED였다. 홀드아웃 표본을
  4개에서 40개로 10배 늘렸는데도 f1 0.14, recall 0.10에 머물렀다 — 표본이 아니라 특징
  문제라는 뜻이다
- 기존 7개 특징은 전부 궤적의 기하학이다. 체인지업·스플리터를 패스트볼과 가르는 것은
  속도인데, 그 속도가 픽셀 단위라 원근에 오염돼 있다
- 좌표 기반 특징 7개(`frame_span`, `end_frame`, `speed_ratio_late_early`, `release_x`,
  `release_y`, `late_drop_ratio`, `vertical_accel_px`)를 추가해 실측했다. 전체 정확도는
  0.587 → 0.673으로 올랐지만 **OFFSPEED의 one-vs-rest AUC는 0.641 → 0.648로 제자리**였다
  (같은 실험에서 FASTBALL 0.792 → 0.851, BREAKING 0.725 → 0.819). 자세한 경위는 TS-023
- **픽셀 좌표만으로는 절대 속도를 복원할 수 없다는 것이 구조적 한계로 확인됐다.** 남은
  속도 대리 지표는 박스 크기 변화율 — 공이 카메라에 가까워지는 속도다

결정

1. `extract_trajectory_candidates`가 감지 후보를 `(x, y, conf)`가 아니라
   `(x, y, conf, w, h)`로 남긴다
2. 새 캐시를 `output/pitch_type_cv/clip_trajectory_cache_v2/`로 분리한다. v1은 지우지 않는다
3. `longest_moving_chain_frames`는 후보 튜플의 길이를 고정하지 않고 앞 두 값만 쓴다 —
   v1·v2 캐시를 모두 읽는다

근거

- **mp4는 처리 후 지운다** (4경기 × 4.5MB × 1193 = 약 5GB). 박스 크기를 지금 안 남기면
  재수집이 한 번 더 필요하고, 그 비용이 4경기 기준 약 150분이다
- **같은 디렉터리에 이어 쓰면 안 된다.** 빌드 스크립트는 `play_id`가 캐시에 있으면
  영상을 건너뛴다. v1이 1193건 전부 채워져 있으므로 같은 경로를 쓰면 재수집이 통째로
  스킵되고 박스 크기는 영영 안 들어온다
- **v1을 지우지 않는 이유**: 좌표 기반 특징을 다시 실험할 때 재취득 150분을 아낀다.
  좌표·신뢰도는 두 캐시가 동일하다(스모크 테스트에서 `(683.0, 328.0, 0.204)` 일치 확인)
- **길이를 고정하지 않은 파싱**: 스키마 버전 필드를 넣는 대신 튜플 길이를 무시하게 했다.
  판별할 것이 "박스 크기가 있나 없나" 하나뿐이라 버전 필드는 과하다

결과

- 감지 설정(imgsz 960 / conf 0.05)과 스캔 윈도우(2.8~4.2초)는 그대로다. 바뀐 것은
  **저장하는 필드뿐**이라 재수집이 같은 궤적을 재현한다
- 좌표 기반 확장 자체는 남긴다. OFFSPEED에는 실패했지만 전체 정확도를 기준선 대비
  +0.165 → +0.212로 올렸고(4경기 leave-one-game-out), 이 이득은 경기별로 일관됐다
- `FEATURE_COLUMNS`는 14개로 확정. 시간 계열 3개는 OFFSPEED를 못 움직였고 정확도
  기여도 미미하지만(11개 0.661 vs 14개 0.659, 폴드 간 편차 이내), 박스 크기가 들어온 뒤
  실제 속도와 결합할 축이라 남긴다

대안과 기각 사유

- **클래스 가중치로 OFFSPEED를 끌어올린다** — 기각. 가중치 8에서 f1 0.35 / recall 0.57로
  목표는 통과하지만 전체 정확도가 0.673 → 0.587로 정확히 원위치한다. AUC가 안 움직였으므로
  같은 ROC 곡선 위에서 동작점만 옮긴 것이다. 재수집으로 정보를 늘린 뒤 다시 볼 문제다
- **경기를 더 늘린다 (ADR-0010의 갈래 B)** — 보류. OFFSPEED AUC가 특징 추가에 반응하지
  않는 상태에서 표본만 늘리면 같은 f1을 볼 위험이 크다
- **캐시에 스키마 버전 필드를 넣고 한 디렉터리를 쓴다** — 기각. 버전이 섞인 캐시에서
  "이 경기는 어디까지 v2인가"를 추적해야 하고, 중단·재개 시 그 상태가 깨지기 쉽다

## ADR-0012 · 구종 분류 범위를 3분류에서 FASTBALL vs BREAKING 2분류로 축소

- 날짜: 2026-08-07
- 상태: 채택됨 (실측 근거 있음)
- 관련 근거: scripts/eval_feature_sets.py, scripts/eval_two_class.py,
  output/pitch_type_cv/{feature_ablation.csv, two_class_folds.csv},
  docs/TROUBLESHOOTING.md TS-023 / TS-024

배경

중계 영상 궤적만으로 FASTBALL / BREAKING / OFFSPEED 3분류를 하려 했다. OFFSPEED(체인지업·
스플리터)는 처음부터 막혀 있었고(f1 0.14, recall 0.10), 원인을 표본 부족으로 보고 4개 → 40개로
10배 늘렸으나 움직이지 않았다. 이후 두 갈래를 순서대로 시도했다.

1. 좌표 기반 특징 7개 추가 (재수집 불필요) — TS-023
2. 박스 크기 기반 특징 2개 추가 (전량 재수집 약 100분) — TS-024

검토한 대안

- 3분류를 유지하고 클래스 가중치로 OFFSPEED를 끌어올린다
- 3분류를 유지하고 경기 수를 늘린다
- 2분류로 축소한다
- Statcast `release_speed`를 입력 특징으로 쓴다

결정

**2분류로 축소한다.** 판정 근거는 one-vs-rest AUC다 — 임계값·클래스 가중치와 무관해서
"정보가 늘었나"와 "동작점을 옮겼나"를 갈라준다.

```
OFFSPEED LOGO AUC
  기준(7)      0.710
  +기하(11)    0.730   (+0.020)
  좌표전체(14) 0.724   (+0.014)
  +박스(16)    0.728   (+0.018)   <- 100분 재수집의 결과
```

특징을 7개에서 16개로 늘리는 동안 OFFSPEED AUC는 0.02 안에서만 움직였다. 같은 기간
FASTBALL은 0.778 → 0.850, BREAKING은 0.715 → 0.822로 올랐다. **정보가 들어간 곳과 안 들어간
곳이 명확히 갈린다.**

결과

```
3분류 (16특징)   LOGO 0.665  기준선 0.449  (+0.216)
2분류 (16특징)   LOGO 0.783  기준선 0.543  (+0.240)   평균 AUC 0.881
                 경기별 정확도 0.735 / 0.794 / 0.827 / 0.777
                 경기별 AUC    0.857 / 0.901 / 0.912 / 0.852
```

- 2분류가 3분류보다 기준선 대비 이득이 크고 경기별 편차도 작다
- 홀드아웃(game_pk=813027) f1은 FASTBALL 0.80 / BREAKING 0.75로 두 클래스가 균형 잡혀 있다
- `FEATURE_COLUMNS`는 16개 그대로 둔다. 박스 특징은 OFFSPEED엔 실패했지만 전체 정확도
  기준 최고 집합이고 `box_growth_per_frame`은 중요도 3위(0.054)다

대안과 기각 사유

- **클래스 가중치로 OFFSPEED를 끌어올린다** — 기각. 가중치 8에서 f1 0.35 / recall 0.57이지만
  전체 정확도가 정확히 원위치한다(0.673 → 0.587). AUC가 안 움직였으므로 새 정보가 아니라
  같은 ROC 곡선 위의 동작점 이동이다. ADR-0006(가중치 미사용)과도 일관된다
- **경기 수를 더 늘린다** — 기각(보류 아님). 표본을 10배 늘려도 안 움직였고, 특징을 9개
  추가해도 AUC가 0.02 안에 머물렀다. 두 축 모두에서 반응이 없는 상태라 경기만 늘리는 것은
  근거가 없다. 2분류의 정밀도를 올리는 목적이라면 유효하다
- **Statcast `release_speed`를 입력으로 쓴다** — 기각. 절대 속도가 있으면 OFFSPEED는 갈리지만
  "중계 영상만으로 예측"이라는 이 파일럿의 전제가 깨진다. 라벨 출처와 입력 출처가 같아져
  실사용에서 성립하지 않는 파이프라인이 된다

한계 명시

이 결정은 **OFFSPEED를 못 하는 것으로 확정한 것이 아니라, 중계 영상 궤적만으로는 못 한다는
경계를 그은 것**이다. 속도 정보가 있는 다른 입력(트래킹 데이터, 다중 카메라, 고프레임 촬영)이
생기면 3분류는 다시 열린다.

## ADR-0013 · 영상 타임라인을 균등 분할에서 스코어버그 앵커 보간으로

- 날짜: 2026-08-10
- 상태: 채택됨 (실측 근거 있음)
- 관련 근거: src/timeline_anchor.py, scripts/build_timeline_anchors.py,
  streamlit_app/fixed_demo_anchors.json, tests/test_timeline_anchor.py,
  docs/TROUBLESHOOTING.md TS-007 / TS-008 / TS-029

배경

앱은 영상 시각을 투구 인덱스로 바꿀 때 영상 길이를 투구 수로 균등 분할했다.
8231초 / 320구 = 25.72초마다 한 칸이다.

그런데 스캔된 실제 투구 간격은 중앙값 96.6초, 최소 12초, 최대 626초다. 광고·리플레이·
타자 교체·투수 교체 때문에 균등하지 않다. 평균은 맞지만 국소적으로는 계속 어긋나고,
사용자에게는 "타임라인이 공 한 개 느리다"로 보인다.

검토한 대안

- 그대로 두고 +1 보정만 한다
- 실시간 OCR로 매 투구를 감지해 인덱스를 올린다
- 스코어버그의 투수 투구수(P:N)를 미리 읽어 앵커로 삼고 사이를 보간한다
- 사전 스캔 시각(65개)의 순번을 그대로 인덱스로 쓴다

결정

세 번째. 오프라인에서 P:N을 읽어 (영상 시각, 투구 인덱스) 앵커를 만들고, 앱은 앵커
사이를 선형 보간한다.

근거

+1 보정은 초반만 가린다. 실측으로 균등 대비 오차가 초반 +1구에서 후반 +18구까지
벌어지므로 상수 보정으로는 못 맞춘다.

실시간 OCR은 비용이 막는다. 감지 자체는 좋지만(투구 시각 12/12 감지, 비투구 15곳
오탐 0) P:N 판독 한 번이 4.7~9.7초다. 재생 중에 돌리면 감지 주기가 그만큼 벌어져
오히려 손해다. 그래서 read_counter 파라미터로 분리해 오프라인에서만 켠다.

사전 스캔 순번을 그대로 쓰는 것도 안 된다. 65개는 320구 중 20%만 잡은 것이라
"i번째 감지 = i번째 투구"가 성립하지 않는다.

P:N은 투수별 카운트라 경기 전체에서 유일하지 않다. Statcast 투구 목록에서 투수별
누적 카운트를 세어 후보를 찾고, 균등 가정 추정치에 가장 가까운 것을 고른다.
균등 가정은 국소적으로 틀려도 전역 평균은 맞으므로 "어느 투수 구간인가"를 고르는
데는 충분하다.

실측

  P:N 판독      46/65 = 71%   (수정 전 0%)
  앵커 채택     33개          (시각·인덱스가 함께 증가하는 것만)
  균등 대비     평균 +8.6구, 초반 +1구 -> 후반 +18구

앵커 인덱스가 균등보다 크다 = 실제로는 균등이 가리키는 것보다 더 많은 투구가
지나갔다 = 타임라인이 뒤처져 있었다. 사용자가 보고한 "공 1개 느림"이 초반 +1구와
일치한다.

결과

- 앵커가 없으면 균등 분할과 완전히 같은 값을 준다. OCR이 실패한 경기에서도 앱은
  지금처럼 동작한다 (테스트로 고정).
- 이동(seek)도 같은 매핑의 역함수를 쓴다. 표시는 앵커 보간인데 이동만 균등이면
  버튼을 누른 순간 영상이 엉뚱한 데로 가고 다음 보고에서 인덱스가 도로 끌려간다.
- 앵커 파일은 streamlit_app/에 둔다. output/은 .gitignore 대상이라 거기 두면 다른
  환경에서 파일이 없어 조용히 균등 분할로 되돌아간다.

한계

- 앵커 사이는 여전히 선형 가정이다. 앵커 간격이 큰 구간(최대 1139초)에서는 어긋난다.
- P:N 오독은 실측에서 전부 감소 방향이었고 단조성으로 걸러진다. 증가 방향 오독이
  섞이면 잘못된 앵커가 채택될 수 있다 — 현재 데이터에서는 관측되지 않았다.
- 고정 데모 경기 하나에서만 검증했다. 다른 중계는 스코어버그 배치가 달라 크롭
  좌표(h 0.766~0.803, w 0.875~1.0)를 다시 잡아야 한다.

## ADR-0014 · 앵커 판독을 원본 seek OCR에서 오버레이 프록시 배열 OCR로, 오독 필터를 최장 증가 사슬로

- 날짜: 2026-08-11
- 상태: 채택됨 (홀드아웃 근거 있음)
- 관련 근거: scripts/scan_overlay_proxy.py, scripts/read_overlay_counters.py,
  scripts/build_anchors_from_overlay.py, src/timeline_anchor.py,
  streamlit_app/fixed_demo_anchors.json, docs/TROUBLESHOOTING.md TS-032 / TS-033

배경

ADR-0013으로 타임라인이 앵커 보간으로 바뀌었지만 앵커가 320구 중 33개뿐이었다.
사이는 직선 보간이고 최대 간격이 1139초(약 44구)라 그 구간에서는 여전히 어긋난다.

앵커를 늘리려면 P:N을 더 많이 읽어야 하는데 두 가지가 막고 있었다.

- 판독 1건에 8초다. 원본(1.1GB, 60fps)을 매번 seek 하기 때문이다. 조밀하게 훑으면
  8231초에 143분이 든다.
- 어디를 읽을지 모른다. TS-032에서 마운드 모션으로 투구 시각을 찾으려 했으나
  홀드아웃에서 균등 분할보다 나빠 폐기했다.

검토한 대안

- **원본 seek 유지, 후보만 줄인다** — 변화점을 찾아 수백 지점만 읽는다. 판독
  1건 8초는 그대로라 400지점에 53분이고, MPH 게이트를 놓치면 그마저 헛돈다.
- **오버레이 프록시 배열을 직접 읽는다** (채택) — ffmpeg으로 스코어버그 박스
  104x24만 4fps로 뽑아 배열(82MB)로 두고, 그 배열을 tesseract에 바로 넣는다.
- **조밀 OCR** — 1fps로 전량. tesseract 1회 1040ms라 143분. 탈락.

결정

(A) 프레임 공급을 프록시 배열로 바꾼다. 판독 규칙(임계값별 다수결, 정규식
`P[^0-9]{0,3}(\d{1,3})`, 두 표 이상)은 `pose_detector._read_pitch_counter`의 것을
그대로 쓴다. **검증된 것은 판독 규칙이고, 검증되지 않은 것은 원본 seek이었다.**

읽을 지점은 변화점이 아니라 **안정 구간**으로 정한다. 글자만 이진화(>190)해 XOR
하면 내용이 안 바뀌는 구간이 그대로 잘린다. 구간 안 픽셀은 동일하므로 구간마다
한 번만 읽으면 된다 (TS-033).

(B) `resolve_anchors`의 오독 필터를 그리디에서 최장 증가 사슬로 바꾼다. 길이가
같으면 앞선 관측을 쓴다 — 오독은 실측에서 전부 감소 방향이므로 나중에 온 작은
값보다 먼저 온 값이 맞다.

실측

| | 기존 (원본 seek) | 신규 (프록시 배열) |
|---|---|---|
| 판독 속도 | 8s/건 | **1.0s/건** |
| 같은 20지점 판독률 | 11/20 | **16/20** |
| 겹치는 값 일치 | — | 10/11 |

전체 소요: 프록시 생성 4.8분(28배속) + 847구간 판독 13.4분 = **18분**.
원본 순차 디코드 117.8분, 조밀 OCR 143분과 비교된다.

오독 필터 교체 효과 (같은 관측 282개):

```
그리디            앵커 153개
최장 증가 사슬    앵커 200개     (탈락 129개가 전부 "인덱스 역행"이었다)
```

홀드아웃 4겹 — 관측을 4등분해 한 겹씩 빼고 적합, 뺀 겹에서만 측정:

```
방법              n   |오차| 중앙   평균    p90    ±1구   ±2구   초오차중앙
새 앵커          50      1.00    1.14    1.3    92%    95%      10.6
균등 분할(기준선) 50      7.38    7.74   14.7     8%    16%     180.9
기존 앵커 33개    50      1.00    3.27   10.7    64%    71%      16.9
```

TS-032에서 홀드아웃 없이 봤다가 속은 적이 있어(적합 70% / 홀드아웃 3% / 균등 9%)
기준선을 항상 같이 잰다.

독립 검사: 같은 투수 안에서 P:N이 1 늘면 인덱스도 1 늘어야 한다. 이 성질은
적합에 쓰이지 않는다. **180/181 = 99%** 일치.

결과

- 앵커 33 -> **200개**, 앵커 간 최대 간격 1139초 -> **547초**.
- 앱 코드는 안 바뀐다. `fixed_demo_anchors.json` 형식이 `[{t, counter}]` 그대로다.
- 기존 65개 관측은 합치지 않았다. 합쳐도 앵커가 2개 늘 뿐이고 최대 간격은 그대로인데,
  `build_timeline_anchors.py`가 "불가능한 값"이라고 적어둔 t=866.9s P=2 를 다시
  들이게 된다.

한계

- 스코어버그가 떠 있는 시간이 전체의 58.8%다. 320구 중 200구까지가 이 한계다.
- 앵커가 커버하는 인덱스는 0~314. 마지막 5구는 외삽이다.
- 최장 증가 사슬은 O(n^2)이다. 관측 수백 개, 경기당 한 번(앱에서 캐시)이라 문제
  없지만 수천 개가 되면 다시 봐야 한다.
- 크롭 좌표(104:24:1120:551)는 이 중계에만 맞다. ADR-0013의 한계가 그대로다.
