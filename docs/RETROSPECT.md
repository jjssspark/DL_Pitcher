## Keep — 계속 할 것

### 1. 실패한 시도를 지우지 않는다

트러블슈팅 40건 전부에 "시도했지만 안 된 것" 항목을 남겼다. 지우면 같은 길을 다시 간다.
TS-032에서 폐기한 접근을 적으며 "다음 후보(미실행)"를 같이 써뒀는데, 그게 다음 세션의
출발점이 됐고 TS-033에서 앵커 33개 → 200개로 이어졌다. 실패 기록에 방향을 남기는 값이
여기서 나왔다.

### 2. 틀린 결정은 지우지 말고 상태만 갱신한다

ADR 14건 중 2건이 나중에 뒤집혔다(0001 대체됨, 0004 부분 대체됨). 지우고 새로 쓰는 대신
상태를 갱신하고 대체한 결정 번호를 적었다. 왜 그때 그렇게 판단했는지가 남아야 같은 착각을
반복하지 않는다.

### 3. 지표 대신 실제 입력을 눈으로 본다

TS-014에서 감지 박스를 프레임에 그려본 10분이, 앞선 몇 시간의 특징 튜닝을 전부 대체했다.
이후 탐지기를 교체할 때는 scripts/verify_ball_detector.py로 실제 영상에 박스를 그려
확인하는 것을 통과 기준으로 삼았다.

### 4. 나빠진 수치도 그대로 싣는다

CV 정확도를 76.7%(n=43)에서 66.4%(n=125)로 내려 적었다. 표본이 경기 초반에 치우쳐 있었던
게 확인됐기 때문이다. 포트폴리오에 좋은 숫자만 남기면 그 숫자가 어떻게 나왔는지 설명할 수
없게 된다.

## Problem — 실제로 겪은 문제

### 1. 파이프라인 맨 밑단 가정을 검증하지 않고 그 위에 쌓았다

"YOLO가 공을 잡는다"는 프로젝트 전체가 딛고 선 전제였는데 확인하지 않은 채 특징 공학,
필터, 분류기, 평가를 그 위에 쌓았다. 실제로는 감지 713건 전부가 글러브였다(TS-014).
전제가 틀리면 그 위 작업은 정교할수록 낭비다.

### 2. 같은 유형의 문제가 네 번 재발했다

정지 물체 오탐이 궤적 사슬의 앞, 뒤, 한가운데, 전체로 위치만 바꿔가며 계속 들어왔다
(TS-015 / TS-017 / TS-019). 그때마다 들어온 위치를 막는 식으로 대응해서 네 번째까지 갔다.
사슬을 구성하기 전에 정지 후보를 제거하는 방식으로 바꾸고 나서야 끝났다.

### 3. 검증이 비싼 가설을 먼저 믿었다

배포 환경에서 성능이 떨어지자 "도메인 격차"로 결론지었다(TS-025). 실제 원인은 학습과
추론의 프레임 샘플링 설정 불일치였고, grep 한 번이면 확인되는 것이었다(TS-028).
도메인 격차는 맞다고 믿는 순간 재수집·재학습으로 직행하는 비싼 가설이다.

### 4. 화면에 뜨는 임시 집계를 성능 수치로 썼다

앱이 표시하던 "이번 세션 x/y"가 그대로 대표 수치가 됐다. 시연 때마다 영상을 처음부터
트니 경기 초반만 반복 채점됐고, 10%p 과대평가로 이어졌다(TS-036).

### 5. 기준선을 랜덤으로 잡았다

8분류 예측은 랜덤 12.5%, CV 분류는 랜덤 33%를 기준으로 삼고 있었다. 클래스가 불균형하면
아무것도 학습하지 않아도 최빈 클래스 비율만큼 나온다. 실제 기준선은 각각 34.3%, 49.6%였다.

## 행동이 어떻게 바뀌었나

전반부(ADR-0001~0008, 7/27~8/3)와 후반부(ADR-0009~0014, 8/6~8/11)를 같은 기준으로 비교했다.

| 항목 | 전반부 | 후반부 | 근거 |
|---|---|---|---|
| 결정에 실측 근거 명시 | 8건 중 2건 (25%) | 6건 중 6건 (100%) | ADR 상태 표기 |
| 성능 주장에 통계 검정 | 0건 | 3건 | 순열검정 p=0.017, LOGO 교차검증, 이항검정 p≈0.004 |
| 기준선 기준 | 랜덤 (12.5% / 33%) | 최빈 클래스 (34.3% / 49.6% / 53.6%) | day2.md, TS-036 |
| 모델 교체 절차 | 학습 후 mAP만 확인 | 학습 전 데이터셋 검증 + 학습 후 실영상 박스 확인 | ADR-0009 |
| 화면 성능 수치 | 하드코딩 | JSON을 정답과 대조해 매번 계산 | TS-036 |
| 정지 오탐 대응 | 들어온 위치를 막음 (4회 재발) | 사슬 구성 전에 제거 (이후 0회) | TS-015 / 017 / 019 |
| 테스트 | 0개 (8/5 이전) | 115개 | tests/ |

가장 크게 바뀐 건 순서다. 전반부에는 만들고 나서 성능을 쟀고, 후반부에는 재기 전에 입력이
맞는지부터 확인했다. ADR-0009에서 학습 전에 라벨 박스 크기 분포를 정량화하고 GT를 렌더링해
눈으로 본 10분이, ADR-0001의 실패를 반복하지 않게 했다.
